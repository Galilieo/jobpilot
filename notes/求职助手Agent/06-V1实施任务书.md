## 执行者须知

本任务书可以交给其他 AI 助手带领执行。执行前请先读：

1. [README](./README.md) 的设计冻结规则，以及 [00](./00-总览与决策.md)、[02](./02-技术架构与数据模型.md)。遇到本任务书没写到的细节，以 02 为准；与 02 冲突时停下来问用户，不要自行改设计。
2. [学习导师提示词](../学习导师提示词.md)与[代码注释规范](../代码注释规范.md)：重复和样板部分由助手直接写，核心部分带用户写；不管谁写的，都要讲清「做什么、为什么、怎么验证」。

执行规则：

- 按任务编号顺序做，一次只做一个任务；做完先跑验收，再进入下一个。
- **先做 P0，再做 P1**：每个任务里属于 [00 第 3.0 节](./00-总览与决策.md#30-v1-最小闭环p0与可延后p1) P1 的部分先跳过，P0 全部完成后再回来补；时间不够的 P1 推到 V1.1，并在进度表里注明。
- 每个任务完成后直接提交到 main（个人仓库，不开分支）；不推送，除非用户要求。
- 不提交密钥、`.env`、真实简历、JD 原文（放在 `evals/private/`）。
- 每周结束时在 [05 落地与里程碑](./05-落地与里程碑.md)记录实际进度；发现设计问题时，按冻结规则写明原因再改。

- 2026-11-21 备注（实施 ③ 时讨论）：
  - P1 多张截图去重的另一条路：先在**像素层面**找相邻两张截图的重叠行、拼成一张长图，再做一次 OCR，就不需要按文字去重（同一行在两张图里可能识别得不一样，正文里也可能本来就有相同的句子）。坑：App 顶部的状态栏和悬浮标题栏每张都一样，容易被误判为重叠区。做 P1 时与「比较交界处首尾几行」对比后再选。
  - 单张高图目前在空白行处切段、不重叠，所以不用去重；找不到空白行时只能硬切。E1、E2 用真实截图评测时若发现硬切错行，再改为「重叠切段 + 按坐标合并文字框」，改动只在 `split_tall_image` 和 `_ocr_image` 内部。
  - 线程池：`run_in_threadpool` 默认共用 anyio 的 40 个线程，而 OCR 用 `threading.Lock` 排队，等锁的请求各占一个线程。同时排队的 OCR 请求一多，线程池会被占满，其他要用线程池的操作（同步接口、`UploadFile` 读取落盘的大文件）跟着卡住。**已改（2026-11-21）**：`api/ocr.py` 的 `OcrQueue` 让请求在事件循环里排队（`anyio.CapacityLimiter(1)`，等待时不占线程，也不用共用线程池），正在识别加排队超过 4 个直接返回 503。同时发现登录、注册的 argon2（约 20 毫秒）直接在事件循环上计算，一并改为放到线程池。
- 测试：OCR 用一张自带的合成截图，只断言能识别出几个关键字；排序用假的模型客户端，覆盖正常排序、非法顺序（重复或缺编号）退回上传顺序、重叠行去重、单张图片不调用模型。
- 事实拆分：通过网关调用模型，输出符合 Pydantic 模型的原子事实列表（经历、类型、职责程度、内容、是否含数字、原文片段）。
- 原文校验：来自简历的事实保存 `source_quote`，程序校验它确实是简历原文的一段（去掉空白后比较），结果写入 `quote_verified`。未通过的事实留在草稿请用户核对，校验通过后才允许确认。
- 2026-11-22 备注（实施 ④ 时讨论）：
  - 设计对照：先分段再定位，与 OpenResume 先识别段落再抽取一致；片段对应到原文位置，与 Google LangExtract 的做法一致；用校验器检查引用是否在原文中，类似 Instructor 的引用校验。区别是找不到就阻断，不做模糊匹配后自动接受。
  - 以后的选项：模糊匹配找到的位置只作为候选高亮给用户看，不自动通过；按段分别调用模型可以缩小提示注入的影响范围（现在模型一次看到整份简历，分段限制不了注入），代价是调用次数增加。
  - 第 ⑤ 步要注意：如果做「全部确认」，带核对原因的条目必须排除在外；前端高亮时，Python 按字符计算的位置要换算成 JavaScript 的 UTF-16 位置，否则遇到表情符号会错位。
  - 评测：拆分在 E1 标注完成前就已实现，偏离了 04 的「先有评测集」原则，已在 [04 第 1.1 节](./04-评测方案.md#11-开发前要回答的五个问题)记录。提交后先标注 5 份合成简历、跑第一版 E1，再决定是否调整提示词。
- 矛盾规则：同一类字段（成绩、日期、同一段经历中的数字）出现不同值时标记为矛盾，返回给调用方，由第 3 周的 `ask_user` 向用户提问。职责程度用 Enum（lead / own / participate / na）；原文没有明确说法时默认 participate，并在返回结果里标记「需要用户核对」。
- 接口：按 [02 第 6 节](./02-技术架构与数据模型.md#6-接口v1)实现上传、查询、修改、确认、补充、删除、提交新版本。
- 第 ⑤ 步设计（2026-11-23，接口见 02 第 6 节的调整说明）：
  - 草稿条目 `items_json` 每项：`lineage_id`、`status`（pending 待确认 / confirmed 已确认 / deleted 下一版移除）、事实字段（经历、段落类型、类型、职责、文字、含数字、来源与出处）和 `review_reasons`。拆出的新事实是 pending；用户补充的事实直接是 confirmed（就是用户自己的说法）；修改已发布的事实时，先把它复制成草稿条目再改。
  - 修改规则：改了文字就转为用户补充，去掉出处和核对原因，`has_number` 按新文字重算；只改职责时去掉职责类的核对原因；简历来源且原文校验没通过的条目不能确认。
  - 批量操作：`confirm_clean` 确认全部没有核对原因的待确认条目；`set_responsibility` 把某段经历里职责未写明的待确认条目设为用户给的职责并去掉这项原因（只适用于项目和实习），之后它们若没有别的原因，就能被 `confirm_clean` 确认。
  - 发布：锁住草稿行，核对请求带的基准版本、草稿的基准版本和最新版本三者一致，否则 409；新版本 = 上一版里草稿没动过的事实（复制一行，`lineage_id` 不变）+ 已确认的条目；deleted 的不再出现；pending 的留在草稿；没有任何改动时返回 400。全部在一个事务里。
  - 模型客户端和 session 工厂通过依赖注入，测试替换为假上游和测试库。
  - 验收测试（先于代码写好）：越权一律 404（隔离测试登记 `fact` 与 `resume_document` 两类资源）；未确认、原文校验未通过的事实不进入版本；30% 改 20% 后旧版本不变、新旧两行共用 `lineage_id`、新行为用户补充；两次并发发布只有一次成功，另一次 409；发布中途出错时数据库没有半个版本；两种批量操作只影响该影响的条目。
- 规则：只有已确认的事实能进入提交的版本。发布后 `fact` 按新版本追加，同一事实修改时沿用 `lineage_id`。

**验收：** 用合成简历走通「上传 → 拆分 → 修改确认 → 提交版本」。未确认事实与原文校验未通过的事实不进入版本。修正 30% 为 20% 后，旧事实不变，两条事实共用同一个 `lineage_id`。验证组合外键拒绝跨用户的事实与版本关联。另上传两份包含同一片段的原文，验证 v3 事实能精确定位原文的 doc_id 和位置；若 20% 来自用户纠正，v4 标记为用户补充。用两张含合成电话的截图验证排序输入已遮蔽；用户将 OCR 识别的 80% 改为 30% 后，按 source_span 从保存的 raw_text 取出的片段与 source_quote 一致，即使外发占位符改变了文本长度。矛盾规则有单元测试，接口加入隔离测试。

2. 拆得比标注粗：「负责借领和归还接口，使用 PostgreSQL……」这类「负责某接口 + 用某技术实现」合成一条；「协助核对……，整理字段说明」合并后，后半句职责未写明的提示也随之消失。
3. 新规则 7、10 和项目简介没写进提示词：模型把「产线布光和相机位置由企业工程师确定」当成候选人的事实（标了职责未写明），也拆出了局限说明和项目简介。
4. 片段漏抄前一分句的职责词，第三次出现：v1、v2 都没解决，说明只靠提示词不够，考虑改程序。

英文探针 resume-019：召回率 95%（修订后）；精确率 61%，误标主要来自「Owned」不在角色词表里，符合预期。

**已知限制：PDF 硬换行。** 从 PDF 提取的文字常在句子中间换行（「响应时间↵降低 30%」），按行、按句划定职责词的作用范围都会断开，结果和细节会被多提醒。方向偏安全，暂不处理；以后可以在提取阶段合并不以要点符号开头的续行。

## 5. 第 2 周：匹配、改写、依据检查与完整简历

### T2.1 匹配报告（F3）

- 迁移：`match_report` 通过组合外键关联同用户 `ai_run`，补齐 `ai_run.job_snapshot_json`。匹配开始时固定事实版本及合并个人修改后的岗位快照，报告沿用快照内的要求 ID。
- 模型判断每条要求已覆盖、部分覆盖、未覆盖，并引用事实 ID；程序校验引用的事实存在、属于该用户、本次运行的 fact_set_id 且已确认。
- 程序把「已覆盖」中引用事实全部来自用户补充（`source = user`）的条目改判为「表达缺口」，并写单元测试；硬性要求单独汇总。
- 不输出笼统的匹配度分数。

**验收：** 用户修改岗位要求后，旧报告仍显示匹配时采用的条目，新报告采用修改后的要求。单独测只改 JD、事实集不变，以及 30% 改为 20% 并更改 JD 两种情况；旧报告保留 v3 和旧要求，新报告分别引用本次快照中的事实和要求，拒绝同一用户其他版本的事实 ID。

### T2.2 依据检查第一、二层（纯函数）

**2026-11-24 设计决定。** 已知局限：两段同名实习只按经历名比较，第一年的成果可能写到第二年。后续在同一底稿内用文档 ID 和段落起点区分，验收同名、不同时期的跨段引用被拦下。

- 第一层：引用存在、已确认、属于本次版本、同一段经历（技能概述除外）。
- 第二层：从改写文本提取数字、技术名、组织名、角色词、程度词，与引用事实比对。角色词的等级与引用事实的 `responsibility` 字段比较；程度词（了解 < 熟悉 < 熟练 < 精通）与事实文本比较。角色词表、程度词表、同义词表放在配置文件里。
- 这是项目核心，**测试要最充分**：六种编造类型各写多个用例，正常改写也要有足够用例，防止误拦。

### T2.3 依据检查第三层（模型）

- 独立的 `ground_check` 调用，只输入「改写句子 + 引用事实原文」，非思考模式、temperature 0。
- 输出：支持、部分支持、不支持，以及不支持的片段。

### T2.4 改写流程图

**2026-11-24 设计决定。** 由 Claude 在第三步实现。第一段通过而第二段在调用前耗尽预算时，查询接口只读业务表。耗尽时用一次事务保存已通过或回退的 tailored_bullet，在 ai_run 记录停止原因、未处理的经历；未检查的句子不入库，也不发布完整版本。关闭页面、重启后应能查到第一段和第二段的停止位置。匹配报告只说明已确认事实能否支撑要求；plan 按所选底稿判断已写到、建议补入或待核对。同人同 JD 换两份底稿，能力结论相同，补写建议可以不同。

- 迁移：`tailored_bullet`、`bullet_fact` 表。改写沿用 `ai_run`，新增 `base_doc_id` 关联本人简历，启动时固定所选底稿、事实集和岗位快照，引用用组合外键校验同一用户和事实库版本。
- LangGraph 图按 [02 第 3 节](./02-技术架构与数据模型.md#3-改写流程图v1-核心)：load_inputs → match → plan → rewrite → ground_check → revise / fallback → finalize。
- 检查点：`AsyncPostgresSaver`。自己建连接或连接池时必须带 `autocommit=True` 和 `row_factory=dict_row`（官方说明，否则建表可能不生效、读取会报错）；首次使用调用 `setup()`。
- `ai_run.thread_id` 保存 `{user_id}:{run_id}`。V1 启动时把遗留的 running 标为 failed，填写 finished_at 和可由状态接口读取的停止原因「服务重启」。
- 执行入口集中在一个函数：第 3 周由 `tailor_resume` 工具在对话中调用，面板的「重新生成」用进程内后台任务调用。
- 改写时每条只放入相关事实和对应 JD 要求（[02 第 11.3 节](./02-技术架构与数据模型.md#113-各场景的做法)）。

**验收：** 端到端测试（假模型）覆盖全部通过、修订后通过、两次修订仍失败而回退、预算耗尽。数据库测试覆盖条目引用同用户当前运行采用的事实、拒绝跨用户及跨事实版本的引用。模拟运行失败，检查状态、finished_at 和独立提交的调用用量。

- 上传 A 再上传 B，默认改写选 B；显式指定 A 时选 A。启动后再上传 C，验证两个运行的 base_doc_id 均保持原值。
- 让一条通过、下一条耗尽预算，断言查询接口返回 budget_exhausted、已通过和未完成的条目、停止原因，未发布完整简历版本。
- 在改写节点执行中重启进程，断言旧 running 变为 failed、原因为「服务重启」，没有从中间节点再次调用模型。

### T2.5 完整简历与导出（F5）

**2026-11-24 设计决定。** 建 resume_version 表前确定：检查绑定版本、条目及受检文字。v2 检查比 v3 保存更晚时，仅更新 v2；先保存的版本显示待检查。分别打开 v1～v3，文字与结论应一一对应。离线 HTML 改动受检文字后，原通过标记失效。

- 迁移：`tailored_resume`、`resume_version`。首次组装和保存编辑都新增版本，在同一事务内更新当前版本指针。完整简历组装成功后发布。回退条目只使用本次事实集的已确认事实文字，无有效事实时标「待处理」；未改写的部分沿用固定底稿。
- 简历模板 `templates/resume.html` 加内嵌编辑脚本，工具栏按 [01 F5](./01-功能设计.md#f5-完整简历预览编辑与导出v1) 的 V1 功能实现；编辑脚本在应用内通过 `postMessage` 保存，单独打开时保存在浏览器本地。
- 导出 HTML（主要格式，去掉依据标签）、DOCX、Markdown；PDF 用浏览器打印（写好打印样式）。
- 每条改写保存依据的事实编号与检查结果，供面板的「依据追溯」显示。

**验收：** 组装规则的单元测试通过，编辑保存后仍能读取旧版本，导出的 HTML 单独打开可以编辑和打印。模拟 finalize 成功提交后、checkpoint 写入前重启；查询已成功的 run 或再次调用 finalize，仍只有一份简历、一个初始版本和一套条目与引用。用 A 请求 B 的运行状态、简历版本和导出，均返回 404。

- 底稿写 30%，本次已确认事实为 20%。强制两次修订失败，组装结果与导出 HTML 只使用 20%；移除有效依据再测，条目标「待处理」，成品里没有旧句。教育等未改写部分与固定底稿相同，再上传一份简历也不改变旧版本导出。
- 两个浏览器标签页从 v1 开始编辑，第一处保存为 v2，第二处携带 base_version_id=v1 保存时收到 409，保留本地草稿，当前版本仍是 v2。

## 6. 第 3 周：对话 Agent

### T3.1 会话与消息

**2026-11-24 设计决定。** 建表时用 PostgreSQL 条件唯一索引限制同一对话同时只有一个 running 或 waiting_confirmation 的运行。分页面对已有待确认卡发新消息，应返回原运行和卡片；另一个对话可以继续执行。

- 迁移：`conversation`、`message`、`agent_action`、`memory`、`application` 表（02 第 5.1 节）。
- 接口：会话列表、新建、获取、改标题与当前岗位、删除（02 第 6 节）。

### T3.2 Agent 图与工具（核心）

**2026-11-24 设计决定。** 建 agent_action 表前确定撤销前提：目标仍处于该动作生成的版本。Agent 生成 v4 后用户编辑成 v5，此时撤销返回 409 并保留 v5。允许撤销事实时追加一个还原版本，最新版本仍按最大版本号读取。

- 按 [02 第 2.2 节](./02-技术架构与数据模型.md#22-对话-agent-与工具v1-核心入口2026-11-16-新增)实现：build_context → call_model（带工具）→ 读取 / 生成类直接执行 → 写入类与提问类 `interrupt()` 暂停 → 用户决定后恢复。
- 工具按读取、生成、写入、提问四类定义；工具只接收登录态的 user_id，模型不能传入用户。
- 写入类工具先写 `agent_action`（pending），修改卡绑定 base_version_id，确认后执行，按 action_id 保存决定、执行结果与撤销信息；`POST /api/actions/{id}/undo` 实现撤销。
- `ask_user`：把第 1 周的原文校验失败、矛盾、职责程度不明，以及当前岗位缺少的关键信息合并成一张提问卡片。
- 当前岗位软绑定：第一次解析出 JD 时自动设置；再发 JD 时用提问卡片询问「新开对话 / 切换 / 保持不变」。
- 预算：每次运行的工具调用次数、token、时长上限。
- 检查点：`ai_run.thread_id` 保存 `{user_id}:{conversation_id}`。补 `ai_run.conversation_id` 关联列及外键，恢复前校验运行和对话归属。

**验收（假模型）：** 写入类操作未经确认不改动任何数据；拒绝后不执行；撤销后数据回到原状态；用 A 的工具读写 B 的岗位、事实、运行和简历版本，覆盖动作参数里嵌套 B 的 ID，验证 B 的数据未变。用真实 Postgres checkpointer 暂停后新建图实例，分别覆盖拒绝、确认、双击确认、业务已提交但 checkpoint 尚未前进；拒绝只留下审计信息，确认最多产生一份结果。同一卡重复提交返回第一次的结果；出卡后另行修改目标版本，首次确认旧修改卡返回 409 并保留草稿。

- 对话只剩一次模型调用时启动改写，子图尝试第二次发送时停止。检查本轮只扣一次、fake 只收到一次请求，并核对 T2.4 的部分结果。
- 让对话在卡片处进入 waiting_confirmation 后重启。原卡继续等待；确认或拒绝后恢复原动作。用涉及既有改写结果的卡验证：等待期间上传新简历，确认后读取和导出的仍是原运行固定的底稿。

### T3.3 流式输出

- `POST /api/conversations/{id}/messages` 与 `POST /api/conversations/{id}/actions/{action_id}` 返回 SSE：`text`、`tool_start`、`tool_end`、`confirm`、`done`、`error`（02 第 2.2 节）。
- 后端进程持有运行，SSE 客户端断开后结果照常写入消息表。

**验收：** 用本机 HTTP 客户端收到首个工具事件后断开，保持后端进程运行；重新打开同一对话能查到完成结果，业务写入只有一次。

### T3.4 上下文与记忆

**2026-11-24 设计决定。** 建表前确定：偏好确认卡真正写入时核对目标是否更新或删除。先出卡再删除偏好，确认旧卡应失效；用户之后主动重新提出可以另建。

- 按 [02 第 11 节](./02-技术架构与数据模型.md#11-记忆与上下文管理)拼装上下文。P0：只放最近 N 轮，超过历史 token 上限时从最早一轮丢弃（N 与上限写进配置，初值见 02 决定 30）。P1：丢弃的轮次压缩进 `conversation.summary`。
  - 验收（假模型）：构造 15 轮对话，检查发给模型的消息只有最近 10 轮；把单轮内容加长到超过上限，检查从最早一轮开始丢弃且至少保留最近一轮；数据库里 15 轮消息全部保留。
- 轻量长期记忆：`remember` 工具（写入类，需确认）；每次对话放入全部记忆；删除后防重建；改写只把写作偏好用于措辞。
- 记忆接口：查看、修改、删除。

### T3.5 轻量投递追踪（F9）

**2026-11-24 设计决定。** 建 application 表前确定：同一岗位第二次投递有独立阶段，列表展示最近一次投递的阶段，收藏、归档属于岗位。验证第二次进入面试后第一次投递仍保留原阶段。

- `record_application` 工具（写入类，需确认）与 `POST /api/applications`：面板提交选定的 resume_version_id；投递卡在出卡时保存该 ID，确认时冻结其内容、事实库版本和 HTML。详情显示「记录投递时选定的版本」。
- 进度更新；`GET /api/applications/{id}/diff`：按条目比较快照与当前简历、列出投递后事实库的变化、标出后来被回退或改弱的表述（程序计算）。

**验收：** 使用事实库 v3 生成写有 30% 的简历 v1 并记录投递，再发布含 20% 的 v4 并修改岗位要求。新改写使用 20% 和新要求，旧报告、旧改写仍指向旧要求、v3 事实及对应原文。投递的 resume_version_id、快照 JSON 和 HTML 保留 v1 的 30%，更新进度也不能改写快照。覆盖 A 引用 B 的简历版本创建投递、访问 B 的投递对比以及反馈目标指向 B 的资源。另测为 v1 出卡、另页保存 v2 后再确认：详情和快照仍是 v1；同一 action_id 再提交返回原投递记录。离线编辑导出的 HTML 后，系统仍展示所选服务端版本。

## 9. 调研中发现的注意事项

- DeepSeek 开启 JSON Output 时，prompt 中必须出现「json」字样并给出格式示例，且 `max_tokens` 要设够，否则输出可能被截断（官方说明）。
- 思考模式下 `temperature` 等参数不生效也不报错，容易误以为设置成功；网关要按用途明确设置思考开关。
- `langgraph-checkpoint-postgres` 的连接要求 `autocommit=True` 与 `row_factory=dict_row`，与 SQLAlchemy 的连接分开管理（两者都用 psycopg 3，但不共用连接）。
- Colima 在电脑重启后不会自动启动，启动脚本要先检查。
- `docker compose down -v` 会清空数据库，平时只用 `down`。
