## 2. 整体架构

下图是以后开放给他人时的完整形态。V1 本地运行时没有 Caddy，其余结构相同；「认证与归属校验」一层在 V1 照常实现。

**用户隔离的实现原则：**
- user_id 只来自登录态，由依赖注入提供给路由，**不接受请求体或查询参数中的 user_id**。
- 数据访问函数的第一个参数都是 user_id，SQL 一律带 `WHERE user_id = ?`；按 ID 查单条记录时，ID 和 user_id 一起作为条件，查不到就返回 404（不区分「不存在」和「无权访问」，避免泄露其他用户的数据是否存在）。
- 关联数据（例如事实引用、岗位、改写运行）在使用前再校验一次归属。
- 向量表（V2）带 user_id 外键并级联删除，检索 SQL 同样带 user_id 条件；LangGraph 的 thread_id 带上 user_id 前缀，并在恢复运行前校验归属。

```text
浏览器（前端）
   │  HTTPS
   ▼
Caddy（HTTPS、静态文件）
   │
   ▼
FastAPI
 ├── 认证与归属校验：每个请求从登录态取 user_id，所有数据按 user_id 隔离
 ├── 对话接口：会话、消息（SSE 流）、确认操作
 ├── 业务接口：事实库、岗位库、简历编辑与导出、记忆（供右侧面板和「我的」页面直接使用）
 ├── Agent 层（LangGraph）
 │     ├── 对话 Agent：工具调用循环；读取与生成直接执行，写入先暂停等用户确认
 │     ├── 工具：按读取 / 生成 / 写入三类权限分组，内部调用能力层
 │     ├── 改写流程图（改写工具内部运行）
 │     └── 模拟面试（V2，对话的一种模式）
 ├── 能力层
 │     ├── 文件解析     ├── 依据检查     ├── 注入检测
 │     ├── 检索（V2）   ├── 记忆（V2）   └── 导出
 ├── 模型调用层：统一入口、重试、预算、调用记录
 └── 存储：PostgreSQL（业务数据 + checkpoint + pgvector 向量）
```

### 2.2 对话 Agent 与工具（V1 核心入口，2026-11-16 新增）

用户的入口是对话。每条用户消息触发一次 Agent 运行：

```text
用户消息（含附件） ──▶ build_context（第 11 节：记忆、当前岗位摘要、历史摘要（P1）、最近 N 轮）
                          │
                          ▼
                     call_model（带工具清单，流式输出文字）
                          │
            ┌─────────────┼───────────────────────────┐
            ▼             ▼                           ▼
        没有工具调用   读取 / 生成类工具              写入类工具
        回复结束      直接执行，结果回到模型          interrupt()：推送确认卡片，暂停
                                                      │
                                         用户确认 ──▶ 执行 ──▶ 回到模型
                                         用户拒绝 ──▶ 把「用户拒绝」告诉模型 ──▶ 回到模型
```

**工具与三类权限**（工具只能拿到登录态的 user_id，模型不能指定用户）：

| 类别 | 工具 | 权限 |
| --- | --- | --- |
| 读取 | `read_facts`、`read_job`、`list_jobs`、`read_match_report`、`read_resume`、`read_memories` | 自动执行 |
| 生成 | `parse_resume`（含 OCR）、`parse_jd`（存入岗位库）、`match_job`、`tailor_resume`（运行改写流程图与三层依据检查）、`export_resume` | 自动执行；只产生新结果或新版本，**不覆盖**已有内容 |
| 写入 | `propose_fact`（新增或修改事实）、`edit_resume_item`、`remember`（写记忆）、`set_current_job`、`record_application`（记录投递并冻结简历快照）、任何删除 | **必须用户确认**：工具先写一条待确认的 `agent_action`，推送确认卡片，用户确认后才执行；确认后的写入可以撤销 |
| 提问 | `ask_user`（原文对不上、说法矛盾、职责程度不明、缺少关键信息时提问，见 01 F1「不确定就问」） | 暂停等待回答；一轮最多一张提问卡片，多个问题合并 |

规则：

- **依据检查在工具内部强制执行。** `tailor_resume`、`edit_resume_item` 生成的简历内容都要过三层检查，Agent 无法绕过；`edit_resume_item` 的检查结果只提示、不阻止用户确认（与 01 F4 手动修改一致）。
- **当前岗位（软绑定）：** 会话记录 `current_job_id`。第一次解析出 JD 时自动设置（这一步不需要确认，因为不改动权威数据）；之后切换或解除由用户在界面操作，或经 `set_current_job` 确认。当前岗位只决定面板显示和工具的默认岗位，读取类工具可以读任何属于该用户的岗位。
- **每次运行的预算：** 工具调用次数、模型 token、总时长都有上限（数值按开发集测量后设定）；超出时停止并告诉用户做到了哪一步。
- **流式事件：** SSE 推送 `text`（回复片段）、`tool_start` / `tool_end`（工具步骤）、`confirm`（确认卡片）、`done`、`error`。客户端断开不影响运行，结果写入消息表，重新打开对话可以看到。
- **恢复：** Agent 图用 Postgres checkpointer。`ai_run.thread_id` 保存 `{user_id}:{conversation_id}`，恢复前校验运行和对话归属。等待确认时服务重启，确认后可以继续。
- **测试必须覆盖：** 写入类工具未经确认不会改动任何数据；拒绝后不执行；工具无法读取其他用户的数据。

参考：对话加右侧产物、产物版本、跨会话记住偏好的整体设计参考 Open Canvas（只参考设计，见决定 25）。

## 3. 改写流程图（V1 核心）

改写流程作为 `tailor_resume` 工具在内部运行，也可以由面板上的「重新生成」按钮直接触发。

```text
START
  │
  ▼
load_inputs        读取本次固定的简历底稿、已确认事实版本与岗位快照；只读取写作偏好用于措辞，不读取其他记忆
  │
  ▼
match              根据本次运行的输入生成匹配报告
  │
  ▼
plan               生成改写计划：保留哪些经历、顺序、每条要突出的 JD 要求
  │
  ▼
rewrite            逐条改写，输出 {text, fact_ids}
  │
  ▼
ground_check       三层依据检查（03 第 1 节）
  │
  ├── 全部通过 ───────────────────────────────▶ finalize
  ├── 有问题且修订次数 < 2 ──▶ revise ──▶ ground_check
  └── 有问题且修订次数 = 2 ──▶ fallback（采用本次已确认事实文字；无有效事实标「待处理」） ──▶ finalize
  │
  ▼
finalize           保存版本，记录运行统计
END
```

### 3.1 状态（State）

| 字段 | 说明 |
| --- | --- |
| run_id | 本次运行 ID |
| user_id | 来自登录态，不由请求体传入 |
| base_doc_id | 启动改写时固定的本人简历底稿 |
| fact_version | 使用的事实库版本 |
| job_id | 岗位 ID |
| match_report | 匹配报告 |
| plan | 改写计划 |
| bullets | 改写条目列表，每条 {bullet_id, text, fact_ids, check_status, issues} |
| revision_count | 修订次数 |
| budget | 剩余模型调用次数与 token |

### 3.2 预算

- 每次改写运行：模型调用次数上限、token 上限、总时间上限（具体数值先按开发集测出的中位数的 2～3 倍设定）。
- 对话发起的改写从本轮对话的剩余额度扣除，包括修订和重试；面板单独启动的改写使用本次运行额度。额度耗尽时停止调用，记录 `budget_exhausted`，接口返回已通过的条目、未完成的条目和停止原因。仅在完整简历组装成功后发布版本。
- 每个用户每天的运行次数上限，防止滥用并控制成本。

### 3.3 恢复

- 后端进程负责运行，SSE 断连只结束此次推送。重启后将遗留的 `running` 标为 `failed`，写入结束时间与「服务重启」原因；已经提交的调用和终态结果保留。
- `waiting_confirmation` 且卡片待决定时继续等待。任务 O 起，已有决定的运行随服务启动补做并继续使用原检查点，详情在同一读快照里返回消息、运行和卡片。改写执行到一半时从 checkpoint 续跑，推迟到 V1 之后。

## 4. 模拟面试流程图（V2）

V2 中作为对话的一种模式：用户在岗位对话里说「开始模拟面试」，Agent 进入下面的流程。

```text
START ──▶ plan_topics（根据 JD 要求 + 事实库项目 + 面经检索，生成考察点清单）
            │
            ▼
         ask（面试官提问；SSE 流式返回）
            │
            ▼
         wait_answer（中断，等待用户回答；使用 LangGraph interrupt）
            │
            ▼
         decide（追问 / 下一个考察点 / 结束）
            ├── 追问 ──▶ ask
            ├── 下一题 ──▶ ask
            └── 结束 ──▶ evaluate（独立评分，引用用户原话）
                           │
                           ▼
                        propose_memories（提出弱项候选，等用户确认）
                           │
                           ▼
                          END
```

- 上下文管理：已结束的考察点只保留摘要（问题、回答要点、判断），当前考察点保留完整对话。
- 多 Agent 对照（V3）：把 ask 与 decide 交给「面试官」，evaluate 交给独立「评分员」，跟单 Agent 版本比较反馈质量和花费。

## 5. 数据模型

私有业务查询从登录态取得 `user_id` 并按它过滤。子表冗余的 `user_id` 要通过组合外键与父表归属保持一致。例如 `fact(fact_set_id, user_id)` 引用 `fact_set(fact_set_id, user_id)`，父表提供对应的唯一约束。岗位归属用 `owner_id`，统计匿名化见第 5.3 节。时间统一用 `timestamptz`（按 UTC 存储）。用于筛选或关联的字段用普通列，结构化内容（如 `parsed_json`、`items_json`）用 JSONB。V2 知识库的切块向量维度随所用模型确定。

### 5.1 V1 表

- **发布事实。** `fact_draft` 承接逐条确认和修改。发布时在一个事务内校验基准版本和出处，写入新的 `fact_set` 和已确认的 `fact` 行。同一原子事实的修订沿用 `lineage_id`，新事实分配新的 ID，从新版本移除事实时保留历史行。
- **固定简历底稿。** 改写启动时将所选简历保存为 `ai_run.base_doc_id`，默认取本人最近上传的简历，用户可在启动前手动更换。以 `(base_doc_id, user_id)` 关联同用户的 `resume_document`。恢复和导出沿用该底稿；条目引用的事实可有各自的来源文档。
- **固定岗位输入。** 匹配和改写启动时，把 `job_posting` 解析结果与当前 `field_overrides_json` 合并，将实际使用的岗位要求及条目 ID 写入 `ai_run.job_snapshot_json`。展示报告和执行改写都读取这份快照。解析新 JD 成功后，同用户的 `user_job_id` 可写回该解析运行。
- **保存改写结果。** finalize 锁住本次运行并核对状态，已成功时直接返回原产物。条目、事实引用、初始简历版本、当前版本指针与成功终态在同一事务提交。重复调用 finalize 返回原结果。若提交后进程重启，已成功的运行保留原产物。
- **记录运行与开销。** 先提交 `ai_run`，再调用模型。发送前用独立短事务登记 `call_id`，初始结果为 unknown，耗时和用量为空。收到响应后用新事务更新同一行，校验失败也保留已知 token。超时或崩溃导致结果未知时保留 unknown 和空用量；重试另记一行。运行状态限 running、waiting_confirmation、succeeded、failed、cancelled、budget_exhausted；后四种为终态，状态与 finished_at 一起写入。普通业务调用必须归入一个运行，预算拒绝发生在发请求前。
- **关联检查点。** 改写使用 `{user_id}:{run_id}`，对话使用 `{user_id}:{conversation_id}`。`thread_id` 只在用到 LangGraph 时填写，同一对话的多次运行可共用一个值，恢复前校验运行和会话归属。

### 5.3 数据删除

**账号（两阶段）：**
1. 申请删除：同一事务记录 `deletion_requested_at`、注销全部登录 session，并取消该用户所有正在执行或等待确认的运行。重复处理同一申请保留原时间。注销后旧 Cookie 返回 401，待删除时重新登录也无法再次申请。运行保存业务结果前在写入事务内通过 `finish_run` 取得终态，已取消就回滚产物。新运行和删号按账号行锁串行化，迁移 `20261125_01` 增加的触发器也检查后台改写派生的匹配运行。删除提交后，后端按本次取消的运行 ID 停止进程内任务。
2. 待删除期（7 天）：可以登录、查看 `/api/me` 的状态与截止时间、下载本人全量数据、恢复和登出。其他需登录的接口返回 403。恢复要求当前时间早于申请时间加 7 天，已到期返回 409。
3. 彻底删除：清理任务逐个重新核对到期状态，删除账号并级联删除私有业务数据。`fact` 通过所属 `fact_set` 级联。`ai_run` 删除时同时清空 `model_call.run_id` 和 `model_call.user_id`，保留匿名统计。以后增加 `event` 时用户外键置空，V2 公开岗位按第 5.2 节保留。清理按账号提交，失败项留待重试，每次记录数量。

对话检查点保存在 `jobpilot_checkpoint` schema，由 LangGraph 的迁移维护。彻底删除前持有账号锁、按 `ai_run.thread_id` 清理检查点、blobs 和 pending writes，和删除账号在同一事务提交。改写子图当前独立运行，由业务运行与产物表记录状态。

**清理任务：** 后端启动时执行一次，之后在进程内每天执行一次。手动清理从仓库根目录运行 `uv run --project jobpilot python -m jobpilot.scripts.purge_accounts`。

**其他内容：** 对话、岗位、改写结果、投递记录等直接删除（前端二次确认）。删除对话不删除其中产生的事实、岗位和简历。经历事实删除只影响新版本，旧版本与用它生成的改写结果保留。

**测试：** 遍历所有需登录的接口以核对待删除账号的访问范围。彻底删除后不能用旧会话或密码取回数据，其他用户也读不到已删资源。恢复后导出数据与申请之前一致。

| POST | /api/jobs/{job_id}/match | 生成匹配报告（只用已发布事实库，固定输入快照） |
| GET | /api/jobs/{job_id}/matches | 列出该岗位的历史匹配报告摘要（按生成时间倒序） |
| GET | /api/match-reports/{report_id} | 按运行固定的岗位快照与事实版本回读匹配报告 |
| POST | /api/jobs/{job_id}/tailor | 启动改写运行，返回 run_id |
| GET | /api/tailor-runs/{run_id} | 运行状态与结果；预算耗尽时返回已通过的条目、未完成的条目、停止原因 |
| POST | /api/tailor-runs/{run_id}/resume/bullets/{bullet_id}/use-facts | 放弃这条改写、改用服务端保存的事实原文组装新版本，并记录 `user_decision = rejected`（2026-11-25 替代原设计的 `PUT /api/tailored-bullets/{bullet_id}`：简历按版本整份保存，单条操作须在简历行锁下核对 `base_version_id` 并追加版本，而不是直接修改运行条目） |
| POST | /api/ocr | 上传一张或多张图片（顺序不限），逐张识别后由模型判断顺序、程序拼接去重，返回文字和采用的顺序（不保存图片），供用户核对后再提交；可带上用户手动指定的顺序跳过模型 |
| GET, PUT | /api/tailor-runs/{run_id}/resume | 获取（可带 `version` 读旧版本，附条目引用的事实）、保存完整简历（二次编辑，携带 `base_version_id`，过期返回 409；返回的是这次保存建立的版本） |
| POST | /api/tailor-runs/{run_id}/resume/reset | 重置：核对 `base_version_id` 后把第一版复制成新版本，旧版本保留（2026-11-25 新增） |
| GET | /api/tailor-runs/{run_id}/preview | 应用内预览页（带检查标记；当前版本内嵌编辑器，旧版本只读）（2026-11-25 新增） |
| GET | /api/tailor-runs/{run_id}/export?format=html\|docx\|md | 导出 |
| POST | /api/feedback | 提交评价 |
| DELETE | /api/account | 申请删除账号，进入 7 天待删除期 |
| POST | /api/account/restore | 待删除期内恢复账号 |

修改类操作携带开始修改时的 `base_version_id`，面板与 Agent 共用服务，在同一事务内核对当前版本并写入。版本不一致返回 409，客户端保留草稿。确认卡先按归属和 `action_id` 读取已处理结果，重送已处理的动作不会重新执行或因版本已变误报冲突。

**2026-11-23 事实接口的调整（T1.4 第 ⑤ 步）：**

- 上传分两步：文件先经 `/api/extract-text`（原 `/api/resumes/extract`）提取文字，用户核对修改后再提交到 `/api/resumes`。事实的原文位置按保存的文字计算，提取错误（PDF 硬换行、双栏交错、乱码）必须在拆分前改掉，与 OCR 的做法一致。
- 用 `lineage_id` 指代一条事实：已发布的事实本来就有，草稿里的新事实创建时就分配。`fact_id` 只代表某个版本里的一行，不用来指代「要改的那条」。
- 批量操作为以后减少用户操作留出接口（E1 测试集每份简历约 17 条事实，带提醒的约 8 条，几乎都是职责未写明，集中在一两段经历里）。界面在第 4 周实现。

面板和「我的」页面上的直接操作（改事实、编辑简历、导出）走对应的业务接口，不经过 Agent；Agent 的工具与这些接口调用同一批服务函数。

除注册和登录外，所有接口都要求登录，user_id 从登录态取，**不接受请求体中的 user_id**。这修正了现有实验中 user_id 由调用方传入的问题（见[工程化职责与心屿交接](../工程化职责与心屿交接.md)）。

## 7. 模型调用网关

所有模型调用都通过 `llm_gateway`，统一处理：

1. **用途标签**：每次调用标明 purpose，便于按功能统计成本和失败率。对话 Agent 的用途为 `agent`，需要工具调用；是否开启思考模式按 E12 评测结果决定。
2. **预算**：检查当前运行与当前用户的剩余预算；对话发起的改写还要计入本轮对话额度。余额不足时在发送前停止。
3. **重试**：只对超时、连接错误、上游 5xx 有限重试；结构化输出校验失败另计一次修复重试。
4. **记录**：发送前登记 `model_call` 并关联 `ai_run`，收到结果后更新同一行。HTTP 成功但输出校验失败按校验失败记录；重试发出前再次检查预算。调用记录独立提交。
5. **隐私遮蔽**：对所有用途（包括 `order_ocr`）在每次发送前遮蔽外发内容中的电话、邮箱、证件号等。用户核对后的原文留在本地供依据定位。
6. **不可信内容包装**：JD 原文、用户回答等不可信文本，统一放进明确的数据区块，不拼接进指令（见 [03](./03-可信安全与隐私.md#2-提示注入防御)）。

## 8. 部署

V1 只在本地运行：README 写明一条命令启动的方法，密钥放在 `.env`（不提交）。以下是以后开放给他人时的方案：

- 一台云服务器，Docker Compose 运行：后端、PostgreSQL（含 pgvector）、Caddy。
- 数据库数据放在挂载卷；每天用 pg_dump 备份一次到对象存储，备份加密。
- 环境变量管理密钥，不写进仓库。
- 日志不记录简历全文、JD 全文和用户回答全文，只记录 ID 和长度。
- 部署地区与备案问题见 [00 第 6 节](./00-总览与决策.md#6-待用户确认的问题)和 [05](./05-落地与里程碑.md)。

## 9. 已确认的架构决定（2026-11-16）

**原则：基础设施尽量简单，核心亮点做深。** 目标是实习岗位，一个人维护得了、每一块都讲得清楚为什么存在。没有 Redis、任务队列和外部观测平台。

## 10. RAG 设计（V2）

| # | 决定 | 内容 |
| --- | --- | --- |
| R1 | 存储 | 与业务数据同一个 PostgreSQL，pgvector 存向量；HNSW 索引，余弦距离 |
| R2 | 检索方式 | **先只做向量检索**作为基线；「jieba 分词 + Postgres 全文检索 + RRF 融合」作为 E9 对照实验，有数据证明有用才保留 |
| R3 | 知识归属 | 切块表 `owner_id`：为空是公共知识（自己整理的面经、八股），有值是某个用户的私有资料（复盘、笔记）。查询条件为「自己的或公共的」。公共内容入库前人工审核 |
| R4 | 模型记录 | 每个切块记录 Embedding 模型名称与版本，换模型时据此重算 |
| R5 | 切块 | 面经按「一道题 + 答案」切块；长文章按段落递归切分。附公司、岗位方向、技术标签、日期 |
| R6 | 检索流程 | 向量检索取前 k 条；不做重排序 |
| R7 | Agent 使用方式 | 出题规划节点**固定检索一次**；追问时检索作为工具，由面试官 Agent 决定是否调用 |
| R8 | 入库 | 资料表记录来源和版本，切块关联资料；更新时删旧切块重新入库；使用与改写任务相同的后台任务机制 |

带过滤条件的近似检索可能召回不足（索引先取近邻再过滤）。每个用户的私有资料很少，可以不走索引直接计算；需要时使用 pgvector 的迭代索引扫描。这一点在 E9 中顺带验证。

现有 `rag_*.py` 中的切块、上下文组装、引用校验思路沿用；`vector_store.py` 基于 Chroma，需按 pgvector 重写。

## 11. 记忆与上下文管理

### 11.1 数据来源

| 层次 | 内容 | 存储 |
| --- | --- | --- |
| 权威数据 | 经历事实库、岗位库、定制简历 | 业务表 |
| 长期记忆 | 用户确认的求职和写作偏好 | `memory` |
| 短期记忆 | 对话原文、滚动工作摘要、运行状态 | `message`、`conversation.summary_json`、LangGraph 检查点 |
| 请求上下文 | 每次调用时组装的内容 | 现场组装 |

### 11.2 对话请求的顺序

1. 固定系统提示词与工具定义。
2. 已确认的长期记忆，按固定栏目顺序写入数据块。
3. 工作摘要，包含目标、要求、已完成和已决定、待处理、提问与答案、待核实。要求保留原话和消息序号或提问卡 ID，可用 `read_conversation_history` 找回。
4. 程序生成的任务状态，包含岗位与绑定修订、事实版本、报告及其输入版本、当前简历版本和有效确认卡。业务正文由读取工具提供。写入、生成和恢复后按数据库刷新。
5. 摘要覆盖点之后仍保留的完整历史轮次，工具步骤以简要结果呈现。
6. 本次用户正文及包装在数据块中的附件。

### 11.3 窗口与压缩

- 见决定 30。每个用途使用登记过的模型档案，协议适配器负责请求字段、用量及超长错误。每轮预算下限为有效窗口的四倍，按 UTF-8 字节预扣额度仍可能先耗尽。
- 窗口估算与费用预扣分别计算。主调用成功且给出用量时，下一次主调用验证发送前缀的哈希，只估算新增后缀。配置变化、请求前缀变化、调用失败或缺用量时重新全量估算。
- 自动和手动压缩使用同一套运行。压缩只处理已结束的完整轮次，模型输入包含上一份摘要与本批移出的轮次。程序核对需求原话来自用户正文或已提交答案。不一致的内容移入待核实。
- 摘要和覆盖点在同一事务条件写入。读请求在同一快照读取摘要及覆盖点之后的原文。压缩后追加的消息仍以原文进入后续请求。
- 窗口不足时只对本次请求临时省略最早完整轮次，并附找回范围。必要时裁剪当前工具结果。服务商返回超长且尚未发送流式正文时，最多用更小的请求重试一次。
- `compact` 有独立的持久化调用额度，共用 `model_call` 账本。失败保留已有摘要，后续尝试缩小已知超长的批次。E11 对照评测留到 T3.6。

### 11.4 写作输入

- 自由文本求职偏好用于对话。初写和修订只读取改写运行建立时固定的三个写作选项，并转成固定措辞句。
- 条目替换直接采用明确的本轮用户原话。开放润色用原条目、已引用事实、写作选项和本轮修改原话单独调用。确认、重放和撤销沿用卡片上已检查的文字。
- 依据检查继续只发送候选文字和事实。模拟面试的弱项记忆与检索属于 V2。
