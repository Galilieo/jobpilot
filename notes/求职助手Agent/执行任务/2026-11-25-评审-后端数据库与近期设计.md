## 怎么评

**只读**：

- 用 `git show`、`git diff`、读文件。
- 不要跑迁移，也不要连开发库。
- 不要跑 `pytest`：测试库是共用的，另一个执行者可能正在用，同时跑会互相清数据。确实需要跑才能确认的，写进报告，说明要跑什么、预期什么。

**每条意见都要能落地**：

- 写出具体的失败场景：什么输入、什么时序 → 什么错误结果。
- 附 `文件:行号`。
- 只是「可以更好」而说不出会出什么错的，归入「建议」。

**和成熟做法对照**：涉及常见问题时，说一下成熟方案通常怎么做，以及本项目的做法差在哪里或为什么够用。常见问题包括：

- 幂等键（如 Stripe 的 Idempotency-Key）；
- 乐观锁（版本号、ETag）；
- 后台任务与租约；
- 软删除与硬删除；
- 多租户隔离；
- 导出的数据可携带。

**用户在学后端**：专业词第一次出现时用一句话解释，例如「可延迟外键」「幻读」「写偏斜」。

## 重点问题（不限于这些）

### 数据库

1. 用户隔离：新表是否都用 `(…, user_id)` 组合外键，绑定同一个用户、同一个事实库版本？有没有能跨用户、跨版本引用的漏洞？
2. 约束：CHECK、UNIQUE 是否和代码常量同一组数？有没有只在代码里校验、数据库能写进非法状态的地方（例如 `stop_reason` 和状态的组合、`current_version_id` 指向别的简历的版本）？
3. 级联与删除：账号删除时，各表的删除顺序、级联、只追加触发器（`fact`）会不会互相冲突？导出是否完整（每张属于用户的表都导出了吗）？任务 C 新增的表和列是否也照顾到了？
4. 迁移：能否回退？加列、加约束时，已有数据会不会让迁移失败？
5. 索引：工作台、列表接口的查询有没有缺索引，或 N+1 查询（一次查询变成很多次）？

### 并发与事务

6. 运行终态：`finish_run` 和产物写入在同一事务。请检查这些情况是否都只有一个结果：两次 finalize、finalize 与启动清理同时发生、后台任务出错与请求取消同时发生。
7. 幂等键：并发两个同键请求（第一个还没完成）时怎么处理？键和请求内容不一致时呢？202 的响应重放时，运行已经结束了，返回什么？
8. 修订号与版本号：草稿的 `expected_revision`、简历的版本冲突（409），是否在读和写之间留有空隙？检查和写入是同一条带条件的 UPDATE，还是先读后写？
9. 改写图并行：多块共用一份预算和信号量，预算扣减是否会超额？一块出错时其他块的结果怎么处理，落库的状态是否和 `plan_json` 一致？

### 接口与安全

10. 简历预览和导出的 HTML 里有用户和模型写的内容，还内嵌了编辑器脚本。转义（Jinja 自动转义、`rich` 过滤器、嵌入 JSON 的 `<` 转义）是否足够？预览页和接口同源，用户的内容能否执行脚本或改别人的数据？需不需要 CSP（内容安全策略）？
11. 编辑后的重新检查：用户改过的条目重跑依据检查第一、二层。检查结果绑定到被检查的文字，能否被前端绕过，比如提交一个声称已通过的条目？
12. 错误码：403/404/409/422/502 用得一致吗？跨用户访问是否一律 404，不泄露资源存在？
13. 待删除账号：哪些接口应该拒绝，现在是否都拒绝了？

### 近期设计（任务 C 等）

14. `fact_set_criteria` 一个版本一行、七个固定字段。对照 JSON Resume、LinkedIn 的做法：多段教育经历（本科 + 硕士）、在读和已毕业放得下吗？字段要增减时迁移成本高不高？`sources_json` 存 JSON 还是拆成子表，哪个更合适？
15. 草稿 `criteria_json` 和事实草稿共用一个修订号。两个人同时改事实和条件时会怎样？这样的设计合理吗？
16. 匹配的程序兜底：JD 里的「每周 4 天以上」「3～6 个月」「本科及以上」「硕士优先」等写法，程序能比对吗？比不了的时候，交给模型是否安全？程序和模型冲突时以程序为准，有没有反过来出错的情况？
17. 事实和条件分开存后，改写、依据检查、对话 Agent 以后要不要读条件？现在的边界会不会让后面的功能难做？
18. T2.6 起的计划里，有没有依赖还不存在的数据或接口、顺序排反、范围过大的任务？

## 回报格式

按严重程度分三组，每组内按重要性排：

- **必须改**：会造成数据错误、越权、数据丢失，或者让任务 C 实施后难以回头。
- **应该改**：现在不出错，但有明确的出错条件，或者会让后续功能明显难做。
- **建议**：可读性、一致性、更好的做法。

每条按这个格式：

```
[编号] 标题（一句话）
位置：文件:行号（设计问题写文档名和小节）
场景：什么输入或时序 → 什么错误结果
成熟做法：……（没有可对照的就省略）
建议改法：……
是否已在 06 或数据库设计里记过：是 / 否
```

最后写：

- 你认为设计得好的地方（三条以内，便于用户判断哪些不要动）；
- 需要跑测试或实验才能确认的疑点；
- 你没看完的部分。
