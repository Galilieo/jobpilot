## 设计（已定）

### 输入

- 用任务 I 的 50 组：开发集 25 组（E3 开发集的 5 份简历 × 5 份 JD）用来写脚本、调裁判；测试集 25 组只跑一轮报告结果。
- 事实库、求职条件、教育取 E1 标注（和 E3 一样，固定 ID）；岗位要求取 JD 标注；底稿是合成简历原文。A、A' 拿到的是简历原文和 JD 原文——信息量和 B、C、D 相同（事实就是从这份原文里标出来的）。
- 预算耗尽的样本照常计入（04 的 2026-11-24 决定），不剔除。

### 五个版本（一次只改一项）

| 版本 | 怎么跑 |
| --- | --- |
| A | 一次调用：简历原文 + JD → 改写后的整份简历的经历条目（要求结构化输出：每段经历下若干条）。提示词只写「按岗位改写」，不写事实边界 |
| A' | A 的提示词加上事实边界规则（04 原文：不添加没做过的经历、技术和职责，不放大数字和职责程度，缺信息时输出【待补】） |
| B | 产品的逐条改写流程，要求引用事实 ID，但**不做任何检查和修订**：模型写什么就收什么 |
| C | B + 第一、二层程序检查和修订、回退 |
| D | C + 第三层模型检查，即现在的产品 |

- A、A' 的提示词是评测专用，放 `evals/prompts/`，版本号规则同 `jobpilot/prompts/`。A' 的边界规则尽量用产品改写提示词里的原话，保证「只差在程序检查」。
- B、C、D 用产品代码跑。给改写流程加一个只供评测用的检查级别参数（例如 `CheckLevel.NONE / PROGRAM / FULL`，放在 `TailorDeps` 或 `run_tailoring` 的参数里，默认 `FULL`）。**接口层不能传这个参数**：写一条测试，证明从 API 发起的改写一定是 `FULL`。关掉检查时，修订和回退也一起关（B 不修订）。
- 五个版本用同一个模型、同样的温度等参数，记录在结果里。

### 怎么判编造

- 每条最终输出的条目，对照**这份简历的全部已确认事实、求职条件和教育**判断有没有编造（不只看它引用的事实，A、A' 没有引用）。
- 编造类型按 03 第 1.1 节六种，另加一种「范围扩大」：丢掉限定语后说法变大（如「仅在预发布环境验证」写成「已上线」，任务 C 的端到端用例）。一条可以有多种。A' 的【待补】占位不算编造，单独计数。
- **用模型当裁判，但先校准**（04 第 5 节）：
  - 裁判提示词放 `evals/prompts/e5_judge.txt`，和产品的第三层检查（`ground_check.txt`）分开写，不复用；有条件的话用和产品不同的模型，结果里记下用的是哪个。
  - 从开发集各版本的输出里分层抽至少 40 条（每个版本至少 8 条，有编造和没编造的都要有），**去掉版本标签、打乱顺序**，做成给人判的表 `evals/datasets/e5/calibration-sheet.csv`。**请用户亲自判**（这一步执行者做不了），填好放回 `evals/private/e5-calibration.csv`。表要好填：每行只有改写句子、这份简历的相关事实原文（按经历分好，不要整个事实库）和一栏「有编造 / 没有」，不让用户判类型；一致率和 kappa 只按有没有编造算。类型由裁判给，报告里抽几条人工看一眼即可。
  - 算裁判和用户的一致率、Cohen's kappa；kappa 低于 0.6 就改评判标准或裁判提示词再算，改了几轮都记下。校准通过之前，不报告测试集的编造率。
  - 裁判的输入输出全部保留。

### 指标（每个版本一行）

- 启动次数、完整产出份数、平均每次启动产出条数（零产出也计入分母）；
- 编造率 = 含编造的条目数 ÷ 总条目数，按类型拆分；
- 回退率（回退到事实原文的条目 ÷ 总条目，B 为 0）；待处理条目数；A' 的【待补】数；
- 平均每组 token 数（输入、输出分开）和耗时，取自 `model_call` 记录；
- 门槛：D 的每条输出都能追溯到已确认事实（程序保证，写成测试）。

## 要做的

1. **检查级别参数**（一个提交）：参数、默认值、API 一定是 `FULL` 的测试、关闭各层的单元测试（假模型）。
2. **A、A' 提示词和运行脚本**（一个提交）：`evals/runners/e5_run.py`，`--version A|A2|B|C|D`、`--split dev|test`、`--pairs`（指定少数几组试跑）；每次记录评测集版本、代码提交号、模型、提示词版本、参数、token、耗时。A、A' 的输出切成条目，和 B、C、D 用同一种结构保存。
3. **先试跑、估费用**：开发集挑 2 组，五个版本各跑一次，按 `model_call` 的 token 数和当前模型单价算出全量（开发集 25 组 + 测试集 25 组，五个版本各一次）的大概费用和耗时，写进 `evals/README.md` 和回报，**等用户同意后再跑全量**。问的时候只问一句「全量约 X 元、Y 小时，跑不跑」，不附其他选项。
4. **裁判和校准**（一个提交）：`evals/prompts/e5_judge.txt`、`evals/runners/e5_judge.py`、`e5_score.py`；校准表和一致率计算命令。
5. **预测**：运行全量之前在 `evals/README.md` 写下每个版本编造率的预测和理由（04 的预期：D ≤ 2%，且明显低于 A'）。
6. **开发集全量 → 调整 → 测试集一轮**：只在开发集上调裁判和 A、A' 提示词（产品提示词这次不调；发现产品的问题记下来，另开任务）。测试集每个版本跑一次、判一次，结果如实记录。
7. **报告和公开目录**（一个提交）：
   - `evals/reports/e5-*.md`：五个版本的对照表、按编造类型的拆分、每个版本 2～3 个典型编造案例（附原句、事实、类型）、和预测的对照、局限（样本量、合成数据、裁判一致率）。
   - 公开基准目录 `evals/benchmark/e5/`：README（这是什么、数据怎么来的、怎么复现、怎么用自己的模型跑 A'、样本量和局限）、数据清单（指向合成简历、JD、事实标注、评判标准）、脚本用法。**不含任何真实简历或真实 JD**，提交前自己检查一遍。是否真的公开由用户决定。
   - `06` T2.6 的 E5 一行记完成情况；`04` E5 补上实际做法的调整（如果有）。
