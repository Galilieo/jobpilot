# 任务 C：求职条件进匹配、抽取保留限定语（「投递前必修」）

日期：2026-11-25（同日按独立评审修订，见「评审后的修订」）。基准：`main` 最新提交。前置：任务 A、B 的提交已在 main（本任务与 B 的账号导出有一处衔接，见第 6 项）。同时在做任务 D（导出与简历保存），文件不重叠，见「协调」。

## 背景

浏览器实测时，合成简历页头写了到岗信息，JD 要求「每周至少到岗 4 天」，匹配报告却判为「未覆盖」。原因有三处，都在设计上：

1. **抽取主动略过**：`jobpilot/prompts/extract_facts.txt` 规则 6 明确不拆「到岗时间」和学历标题行（学校、专业、学位）。
2. **没有合适的存放位置**：事实（`fact`）必须有所属经历、类型和职责。匹配提示词的示例只好把「每周可到岗 3 天」写成「求职意向」经历下的 role，不像事实。任务 A 实测时，用户也是手动补了一条「求职条件」事实来凑。
3. **会被误判成表达缺口**：`jobpilot/services/matching.py` 约 212 行，引用的事实全部来自用户补充时改判为「表达缺口」。对项目经历这是提醒「把做过的事写进简历」；对到岗承诺，用户本人就是信息来源，这个判断会误导。

另外，评审指出抽取提示词自相矛盾：规则 2 说范围说明留在事实里，规则 6 又把「目前只覆盖查询接口」列为要跳过的例子。限定语丢了，后面的依据检查就看不到「成果只适用于什么范围」。

## 已定的设计（用户 2026-11-25 确认）

**结构化存放求职条件和教育，沿用事实库的草稿和发布流程。** 不塞进 `fact`，也不做一份和事实库无关的独立档案：

- 用户在「我的 · 经历」里看到「求职条件」和「教育」两张卡片，和事实一样：抽取出来先进草稿 → 用户确认或修改 → 随事实库一起发布成新版本。
- 跟着事实库版本走，旧匹配报告仍能说明当时依据的是哪个版本的条件（追溯）。
- 匹配时作为单独一块交给模型；能由程序判定的数字和等级**由程序判**；引用求职条件的结论**永远不改判为表达缺口**。
- 改写不使用求职条件和教育；完整简历的页头和教育栏照旧原样出自底稿。

对照：JSON Resume / Reactive Resume 把教育单独结构化，且可以有多条（学校、专业、学位、时间）；LinkedIn 的「Open to work」把到岗时间等求职偏好和经历分开存。我们在这之上保留「有原文出处、用户确认、有版本」，这是本项目的核心。

### 评审后的修订（2026-11-25）

独立评审指出原稿有六处会出错，本稿已改：

| 原稿 | 会出什么错 | 现在 |
| --- | --- | --- |
| 出处只存 `quote + span` | 两份简历都有同一片段时，说不清来自哪份文件；旧报告和账号归档无法还原来源 | 每项出处带 `source_doc_id`，和 `fact` 一样用 `(source_doc_id, user_id)` 组合外键 |
| 一组 `school / major / degree / graduation` | 本科已毕业、硕士在读时分不清；逐字段补空可能拼出「A 校＋B 校专业」这种不存在的经历 | 教育单独成表，每条一段完整经历，含就读状态，整条确认 |
| 程序兜底在模型引用了条件时才触发 | 模型答 `missing` 时按契约不带引用，兜底没有机会纠正；「本科及以上，硕士优先」只取最高等级会误判 | 程序先把 JD 要求解析成结构化要求，独立比对，不看模型是否引用 |
| 没写发布时怎么继承、删除 | 只复制已确认的会丢掉旧值；一律回填旧值会让用户删掉的值复活 | 四种操作写明（§3） |
| 匹配的两个入口各自组装输入 | 「生成简历」的入口只传 `facts`，两个入口对同一版本给出不同结论 | 共用一个按版本加载匹配输入的函数（§4） |
| 删除、改字不强制修订号 | 旧窗口可以删掉另一个窗口刚确认的草稿事实，找不回 | 替换和删除草稿项一律带 `expected_revision`（§3） |

## 要做的

### 1. 表与数据结构（一个提交：模型 + 迁移 + 约束测试）

**出处字段**两张新表都有，和 `fact` 完全一样：`source`（`resume` / `user`）、`source_doc_id`、`source_quote`、`span_start`、`span_end`，同样的 CHECK（来自简历时四项必填、`raw_text[span_start:span_end] == source_quote`；来自用户时四项为空），`(source_doc_id, user_id)` 组合外键到简历文档。能复用 `fact` 的约束写法和校验函数就复用。

- **`fact_set_criterion`**：每个事实库版本、每一项至多一行，唯一键 `(fact_set_id, field)`。
  - `field`：`onsite_days_per_week`、`internship_months`、`earliest_start` 之一；
  - 值：`int_value`（天数 1～7、月数 1～24）或 `text_value`（`earliest_start` 照原文，如「可立即到岗」「2026 年 1 月」），按 `field` 用 CHECK 约束只能填其一；
  - 出处字段。
- **`fact_set_education`**：每个事实库版本可以有多条，每条是一段完整的教育经历。
  - `education_id`（跨版本不变的 ID，类似事实的 `lineage_id`）、`school`、`major`、`degree`（`associate` / `bachelor` / `master` / `phd`）、`status`（`enrolled` 在读 / `completed` 已取得）、`start_text`、`end_text`（照原文，如「2027 届」「2027.06」）；
  - 出处字段：`source_quote` 是这段教育在简历里的原文（可以多行）。
- 两张表都是 `(fact_set_id, user_id)` 组合外键到 `fact_set`，级联删除；**只追加**，加和 `fact` 一样的禁止 UPDATE 的触发器（旧报告要能一直读回当时的条件）。
- 数值与枚举写成 CHECK 约束，代码里的常量和约束用同一组数。
- 草稿：`fact_draft` 加 `criteria_json` 和 `education_json`，每项带状态（见 §3）。草稿的每次修改照样让 `revision` 加 1，事实、求职条件、教育共用这一个修订号：两个窗口同时改不同部分，后提交的收到 409，前端保留本地输入。
- 迁移按 `db/base.py` 命名约定；在含已有事实、草稿、匹配报告、多版本简历的测试库上验证升级、回退、再升级，`alembic check` 无差异，`fact` 的只追加触发器仍生效。

### 2. 抽取（改 `extract_facts.txt`，版本号加 1）

- 同一次调用多输出 `criteria`（三项，各给值和逐字复制的原文片段）和 `education`（列表，每段教育一条，给各字段和整段原文）。简历没写的留空，不推测：「本科在读」不能推出毕业时间；没写「在读」或「已毕业」时，按时间能判断就判断，不能判断的标为需要核对。
- 学历标题行进入 `education`，仍然不拆成事实。
- **限定语**：删掉规则 6 里「目前只覆盖查询接口」这类例子；改为：会改变成果真假或范围的限定语（「只覆盖查询接口」「仅在预发布环境验证」「由导师负责上线」）附在它限定的那条事实里，不单独成条。背景原因（「有一批文件因为超时被重复上传」）仍然不拆。
- `services/facts.py` 解析并定位（复用 `locate_quote`），每项记下来源文档 ID。找不到原文的标为需要核对，和事实的 `quote_not_found` 一样不能直接确认。
- `api/resumes.py` 上传后合并进草稿：已确认的项不覆盖；同一项未确认的用新抽取替换；教育按学校与学位对应，对不上的作为新的一条。

### 3. 草稿、发布与接口

**草稿项的四种状态和发布规则**（求职条件按项、教育按条）：

| 草稿里的状态 | 发布时 |
| --- | --- |
| 没碰（草稿里没有这一项） | 继承上一版本的值和出处 |
| 已确认（新值） | 用新值；用户**只按确认、没改字**时保留简历出处，改了字才变成 `user` |
| 待核对 | 不发布，留在草稿；上一版本有值就继续用旧值 |
| 明确删除 | 新版本里没有这一项 |

- **修订号必须带**：替换和删除既有草稿项（事实、求职条件、教育都算）一律要求 `expected_revision`，在现有的草稿行锁内比较，过期回 409。现在 `DELETE /api/facts/{lineage_id}` 不带修订号，改文字或类型的 `PUT` 也可以省略，这两处一并改掉（行为修复，单独提交，先写会失败的测试：旧窗口删除另一窗口刚确认的草稿事实，应得到 409）。前端 `web/src/api/endpoints.ts` 约 75 行的删除调用同步带上修订号。`数据库设计.md` 里「可以省略」的取舍记录改为现在的规则并写明理由。
- `GET /api/facts`：已发布版本和草稿里都带求职条件和教育。
- `PUT /api/facts/criteria`、`PUT /api/facts/education/{education_id}`、`DELETE /api/facts/education/{education_id}`、`POST /api/facts/education`：修改草稿，带 `expected_revision`。**注意路由顺序**：静态路由 `/facts/criteria`、`/facts/education...` 要注册在 `PUT /facts/{lineage_id}` 之前，否则 `criteria` 会被当成 UUID 校验回 422，写测试确认。
- `POST /api/facts/commit`：按上表发布。只改了求职条件或教育、没有事实改动，也能发布新版本。
- 隔离测试登记新接口；跨用户 404；待删除账号被拒绝（任务 B 的规则）。

### 4. 匹配（改 `match_job.txt`，版本号加 1；改 `services/matching.py`）

**输入：两个入口共用一个加载函数。** 现在「匹配」按钮走 `api/matching.py`，「生成简历」在 `services/tailoring_graph.py` 约 194 行自己组装、只传 `facts`。新增一个按 `(user_id, fact_set_id)` 加载匹配输入（事实、求职条件、教育）的函数，两个入口都用它。改写的规划和改写只取经历事实，不变。前置条件：

- 匹配：事实、求职条件、教育至少有一样就能跑（现在只有条件、没有事实的版本会 422，要改）；
- 改写：仍需要至少一条经历事实，否则 422 并说明原因。

**程序判定，不依赖模型引用。** 新增纯函数模块（例如 `services/criteria_match.py`，不访问数据库、不调模型）：

1. 先把 JD 的**具体要求**解析成结构化要求：对应哪一项（天数、月数、学历、就读状态）、单位、比较方式（至少、范围、等于）、硬性还是优先、原文。「每周至少 4 天」→ 天数 ≥ 4，硬性；「3～6 个月」保留上下界；「本科及以上，硕士优先」→ 学历 ≥ 本科（硬性）＋ 硕士（优先），两条分别判。单位、学历等级、「及以上」「优先」这类词放 `jobpilot/data/criteria_rules.yaml`。
2. 再和已确认的求职条件、教育独立比对：满足 → 已覆盖；低于硬性要求 → 部分覆盖，写「低于岗位要求」；用户没写 → 未覆盖，建议「在『求职条件』里补上」，不建议写进简历。
3. 复合、互相矛盾、读不出数字的要求，以及 JD 基本字段和逐条要求不一致时（两处可以分别被用户改过），标为**待核对**，交给模型并在报告里说明，不由程序硬判。
4. 程序判定的结论覆盖模型的结论；同步更新这条的 `reason`、`suggestion` 和整份报告的 `main_gaps`，不能明细改对了、摘要还报缺口。

**交给模型的部分**：求职条件和教育作为单独的 `<untrusted_data label="criteria">` 区块，每项一个 ID（如 `criteria.onsite_days_per_week`、`education.<education_id>`）。程序校验引用的 ID 存在。提示词示例改掉「求职意向」那条假事实。引用了求职条件或教育的结论**不改判为表达缺口**（`matching.py` 约 212 行的规则只看事实）。

**报告存储**：现在的报告把每个引用都当事实 UUID。改为分开存 `fact_ids` 和 `criteria_refs`；旧报告的 `criteria_refs` 默认为空。报告详情按运行当时的 `fact_set_id` 回读条件和教育（它们只追加，读得回来）。

1. **先标注再运行**：在 E1 标注文件里给开发集样本补 `criteria` 和 `education` 的标准答案，并补「限定语」用例——至少 5 条原文里有限定语的事实，标注写明限定语应留在哪条事实里。开发集、测试集分组沿用 `evals/README.md`。**标注完先请用户抽查**（像之前一样，用户看几份确认思路一致），再往下做。

3. `e1_score.py` 增加：求职条件各项准确率、教育逐条准确率（值、就读状态和出处都对才算对；简历没写而输出了值算编造）；限定语保留率。原有指标照算。
4. **运行前**在 `evals/README.md` 写预测：各项准确率、编造数、原有召回率和职责准确率会不会下降。

6. **限定语要接到最终成品**：E1 只量抽取时有没有保留，保留了但改写写成「已上线」照样会出事。加一条从原文到成品的用例：原文「仅在预发布环境验证」→ 抽取保留在事实里 → 用假模型让改写写成「已上线」→ 依据检查必须拦下（修订或回退），成品里没有「已上线」。再用真实模型在一份合成简历上走一遍，记录这条最后的结论。
7. 匹配：用假模型写单元测试——满足、低于、没写三种；模型答 `missing` 但程序比对满足，以程序为准；「本科及以上，硕士优先」对本科用户判硬性满足、优先未满足；硬性与优先并存；JD 基本字段和逐条要求冲突时为待核对；引用求职条件不改判表达缺口；两个入口对同一版本结论一致。再用真实模型在 2～3 份合成简历和合成 JD 上跑一遍，记录这几条的结论。
8. 真实模型调用会产生少量费用：E1 开发集每份跑 3 次即可；同一组输入不要重复跑。

## 怎么实测

`.claude/launch.json` 的 `api`（8000）和 `web`（5174）。本机 8000 端口可能还有更早启动、没有 `--reload` 的进程，先确认端口上跑的是最新代码。开发库先 `uv run alembic upgrade head`。用 `evals/datasets/resumes/` 的合成简历（页头写了到岗信息的那几份）和自己写的合成 JD；测试账号密码只放在被 Git 忽略的 `.cache/`。

验收：

- 同一份简历写「每周可到岗 5 天」，JD 要 4 天 → 已覆盖；改成 3 天并发布 → 部分覆盖、写明低于要求；明确删除这一项并发布 → 未覆盖、建议去求职条件里补。三种情况都不会出现「表达缺口」。
- 只改一条事实并发布，求职条件原样继承；只改求职条件并发布，事实原样继承。
- 两份简历有相同的到岗片段，各自上传后，出处指向正确的文档。
- 两段教育（本科已取得、硕士在读）分别显示、分别确认；JD「硕士在读可投」判已覆盖。
- 「匹配」和直接「生成简历」两个入口，对同一版本的到岗结论一致。
