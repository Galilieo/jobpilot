# 任务 C：求职条件进匹配、抽取保留限定语（「投递前必修」）

日期：2026-11-25。基准：`main` 最新提交。前置：任务 A、B 的提交已在 main（本任务与 B 的账号导出有一处衔接，见第 6 项）。

## 背景

浏览器实测时，合成简历页头写了到岗信息，JD 要求「每周至少到岗 4 天」，匹配报告却判为「未覆盖」。原因有三处，都在设计上：

1. **抽取主动略过**：`jobpilot/prompts/extract_facts.txt` 规则 6 明确不拆「到岗时间」和学历标题行（学校、专业、学位）。
2. **没有合适的存放位置**：事实（`fact`）必须有所属经历、类型和职责。匹配提示词的示例只好把「每周可到岗 3 天」写成「求职意向」经历下的 role，不像事实。
3. **会被误判成表达缺口**：`jobpilot/services/matching.py` 约 212 行，引用的事实全部来自用户补充时改判为「表达缺口」。对项目经历这是提醒「把做过的事写进简历」；对到岗承诺，用户本人就是信息来源，这个判断会误导。

另外，评审指出抽取提示词自相矛盾：规则 2 说范围说明留在事实里，规则 6 又把「目前只覆盖查询接口」列为要跳过的例子。限定语丢了，后面的依据检查就看不到「成果只适用于什么范围」。

## 已定的设计（用户 2026-11-25 确认）

**新建一张结构化的「求职条件」表，沿用事实库的草稿和发布流程。** 不塞进 `fact`，也不做一份和事实库无关的独立档案：

- 用户在「我的 · 经历」里看到一张「求职条件」卡片，和事实一样：抽取出来先进草稿 → 用户确认或修改 → 随事实库一起发布成新版本。
- 跟着事实库版本走，旧匹配报告仍能说明当时依据的是哪个版本的条件（追溯）。
- 匹配时作为单独一块交给模型；引用求职条件的结论**永远不改判为表达缺口**。
- 改写不使用求职条件；完整简历的页头照旧原样出自底稿。

对照：JSON Resume / Reactive Resume 把教育单独结构化（学校、专业、学位、时间），LinkedIn 的「Open to work」把到岗时间等求职偏好和经历分开存；我们在这之上保留「有原文出处、用户确认、有版本」，这是本项目的核心。

## 要做的

### 1. 表与数据结构（一个提交：模型 + 迁移 + 约束测试）

- 新表 `fact_set_criteria`：每个事实库版本至多一行，`(fact_set_id, user_id)` 组合外键到 `fact_set`，级联删除。
- 字段（都可空，没写就是空）：
  - `onsite_days_per_week`：整数 1～7；
  - `internship_months`：整数，可连续实习的月数；
  - `earliest_start`：文字，照原文（如「可立即到岗」「2026 年 1 月」）；
  - `school`、`major`：文字；`degree`：`associate`、`bachelor`、`master`、`phd` 之一；`graduation`：文字，照原文（如「2027 届」「2027.06」）。
- 每个字段的出处另存一份 `sources_json`：`{字段名: {"source": "resume"|"user", "quote": ..., "span_start": ..., "span_end": ...}}`。来自简历的要有能在原文定位到的片段（复用 `locate_quote`），找不到就标为需要核对，和事实的 `quote_not_found` 一样不能直接确认。
- 草稿：`fact_draft` 加 `criteria_json`（结构同上，加每个字段的确认状态）。草稿的每次修改照样让 `revision` 加 1。
- 数值写成 CHECK 约束（天数 1～7、月数 1～24、学历四选一），代码里的常量和约束用同一组数。
- 迁移按 `db/base.py` 命名约定；在含已有事实和草稿的测试库上验证升级、回退、再升级，`alembic check` 无差异，`fact` 的只追加触发器仍生效。

### 2. 抽取（改 `extract_facts.txt`，版本号加 1）

- 同一次调用多输出一个 `criteria` 对象：上面七个字段，每个给值和逐字复制的原文片段；简历没写的留空，不推测（「本科在读」不能推出毕业时间）。
- 学历标题行（学校、专业、学位、时间）进入 `criteria`，仍然不拆成事实。
- **限定语**：删掉规则 6 里「目前只覆盖查询接口」这类例子；改为：会改变成果真假或范围的限定语（「只覆盖查询接口」「仅在预发布环境验证」「由导师负责上线」）附在它限定的那条事实里，不单独成条。背景原因（「有一批文件因为超时被重复上传」）仍然不拆。
- `services/facts.py` 解析并定位 `criteria`；`api/resumes.py` 上传后把它合并进草稿：草稿里已有用户确认过的字段不覆盖，只填空字段或更新未确认的字段。

### 3. 接口

- `GET /api/facts`：已发布版本和草稿里都带求职条件。
- `PUT /api/facts/criteria`：修改草稿里的求职条件（改动的字段出处变为 `user`），带 `expected_revision`，过期 409，和事实确认一样。
- `POST /api/facts/commit`：把草稿里已确认的求职条件复制进新版本。没有任何事实改动、只改了求职条件，也能发布新版本。
- 隔离测试登记新接口；跨用户 404；待删除账号被拒绝（任务 B 的规则）。

### 4. 匹配（改 `match_job.txt`，版本号加 1；改 `services/matching.py`）

- 求职条件作为单独的 `<untrusted_data label="criteria">` 区块交给模型，每个已确认字段一个 ID（如 `criteria.onsite_days_per_week`）。匹配结果里的引用可以是事实 ID，也可以是求职条件 ID；程序校验 ID 存在。
- 提示词示例改掉「求职意向」那条假事实。
- **程序兜底**：到岗天数、实习月数、学历这三类，如果 JD 解析出的 `basic_fields` 能读出数字或学历等级，而模型引用了对应条件，程序再比一次数字，和模型的结论对不上时以程序为准，并在 `reason` 里写明。读不出数字的交给模型。
- 引用了求职条件的结论**不改判为表达缺口**（`matching.py` 约 212 行的规则只看事实）。
- 结论的展示：满足 → 已覆盖；低于要求 → 部分覆盖，`reason` 写「低于岗位要求」；求职条件里没写 → 未覆盖，`suggestion` 写「在『求职条件』里补上」，不建议用户在简历里写。
- `match_report` 要能回读当时引用的求职条件（报告已经按 `fact_set_id` 追溯，求职条件跟着版本走即可）。

### 5. 前端（「我的 · 经历」和匹配报告）

- 「求职条件」卡片：七个字段，显示值、原文出处、确认状态；可以改、可以确认；需要核对的标黄。草稿的修订号沿用事实库那套（409 刷新提示）。
- 匹配报告里，引用求职条件的条目显示「依据：求职条件 · 每周到岗 5 天」。
- 前端测试补：求职条件 409 刷新；匹配报告渲染求职条件依据。

### 6. 衔接

- 任务 B 的「导出全部数据」把求职条件一起导出（加字段、加测试）。
- `02` 第 5 节、`数据库设计.md`（新表、新列、迁移记录）、`06`（「投递前必修」标为完成并记录结果）同步更新。

## 评测（按项目规则，不能省）

1. **先标注再运行**：在 E1 标注文件里给开发集样本补 `criteria` 的标准答案，并补「限定语」用例——至少 5 条原文里有限定语的事实，标注写明限定语应留在哪条事实里。开发集、测试集分组沿用 `evals/README.md`。**标注完先请用户抽查**（像之前一样，用户看几份确认思路一致），再往下做。
2. `e1_score.py` 增加两项：求职条件各字段的准确率（值和出处都对才算对；简历没写而输出了值算编造）；限定语保留率。原有指标照算。
3. **运行前**在 `evals/README.md` 写预测：各字段准确率、编造数、原有召回率和职责准确率会不会下降。
4. 先跑开发集；不达预期就调提示词再跑开发集；满意后测试集只跑一次，结果如实记录，不在测试集上调。
5. 匹配：用假模型写单元测试（满足、低于、没写三种结果；程序兜底改正模型的错误数字判断；引用求职条件不改判表达缺口），再用真实模型在 2～3 份合成简历和合成 JD 上跑一遍，记录报告里这几条的结论。
6. 真实模型调用会产生少量费用：E1 开发集每份跑 3 次即可；同一组输入不要重复跑。

## 怎么实测

`.claude/launch.json` 的 `api`（8000）和 `web`（5174）。开发库先 `uv run alembic upgrade head`。用 `evals/datasets/resumes/` 的合成简历（页头写了到岗信息的那几份）和自己写的合成 JD；测试账号密码只放在被 Git 忽略的 `.cache/`。

验收：同一份简历写「每周可到岗 5 天」，JD 要 4 天 → 已覆盖；改成 3 天并发布 → 部分覆盖、写明低于要求；删掉这一项 → 未覆盖、建议去求职条件里补。三种情况都不会出现「表达缺口」。
