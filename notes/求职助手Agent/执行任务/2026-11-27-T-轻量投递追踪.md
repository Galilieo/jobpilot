# 任务 T：轻量投递追踪（T3.5）

日期：2026-11-27。基准：`main` 最新提交（`45ebc8b` 之后）。状态：设计已定，三个建表前的决定和阶段记录表都由用户确认过，见末尾「设计变更记录」。

## 背景

第 4 周的完成标准是「在本地网页上通过对话独立完成一次完整流程，**并记录一次投递**」。前面几步已经能做：对话、匹配、生成简历、编辑、导出。现在差最后一步：投出去以后，系统不知道投了哪一版，也记不下后面的进度。

现在能用的只有 `user_job.stage`：岗位详情里有个下拉框，能手动选「已投递、面试中……」。它有三个问题：

- 不知道投的是哪份简历、哪个版本；
- 同一个岗位投两次，只能存一个阶段；
- 改阶段时直接覆盖，看不出之前走到了哪一步。

本任务分两个阶段：

- **阶段一**：后端，包括表、接口、对比和对话工具；
- **阶段二**：前端，包括岗位详情、看板和对话卡片。

每个阶段都有自己的验收和回退点。

## 成熟方案对照（2026-11-27 调研）

| | 投递和岗位的关系 | 阶段记在哪 | 投递用的简历 | 被拒怎么记 | 改阶段 |
| --- | --- | --- | --- | --- | --- |
| Huntr、Teal（求职者用） | 一个岗位一张卡，不单独支持投两次 | 岗位卡上：已收藏 → 已投递 → 面试中 → 谈薪 → 已接受 | 跟着岗位保存当时那份 | 一个阶段 | 拖动卡片 |
| Greenhouse（招聘方用） | 候选人和投递分开，每次投递一条记录 | 投递上，并保留**阶段历史**：每段有进入、离开时间，没离开的那段就是当前阶段 | 附件存在投递上 | — | 必须带上当前阶段，对不上就拒绝 |
| Lever（招聘方用） | 每次投递是独立的一条 | 投递上 | — | 「归档 + 原因」，不算阶段；撤销归档回到之前的阶段 | — |

本项目的取法：

- **投递单独一张表，阶段记在投递上**。和招聘系统一致，因为 06 已经定了同一岗位投两次要各有阶段。
- **投递自带快照**。和这几个产品一致：当时投的那份要原样留下。
- **阶段历史只追加不修改**。参考 Greenhouse：不记的话，「未通过」会盖掉之前的阶段，V2 的转化统计也没有数据可用，而且事后补不回来。
- **改阶段带修订号**，和 Greenhouse 带当前阶段是同一个目的，也沿用本项目记忆接口的写法。
- **逐条对比**：这几个产品都不做，只保存当时的版本。本项目在同一份简历内部做，跨两次改写只并排展示，不硬配对。

来源：[Huntr](https://huntr.co/product/job-tracker)、[Teal](https://help.tealhq.com/en/articles/14435727-how-to-track-your-job-applications)、[Greenhouse application stages](https://harvestdocs.greenhouse.io/reference/application-stages)、[Lever archive](https://help.lever.co/hc/en-us/articles/20087374094365)。

## 设计

### 1. 数据表

**`application` 投递**：每投一次一行。

| 字段 | 说明 |
| --- | --- |
| `application_id`, `user_id` | `user_id` 删号级联 |
| `user_job_id` | 可空。岗位删除时置空（`ON DELETE SET NULL (user_job_id)`，PostgreSQL 15 起支持只置空指定列，本项目是 18），投递记录保留 |
| `job_snapshot_json` | 记录时的岗位基本信息（合并个人修改后的岗位名、公司、地点、薪资、链接），岗位删掉后靠它显示。不存 JD 原文 |
| `resume_version_id` | 可空。简历或岗位删除时置空，同样只置空这一列 |
| `resume_id`, `resume_version` | 快照来自哪份简历的第几版，删除后仍可显示「来自第 3 版」，并用于判断有没有重新生成过 |
| `fact_set_id` | 生成这份简历时用的事实库版本（取自 `ai_run.fact_set_id`） |
| `snapshot_json` | 冻结的 `ResumeContent` |
| `snapshot_html` | 冻结的导出 HTML（不带编辑器） |
| `backfilled` | 迁移补录的旧数据为 true，这类记录没有快照，见第 5 节 |
| `applied_at` | 投递日期（`date`），默认今天 |
| `channel` | 渠道，自由文本，有长度上限 |
| `stage` | `applied` / `written_test` / `interviewing` / `offer` / `rejected` |
| `revision` | 修订号，改阶段、改渠道或日期时 +1 |
| `action_id` | 可空、唯一。从对话确认卡创建时填，用来去重 |
| `created_at`, `updated_at` | |

约束：

- `CHECK (backfilled OR (snapshot_json IS NOT NULL AND snapshot_html IS NOT NULL AND fact_set_id IS NOT NULL))`：非补录的记录必须有完整快照；
- 组合外键 `(user_job_id, user_id)`、`(resume_version_id, user_id)`、`(fact_set_id, user_id)` 保证引用同一用户的数据（决定 7、29）。`resume_version` 上如果还没有 `(resume_version_id, user_id)` 唯一键，就在同一迁移里加上；
- 快照字段建好以后不再修改。接口不提供修改入口，服务层也不写；是否加数据库触发器，参考 `fact` 的做法自行判断，并在回报里说明。

**`application_stage_event` 阶段记录**：只追加。

| 字段 | 说明 |
| --- | --- |
| `event_id`, `user_id`, `application_id` | `application_id` 级联删除 |
| `from_stage` | 可空；新建投递时为空 |
| `to_stage` | |
| `occurred_at` | 阶段发生的日期，默认今天；用户可以补填过去的日期 |
| `created_at` | |

- 新建投递时写一条（空 → `applied`）；每次阶段真正变化写一条；阶段没变不写。
- 投递的 `stage` 列等于它最后一条记录的 `to_stage`，在同一事务里写，测试要验证两者一致。不另存「当前阶段」以外的任何派生字段。
- 用户选错了阶段，就再改一次，追加一条新记录，不删旧记录。

阶段值写成一个枚举，数据库 CHECK 和代码共用同一组值（照 `JobStage` 的写法），不在两处各写一遍。

### 2. 岗位的阶段从投递推出来

`user_job.stage` 删掉，换成 `archived_at`（可空时间）。岗位上显示的阶段由程序推出来，不再存：

1. `archived_at` 不为空 → 已归档；
2. 否则有投递 → **最近一次投递**的阶段；
3. 否则 → 已收藏。

「最近一次」按 `applied_at` 倒序，再按 `created_at` 倒序。这样补记一条更早的投递，不会盖掉后面那次。

- 写一个推导函数，岗位列表、岗位详情、工作台看板、`overview` 统计都调用它，不各写一套。一次查询取出所有岗位的最近一次投递，不要每个岗位查一次。
- `JobStage` 改为纯展示用的枚举：`saved`、`applied`、`written_test`、`interviewing`、`offer`、`rejected`、`archived`。
- `PUT /api/jobs/{job_id}` 去掉 `stage`，改为 `archived: bool`。改阶段只能通过投递接口。
- 看板「已投递」列收录阶段为 `applied`、`written_test`、`interviewing`、`offer`、`rejected` 的岗位，同时显示具体阶段。

### 3. 记录投递

`POST /api/applications`（带幂等键，沿用现有的幂等写法）：

```json
{ "job_id": "...", "resume_version_id": "...", "applied_at": "2026-11-27", "channel": "官网" }
```

- `resume_version_id` 必须属于这个岗位的定制简历（版本 → 简历 → `ai_run.user_job_id` 等于 `job_id`），否则返回 422。别人的岗位或版本一律返回 404，不区分不存在和没权限。
- 在一个事务里冻结：`snapshot_json` = 该版本的 `content_json`；`fact_set_id` = 该简历运行的 `fact_set_id`；`snapshot_html` = 用 `render_html` 按导出模式渲染；`job_snapshot_json` = 合并个人修改后的基本信息。再写第一条阶段记录。
- 选中的必须是这个版本本身，不是「这份简历的当前版本」。等待确认期间有了新版本，也用选中的那版（F9「出卡时绑定版本」）。
- 同一岗位可以有多条投递，不限制。

### 4. 更新、删除和查看

| 接口 | 说明 |
| --- | --- |
| `GET /api/applications?job_id=` | 某岗位的投递列表，新的在前；不传 `job_id` 时列出全部 |
| `GET /api/applications/{id}` | 详情，包括阶段记录时间线；不返回 `snapshot_html` |
| `GET /api/applications/{id}/snapshot.html` | 快照 HTML，供 iframe 预览和打印成 PDF，安全头和 CSP 沿用现有预览页 |
| `PUT /api/applications/{id}` | `{expected_revision, stage?, occurred_at?, channel?, applied_at?}`，`extra="forbid"`，修订号不对返回 409。快照字段不在请求里 |
| `DELETE /api/applications/{id}` | `{expected_revision}`，连同阶段记录一起删（02 第 5.3 节：投递记录直接删除，前端二次确认） |

### 5. 旧数据迁移

迁移时，`user_job.stage` 为 `applied`、`interviewing`、`offer`、`rejected` 的岗位，各补一条投递：

- `backfilled = true`，没有快照和简历版本；
- `applied_at` 取 `user_job.updated_at` 的日期；
- 阶段照搬（`interviewing` 映射到 `interviewing`，依此类推）；写一条阶段记录（空 → 该阶段）；
- `stage = 'archived'` 的岗位只设 `archived_at`，不补投递；`saved` 什么都不做。

降级时用最近一次投递的阶段写回 `user_job.stage`，`written_test` 写回 `applied`。降级会丢失多次投递和快照，在迁移文件的注释里写明。

页面上，补录的记录显示「迁移前记录的进度，没有当时的简历」，不显示快照和对比入口。

### 6. 投递以后的对比

`GET /api/applications/{id}/diff`，全部由程序计算，不调模型。

**简历差异**分三种情况：

| 情况 | 怎么判断 | 返回 |
| --- | --- | --- |
| 同一份简历 | `resume_version_id` 还在，取这份简历的当前版本 | 按 `bullet_id` 对齐，列出修改、新增、删除，修改的给出前后文字 |
| 之后重新生成过 | 这个岗位有比快照里的 `resume_id` 更新的定制简历 | 不逐条对齐，返回 `regenerated: true` 和新简历的 ID，前端并排显示 |
| 原简历已删除 | `resume_version_id` 为空 | `source_deleted: true`，只能看快照 |

前两种可以同时出现：旧简历还在、又生成了新的，就两样都返回。

**事实库差异**：快照的 `fact_set_id` 和用户最新的事实库版本比，按 `lineage_id` 对齐，列出新增、修改（前后文字）、删除的事实。先找有没有现成的事实版本比较函数，没有再写纯函数。

**风险提醒**：标出快照里的条目，满足任一条：

1. 它引用的事实在之后的版本里被修改或删除了（例如「30%」改成了「20%」）；
2. 同一份简历的当前版本里，这一条改成了事实原文，或者被删掉了。

每条提醒写清是哪条条目、哪个原因、对应的事实前后文字。提示语的意思是「面试时按当时的写法准备，但不要再往上夸大」（F9）。

### 7. 对话工具 `record_application`

- 写入类，需要确认，照 `remember` 的出卡、确认、撤销流程写。
- 参数：`job_id`（默认当前岗位）、`resume_version_id`（默认当前岗位最新定制简历的当前版本）、`applied_at`（默认今天）、`channel`（可空）。参数里的 ID 都要在服务端校验，不信模型给的。
- **出卡时**就把 `resume_version_id` 解析成具体版本存进卡片；确认时用卡片上的版本，和第 3 节走同一个服务函数，不另写一套冻结逻辑。同一 `action_id` 再次确认，返回原投递记录。
- 卡片显示：岗位名、公司、「第 N 版简历」、日期、渠道。
- **撤销**：只在这条投递的修订号还是创建时的值（之后没改过阶段、日期、渠道）时允许，撤销即删除这条投递；改过就返回 409，提示到岗位详情里处理。
- `agent.txt` 升一个版本，写明：用户说已经投了、投出去了这类话时，提议 `record_application`；没有定制简历时先说明，不出卡。同步 `versions.lock.json`。
- 改阶段不做成对话工具，V1 只在岗位详情里改（见「不做的」）。

## 验收

先写会失败的测试，再写实现；关键判断做变异检查。

### 阶段一：后端

1. **06 的版本场景**：事实库 v3（写着 30%）生成简历 v1 并记录投递；之后发布含 20% 的 v4，并修改岗位要求。
   - 新的改写用 20% 和新要求；旧的报告和改写仍指向旧要求、v3 事实和对应原文；
   - 投递的 `resume_version_id`、`snapshot_json` 和 `snapshot_html` 仍是 v1 的 30%；之后改阶段，快照不变；
   - 对比接口在风险提醒里标出这条 30%，原因是引用的事实被修改。
2. **出卡绑定版本**：为 v1 出卡，在另一处保存出 v2，再确认：投递详情和快照都是 v1。同一 `action_id` 再次确认，返回原投递记录，不新增。
3. **两次投递**：同一岗位第一次投递改成「未通过」，第二次投递进入「面试」。岗位显示「面试」，第一次投递仍是「未通过」，阶段记录完整。再补记一条 `applied_at` 更早的投递，岗位仍显示「面试」。
4. **删除岗位**：删掉岗位后，投递记录还在，`user_job_id`、`resume_version_id` 为空，`job_snapshot_json` 和快照能正常显示；对比返回 `source_deleted`。
5. **重新生成**：投递后为同一岗位重新改写，对比返回 `regenerated` 和新简历 ID，不做逐条对齐。
6. **阶段记录**：每次改阶段追加一条；阶段不变不追加；`stage` 列始终等于最后一条记录的 `to_stage`；修订号过期返回 409。
7. **迁移**：在测试库上验证升级、降级、再升级。准备 `saved`、`applied`、`interviewing`、`rejected`、`archived` 各一个岗位，验证补录结果和第 5 节一致，`alembic check` 无差异。
8. **对话撤销**：确认后马上撤销，投递删除；改过阶段后撤销，返回 409。
9. **离线编辑**：离线编辑导出的 HTML 后，系统展示的仍是服务端所选的版本。
10. **配套**：第 8 节的删号、导出和隔离测试。
11. 全量 `uv run pytest -q`、`ruff check`、`ruff format --check .` 通过。

### 阶段二：前端

1. 单测覆盖：记录投递弹窗的默认值、改阶段并追加时间线、409 重读、删除二次确认、补录记录不显示快照入口、对比抽屉的三种情况、确认卡渲染和撤销。
2. 浏览器实测（合成账号，可用假上游，不花模型费用）：在岗位详情记录投递 → 改成笔试 → 再改成面试 → 查看当时的简历并打印 → 修改简历后看对比；在对话里说「我投了」→ 确认卡 → 撤销。1440×900 和 375×844 各截一组，无水平溢出。
3. `pnpm --dir web format:check`、`lint`、`test`、`build` 通过。
