# 任务 Q：长期记忆与上下文压缩（T3.4）

日期：2026-11-26。基准：`main` 最新提交。状态：设计已定。第三轮独立评审（只评本草案）提了 14 条，用户也做了决定，见末尾「设计变更记录」。

## 背景

对话 Agent 的后端已由任务 N、O 完成。现在的上下文只做截断：

- 只放最近 10 轮，估算约 8,000 token，更早的直接丢掉；
- 旧的工具结果只留简短结果；
- `conversation.summary` 这一列已经建了，但还没用上。

一段围绕岗位的对话很容易超过 10 轮，截断之后，前面说过的要求就忘了。长期记忆（F8）也还没做，每次新开对话都要从头讲偏好。

这两件事都要改组装上下文的同一个文件（`services/agent/context.py`），所以放在同一个任务里，**分两个阶段做**：

- **阶段一**：记忆；
- **阶段二**：压缩。

每个阶段都有自己的验收和回退点。

## 成熟方案对照（2026-11-26 调研）

### 上下文压缩

| | 触发 | 原样保留 | 摘要结构 | 再次压缩 |
| --- | --- | --- | --- | --- |
| pi | 剩余少于 16K；超出上限时压缩后重试一次；也可手动 `/compact [重点]`；不同模型可以分别配置 | 系统提示词；最近约 20K，在消息边界切开；切点和摘要一起保存 | Goal / Constraints & Preferences / Progress / Key Decisions / Next Steps / Critical Context | 把上一份摘要合并进来；完整历史留在磁盘上 |
| OpenCode | 剩余少于窗口的 15%；超出上限时按比例缩小重试 | 系统提示词；最近约 15K，按完整的一问一答保留 | Objective / Requirements / Decisions / Work State / Next Move / Important Context | 在旧摘要上更新，有冲突时以新的为准 |
| Hermes | （没读到具体数字） | 系统提示词；末尾按 token 保留；用户的原话单独留约 6K | 不确定的内容单列一段；附「怎样找回」的指引 | 保留上一份摘要；旧的工具输出先换成占位符 |
| Anthropic | 达到设定的门槛，或者手动 | 压缩块之后的消息 | 可以自定义；先保证不漏，再删多余的 | 新摘要 = 旧摘要 + 之后的消息 |

- Hermes 的压缩评测问的是被压掉那段里的问题。摘要带「去哪里找回」指引的，比不带的高 30 多分。
- Anthropic 认为清理旧的工具结果是最安全的一步。
- Chat Completions 这类接口是无状态的：每次调用都要重发全部历史；超出上限返回 400，不会自动截断。只有少数服务商提供服务端压缩。**本项目不依赖任何服务商的专属能力**，见设计第 1 节。

### 长期记忆

- ChatGPT：可以查看、删除已保存的记忆，也可以直接说「忘掉」。
- Claude：按主题列出，可以编辑。
- Letta：记忆分成块，每块有字数上限。
- Mem0：让模型自行决定新增、修改、删除。有人报告它会误删仍然有效的偏好，新版也去掉了这一步。

本项目的取法：用固定栏目的档案，写入需要用户确认，不让模型自行删除。

## 设计

### 1. 通用：窗口、token 计量和超长错误

**模型档案**：在配置里按模型名登记 `context_window` 和 `max_output_tokens`。没有登记的模型启动时报错，不猜默认值。换模型只改配置，不改代码。

**有效窗口**取三者中最小的一个：

1. 模型自己的窗口；
2. 模型窗口 × `context_window_ratio`；
3. `context_window_cap_tokens`。

| 场景 | 配置 | 效果 |
| --- | --- | --- |
| 开发和测试 | ratio 0.5，cap 32,000 | 32K，容易触发压缩，便于测试 |
| 上线（用户决定） | ratio 0.5，不设 cap | 1M 的模型得到 512K |

**token 计量**：

- 用上一次调用服务商返回的实际输入 token（`model_call.prompt_tokens`），加上之后新增内容的估算（pi 的做法）。
- 新增内容沿用网关的 UTF-8 字节上界估算。这个估算偏高，偏向安全。
- 一段对话还没有实际用量时，整个请求都按估算。

**超长错误**：网关把各服务商的「上下文超长」错误统一成 `ContextOverflowError`。

- DeepSeek 的判断写在网关的适配函数里，其他代码只认这个统一错误。
- 普通的 400 不算超长。

**预算一致性**：启动时检查「每轮 token 预算 ≥ 4 × 有效窗口」，不满足就拒绝启动。比如上线放到 512K 时，要同时调大每轮预算，否则一次满窗口的调用就会用光一轮的额度。

> 留尾（不在本任务）：每轮预算改成按实际费用计算。命中缓存的输入价格约为不命中的 2%，窗口放大以后，按 token 数限额会过于保守。

### 2. 每次调用模型时的上下文

顺序按评审 [13] 调整：越固定的越靠前，有利于前缀缓存命中，但不为缓存做专门设计。

| 顺序 | 内容 | 谁来写 | 是否压缩 |
| --- | --- | --- | --- |
| 1 | 系统提示词与工具清单 | 固定 | 不压缩 |
| 2 | 长期记忆，按固定的栏目顺序渲染 | 用户确认过的 | 不压缩；栏目和长度都有上限 |
| 3 | 工作摘要 | 模型写，滚动更新 | **主要压缩的部分** |
| 4 | 任务状态 | 程序从数据库生成 | 不压缩，状态变化时重新生成 |
| 5 | 最近几轮的原文 | — | 按完整的轮切开，至少保留当前这一轮 |
| 6 | 本次输入 | 用户 | 附件按不可信数据处理 |

**任务状态**（评审 [08]）：

- 包含这些字段：
  - 当前岗位 ID 和绑定修订号；
  - 事实库版本；
  - 适用于这个岗位的最新报告 ID，以及它基于的岗位版本和事实版本；版本不一致时标「基于旧版本」，没有报告时写「未匹配」；
  - 当前简历的运行 ID 和版本号；
  - 有效卡的 ID 和状态。
- 报告详情、卡片参数、JD 全文和简历正文都交给读取工具去取，不放进任务状态。
- 来自 JD 的字符串（岗位名、公司）有长度上限，并按数据渲染。
- 不放时间戳这类和业务无关、每次都会变的内容。
- 刷新时机：
  - 切换岗位、写入、生成、暂停后恢复之后，重新生成变化的部分；
  - 图在确认卡之后不会再经过 `build_context`，所以要在 `apply_action` 和生成类工具之后刷新，不能沿用一轮开始时的状态。
- 复用现有的 `current_job_summary` 等查询，不另写一套。

### 3. 工作摘要

**栏目**：结构化 JSON，用 Pydantic 校验，渲染成小标题加列表。每栏的条数和字数有上限，写成命名常量。

| 栏目 | 内容 |
| --- | --- |
| `goal` | 这段对话要做成什么 |
| `requirements` | 用户提过的要求。否定、硬性要求、例外、改口这几类，每条都要带**短原话、来源消息序号、适用岗位**；新要求取代旧要求时，记下取代了哪一条（评审 [06]） |
| `done_and_decided` | 已完成的事和已定下的事 |
| `open_items` | 还没做完的事 |
| `answered_questions` | 提问卡上的问题和对应的答案，保持一一对应 |
| `unverified` | 不确定的内容。不确定的说法只能放在这里 |

**原话校验**：摘要写入前，程序逐条核对引用的原话：它确实是对应序号那条消息里的一段，那条消息属于本对话，角色是用户。核对不上的条目移到 `unverified`。栏目放不下时，保留「消息 x～y 里还有相关内容」这种范围提示，不悄悄丢掉。

**滚动更新**：每次压缩的输入是「上一份摘要 + 这次移出的完整轮次」。移出轮次的序列化方式：

- 用户正文和提问卡的答案完整保留；
- 工具结果每条最多 2,000 字符；
- 附件只留来源说明和前 500 字符。

**防注入**：

- 摘要放在不可信数据区；
- 摘要不作为改写、依据检查或任何写入卡的输入；
- 摘要里的内容不能拼成当前这一轮的 `user` 指令（评审 [02]）。

**找回工具** `read_conversation_history`（只读，评审 [09]）：

- 服务端绑定当前登录用户和当前对话，消息序号只是筛选条件。
- 按「序号范围」或「关键词」查询。返回的每段都标明来源（用户正文、附件片段、提问卡答案、助手回复、工具步骤摘要）以及有没有被截断。
- 按条数和字节双重上限分页，返回下一页的位置。
- 原业务对象有 ID 的，告诉模型用相应的读取工具去取详情。
- 读回来的内容照样按不可信数据包装。

摘要末尾固定加一行找回指引。

### 4. 压缩：边界、时机和运行

**同一道边界**（评审 [01]）：

- `conversation` 新增这几列：
  - `summary_json`，JSONB；
  - `summary_through_seq`，摘要覆盖到的最后一条消息的序号；
  - `summary_revision`。

  删掉旧的 `summary` 文本列。
- **写入**：调用模型前，先固定三样东西：旧修订号、旧覆盖点、本次截止序号。截止序号只能落在**已经结束的完整轮次**上。模型返回后，在一次条件更新里写入摘要、截止序号和修订号加一，条件是修订号仍为旧值。压缩期间有新消息追加，不影响这次的结果。
- **读取**：在同一个读快照里取摘要和覆盖点之后的消息，本轮输入只出现一次。
- **计量**：从覆盖点之后的全部历史算起，不能用「最近 10 轮」裁剪后的结果来判断。删掉 `history_turns` 这个配置，由 token 水位决定保留多少。

**水位**（用户决定，评审 [07]）：

| 量 | 初值 |
| --- | --- |
| 自动压缩的触发点 | 下一次请求的预计大小（固定部分 + 摘要 + 任务状态 + 保留的原文 + 输出预留）超过有效窗口的 **80%** |
| 压缩后的目标 | 摘要不超过窗口的 10%，原文不超过 40%，整个请求约 50%。留出余量，压一次能撑好几轮 |
| 只在能移出至少一个完整轮次时才压缩 | 否则不调用模型 |

三个比例都写成配置，由 E11 来调。

**入口**：同一个压缩函数，只有入口不同。

| 入口 | 什么时候 | 怎样运行 |
| --- | --- | --- |
| 自动 | 一轮结束后达到触发点 | 在后台跑，用户不用等 |
| 手动 | 用户点「压缩上下文」，可以附一句重点 | `POST /api/conversations/{id}/compact`。重点说明只能调整「多保留什么」，不能挤掉仍然有效的硬性要求。对话有运行在跑时返回 409；没有可移出的轮次时返回 200 和「无需压缩」 |
| 本次请求超出窗口 | 某次主调用的完整请求超过「有效窗口 − 输出预留」 | 只对这一次请求丢掉最早的、还没被摘要覆盖的原文，**不推进覆盖点**，并告诉模型「消息 x～y 未包含，可以用 read_conversation_history 查」。当前这一轮自己就超过时，按明确的错误结束，提示用户拆分输入 |
| 服务商返回超长 | 收到 `ContextOverflowError`，请求还能缩小，剩余预算也够 | 按上一条缩小后重试一次。不原样重发 |

**压缩运行**（评审 [05]）：

- 新增 `ai_run.kind = 'compact'`，需要迁移 `ck_ai_run_kind`。另加一个条件唯一索引：每段对话同时最多一个活跃的 `compact` 运行。手动重复请求时，返回已有的那个运行。普通的 `agent` 运行不受影响，用户照常可以发消息。
- 创建压缩运行时，核对账号有效、对话存在。收尾在同一个事务里完成：先检查运行仍然活跃、归属和覆盖边界都没变，再写入摘要和终态。如果删除或删号先完成，就放弃这次结果，已经发出去的调用照实记账。
- 压缩有自己的调用次数和输入上限。网关目前的预算检查只接受 `kind = 'agent'` 的父运行，要扩展，或者给压缩单独设一份预算。
- 压缩失败（调用失败、校验不通过、超长）时，保留旧摘要，记日志，不影响对话，下一轮结束后再试。

### 5. 长期记忆

**栏目**：放在 `jobpilot/data/memory_keys.yaml`。

| 类别 | 栏目 | 取值 |
| --- | --- | --- |
| 求职偏好 | `target_direction` 目标方向 | 文字，≤ 100 字 |
| 求职偏好 | `cities` 城市 | 列表，≤ 5 个，每个 ≤ 20 字，去重，保留用户给的顺序 |
| 求职偏好 | `excluded_types` 不考虑的岗位或公司类型 | 列表，≤ 5 个，每个 ≤ 30 字 |
| 求职偏好 | `job_notes` 其他 | 文字，≤ 300 字 |
| 写作偏好 | `tone` 语气 | 枚举：平实 / 简洁有力 |
| 写作偏好 | `bullet_length` 每条长度 | 枚举：尽量一行 / 不超过两行 / 不限。这是偏好，不保证排版后的行数 |
| 写作偏好 | `tech_terms` 技术名写法 | 枚举：英文原名 / 中文 / 中英并列 |

每周到岗天数、实习时长、最早到岗已经在事实库的「求职条件」里，不再重复记。

**表**：`memory` 的主键是 `(user_id, key)`，字段有 `value_json`、`revision`、`deleted_at`、`source`（对话的 `conversation_id` 和 `message_id`，或者「手动」）、`updated_at`。

- 撤销需要用到的上一个值，存在对应的 `agent_action.result_json` 里，不放进 memory 表，也不会出现在读取接口和模型上下文里。
- 键和取值的上限，数据库约束和代码用同一组常量。

**版本规则**（评审 [04]）：

- 从来没创建过的栏目，预期版本是 0。
- 第一次写入靠主键竞争决定谁先写成，后写的那个返回 409。
- 已有的行，按 `(user_id, key, expected_revision)` 做一次条件写入。
- 新增、修改、删除、恢复、撤销，都会让修订号加一。
- 撤销时恢复的是上一个值和删除状态，修订号照样往前走，不会回到旧号。所以更早的失效卡也不会因此重新生效。
- 确认接口可以提前报冲突，但真正执行写入的事务里还要再检查一次。

**写入工具必须引用本轮原话**（评审 [02]、[03]，用户同意的做法）：

- `remember(key, value, quote)`，写入类，需要确认。
  - `quote` 必须是**本轮用户消息正文**里的一段，不能来自附件、摘要或历史。服务端照 `parse_jd` 核对来源的方式校验，校验不通过就不出卡。
  - 卡片显示「来源：你刚才说的『……』」，以及修改后的完整值。列表类的栏目要标明是「增加」还是「替换」，比如「上海也可以」应该是增加。
- `forget(key, quote)`，规则相同。
- 这个机制的效果：
  - 删掉以后，旧对话和摘要里的值不能再变成建议卡，因为它们不是本轮的原话；
  - 用户这一轮明确再说一次，就可以重新记下；
  - JD 和历史里藏的指令触发不了写入。
  - 用户在管理页手动恢复，也算数。
- 两个工具都可以撤销，规则同上。

**接口**：

- `GET /api/memories`，返回每栏的值和修订号，已删除的栏也返回修订号，供重建时使用；
- `PUT /api/memories/{key}`，带 `expected_revision`；
- `DELETE /api/memories/{key}`，也带 `expected_revision`。

账号导出要包含记忆，删除账号时级联删除。

**用在哪里**：

- 对话时，全部记忆放进第 2 块。
- 改写时，只用写作偏好的三个枚举值，由程序翻译成固定的措辞要求句。
- `job_notes` 等自由文字不进入改写。

### 6. 改写入口与评测兼容

**写作偏好在改写运行创建时固定下来**（评审 [10]）：由服务端读取本人已经确认的三个枚举，记进运行的计划。对话里的 `tailor_resume` 和岗位页发起的改写共用这一套；恢复运行时用当初记下的那份。

**用户没设任何写作偏好时，E3 和 E5 实际发出去的消息必须逐字节不变**，包括不能多出空字段、空标题或换行。验证方法：

- 用同一组合成输入和假网关，抓取修改前后实际发出的消息并比对；
- 覆盖 E3 的匹配，以及 E5 各阶段：匹配、初写、修订、依据检查；
- 基线组和产品路径分开验证。

设了偏好时，只允许指定的写作请求里多出那几句固定措辞。这只能证明输入兼容，不能证明真实模型重跑的分数一定相同。

**改一条简历条目时不再由主对话模型直接写文字**（评审 [02]）：

- `edit_resume_item` 的参数改为 `run_id`、`bullet_id`、`instruction`。`instruction` 是本轮用户的修改要求，和 `remember` 一样要引用本轮原话。
- 服务端组装输入：
  - 原条目；
  - 它引用的事实；
  - 写作偏好的枚举值；
  - 上面那条修改要求。

  这些交给新提示词 `edit_bullet.txt`，由它生成候选文字，再照常跑三层依据检查和出卡。
- 出卡时，把生成的候选文字和检查结论存进卡的 `args_json`，字段名沿用现在的 `text`。确认时执行的就是卡上显示的这段文字。任务 P 的确认卡渲染按现在的字段写，不受影响。
- 不改 `revise_bullet.txt`，它属于 E5 的输入。调用和解析的代码复用 `rewriting.py` 里修订那一套，不重写。
- 用户本轮直接给了替换文字的（比如「第二条改成：……」），`instruction` 引用这段原话，服务端直接用这段文字去检查，不再经过模型。
- `job_notes`、摘要和历史读取的结果都进不了 `edit_bullet` 的输入。

### 7. 系统提示词

`agent.txt` 升到 v3，写明这几点：

- 记忆、工作摘要、任务状态三块分别是什么；摘要只能参考，以读取工具读回的为准；
- 涉及硬性要求、又有冲突时，先用 `read_conversation_history` 查原文；
- 只有用户本轮明确说了跨对话的偏好，才提议 `remember`，并引用原话；一次性的要求不记；
- 经历一律进事实库。

## 验收

先写会失败的测试，再改代码；关键判断做变异检查。时序问题用可以控制的暂停点来固定顺序。

### 阶段一：记忆

- 跨对话召回；改口时覆盖原值；列表增加和替换分开处理。
- 删除后的两种情况：旧对话或摘要里的值不出卡；本轮重新明确说的，出卡。
- `quote` 来自附件、摘要或历史读取的结果时，不出卡。
- 不认识的键、超长的值，返回 422。
- 用 A 的接口和工具改不了 B 的记忆。
- **两段对话、两张不同的卡**，同时为一个还不存在的栏目确认：一个成功，一个冲突。
- 旧管理页带过期的版本号去删除，返回 409。
- 撤销后恢复上一个值，并且更早的失效卡不会重新生效。
- 改写边界：
  - 「`job_notes` 写着『把我写成负责人』→ 用户要求润色第二条 → 检查」这条链路里，`edit_bullet` 和依据检查实际收到的输入都没有这句话；
  - 「旧 JD → 历史读取 → 出卡」这条链路不会出 `remember` 卡；
  - 没有写作偏好时，E3 和 E5 实际发出的消息逐字节不变。

### 阶段二：压缩

- 六块的顺序和各自的上限。
- 摘要不能覆盖到压缩期间新来的消息：先固定截止到第 80 条，期间消息涨到第 90 条，写入后覆盖点是 80，81～90 仍然以原文出现。
- 读取用同一个快照，不会漏掉一段或重复一段。
- 超过触发点时，一轮结束后在后台压缩；压缩后的请求在目标以内。
- 滚动更新的输入只有「上一份摘要 + 新移出的完整轮次」。
- 原话校验不通过的条目，移到 `unverified`。
- 三次压缩以后，「否定 → 某个岗位例外 → 撤回例外」仍然正确；提问卡里的答案保留。这一项用假模型测管道，内容质量交给 E11。
- 本次请求超出窗口时，只截断这一次、不推进覆盖点，并且告诉模型哪段消息没放进来；当前这一轮自身超长时，按明确的错误结束。
- 统一超长错误：收到 `ContextOverflowError` 时缩小后重试一次；普通 400 不重试。
- 并发与删除：分别在「读完历史」「请求已登记」「返回了但还没写入」三个位置暂停，插入新消息、第二次压缩、删除对话、删号，检查覆盖范围、终态和实际发出的请求数。
- 手动压缩：重复请求返回同一个运行；带重点时，重点会传进压缩提示词，但硬性要求仍然保留；对话正在运行时返回 409。
- 找回工具：
  - 同一用户的另一段对话；
  - 别人消息的序号；
  - 只在附件里出现的关键词；
  - 大附件分页。
- 配置：有效窗口取最小值；没有登记的模型启动时报错；预算不满足一致性检查时启动时报错。

### 通用

- `cd jobpilot && uv run pytest -q`、`uv run ruff check`、`uv run ruff format --check .` 都通过。
- 迁移能回退再升级。

**真实模型的 E11 不在本任务里**（评审 [11]）。正式的 E11 要比三组：全部历史、只截断、摘要 + 截断。三组共用同样的模型、工具、任务状态、记忆和预算，只有历史策略不同。题目分成两类：答案只在已移出的历史里，以及要查当前业务数据。记录这些结果：
