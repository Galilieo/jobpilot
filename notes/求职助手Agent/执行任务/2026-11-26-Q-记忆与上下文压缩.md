## 设计

### 1. 通用：窗口、token 计量和超长错误

**模型档案**：在配置里按模型名登记 `context_window`、`max_output_tokens`，以及它使用的**协议适配器**。没有登记的模型启动时报错，不猜默认值。

适配器负责三件事：哪些字段可以发送（例如 DeepSeek 的 `thinking`）、用量怎样读、超长错误怎样识别。上层只认统一的结果。所以准确的说法是：「已有适配器支持的模型，换模型只改配置」；接新的服务商要加一个适配器。验收用两种假服务商的响应来覆盖，不需要接第二家真实模型（评审四 [10]）。

**有效窗口**取三者中最小的一个：

1. 模型自己的窗口；
2. 模型窗口 × `context_window_ratio`；
3. `context_window_cap_tokens`。

| 场景 | 配置 | 效果 |
| --- | --- | --- |
| 开发和测试 | ratio 0.5，cap 32,000 | 32K，容易触发压缩，便于测试 |
| 上线（用户决定） | ratio 0.5，不设 cap | 1M 的模型得到 512K |

**窗口估算**：函数命名为 `estimate_request_tokens`。它和网关预扣费用用的估算是两回事，分开命名、分开测试（评审四 [03]）。

- **只有能证明前缀相同时，才用增量计算**。条件是以下三项同时成立：
  - 同一次运行里，同一条主调用的消息流；
  - 同一个模型和适配配置；
  - 上一次实际发送的内容（包括工具定义），是这一次请求从头开始的完整前缀。

  满足时，本次 = 上一次服务商返回的实际输入 token + 新增后缀的估算。新增后缀包括上一次回复里的工具调用、工具结果和要回传的推理内容。
- **怎样判断前缀相同**：在内存里记下上一次请求的序列化摘要值（哈希），本次用同样的方法算出前缀的哈希来比对。不保存请求原文。跨轮、跨运行都不复用。
- **其他情况一律全量估算**：切换了模型、压缩过、临时截断的边界变了、无法证明前缀相同、上一次调用失败、没有返回用量。
- 估算沿用网关的 UTF-8 字节上界，会偏高，偏向安全。
- 只取主调用自己的用量，同一轮里子调用（例如依据检查）的用量不参与。

**超长错误**：网关把各服务商的「上下文超长」错误统一成 `ContextOverflowError`，由各适配器负责识别。普通的 400 不算超长。

**预算一致性**：启动时检查「每轮 token 预算 ≥ 4 × 有效窗口」，不满足就拒绝启动。比如上线放到 512K 时，要同时调大每轮预算，否则一次满窗口的调用就会用光一轮的额度。

这条检查只是配置的下限，**不保证一轮一定能完成四次满窗口的主调用**：网关按字节上界预扣，可能比实际更早拒绝。另外，用户输入的字符上限（`AgentLimits.input_characters`）是从每轮预算推出来的，调大预算时它也会跟着放宽，要一起验证（评审四 [06]）。

> 留尾（不在本任务）：每轮预算改成按实际费用计算。命中缓存的输入价格约为不命中的 2%，窗口放大以后，按 token 数限额会过于保守。

### 2. 每次调用模型时的上下文

顺序按评审 [13] 调整：越固定的越靠前，有利于前缀缓存命中，但不为缓存做专门设计。

| 顺序 | 内容 | 谁来写 | 是否压缩 |
| --- | --- | --- | --- |
| 1 | 系统提示词与工具清单 | 固定 | 不压缩 |
| 2 | 长期记忆，按固定的栏目顺序渲染 | 用户确认过的 | 不压缩；栏目和长度都有上限 |
| 3 | 工作摘要 | 模型写，滚动更新 | **主要压缩的部分** |
| 4 | 任务状态 | 程序从数据库生成 | 不压缩，状态变化时重新生成 |
| 5 | 最近几轮的原文 | — | 按完整的轮切开，至少保留当前这一轮 |
| 6 | 本次输入 | 用户 | 附件按不可信数据处理 |

**任务状态**（评审 [08]）：

- 包含这些字段：
  - 当前岗位 ID 和绑定修订号；
  - 事实库版本；
  - 适用于这个岗位的最新报告 ID，以及它基于的岗位版本和事实版本；版本不一致时标「基于旧版本」，没有报告时写「未匹配」；
  - 当前简历的运行 ID 和版本号；
  - 有效卡的 ID 和状态。
- 报告详情、卡片参数、JD 全文和简历正文都交给读取工具去取，不放进任务状态。
- 来自 JD 的字符串（岗位名、公司）有长度上限，并按数据渲染。
- 不放时间戳这类和业务无关、每次都会变的内容。
- 刷新时机：
  - 切换岗位、写入、生成、暂停后恢复之后，重新生成变化的部分；
  - 图在确认卡之后不会再经过 `build_context`，所以要在 `apply_action` 和生成类工具之后刷新，不能沿用一轮开始时的状态。
- 复用现有的 `current_job_summary` 等查询，不另写一套。

### 3. 工作摘要

**栏目**：结构化 JSON，用 Pydantic 校验，渲染成小标题加列表。每栏的条数和字数有上限，写成命名常量。

| 栏目 | 内容 |
| --- | --- |
| `goal` | 这段对话要做成什么 |
| `requirements` | 用户提过的要求。否定、硬性要求、例外、改口这几类，每条都要带**短原话、来源消息序号、适用岗位**；新要求取代旧要求时，记下取代了哪一条（评审 [06]） |
| `done_and_decided` | 已完成的事和已定下的事 |
| `open_items` | 还没做完的事 |
| `answered_questions` | 提问卡上的问题和对应的答案，保持一一对应 |
| `unverified` | 不确定的内容。不确定的说法只能放在这里 |

**原话校验**：摘要写入前，程序逐条核对引用的原话。只承认两种来源（评审四 [07]）：

1. 本人在本对话里的**用户消息正文**（不含附件）。引用时记消息序号。
2. 本人**已经提交的提问卡答案**。引用时记 `action_id + question_id`，到已保存的决定里核对问题和答案。

其他工具消息（比如读回来的 JD）里，即使出现同样的文字，也不算来源。核对不上的条目移到 `unverified`。栏目放不下时，保留「消息 x～y 里还有相关内容」这种范围提示，不悄悄丢掉。

**滚动更新**：每次压缩的输入是「上一份摘要 + 这次移出的完整轮次」。移出轮次的序列化方式：

- 用户正文和提问卡的答案完整保留；
- 工具结果每条最多 2,000 字符；
- 附件只留来源说明和前 500 字符。

**防注入**：

- 摘要放在不可信数据区；
- 摘要不作为改写、依据检查或任何写入卡的输入；
- 摘要里的内容不能拼成当前这一轮的 `user` 指令（评审 [02]）。

**找回工具** `read_conversation_history`（只读，评审 [09]）：

- 服务端绑定当前登录用户和当前对话，消息序号只是筛选条件。
- 按「序号范围」或「关键词」查询。返回的每段都标明来源（用户正文、附件片段、提问卡答案、助手回复、工具步骤摘要）以及有没有被截断。
- 按条数和字节双重上限分页，返回下一页的位置。
- 原业务对象有 ID 的，告诉模型用相应的读取工具去取详情。
- 读回来的内容照样按不可信数据包装。

摘要末尾固定加一行找回指引。

### 4. 压缩：边界、时机和运行

**同一道边界**（评审 [01]）：

- `conversation` 新增这几列：
  - `summary_json`，JSONB；
  - `summary_through_seq`，摘要覆盖到的最后一条消息的序号；
  - `summary_revision`。

  删掉旧的 `summary` 文本列。
- **写入**：调用模型前，先固定三样东西：旧修订号、旧覆盖点、本次截止序号。截止序号只能落在**已经结束的完整轮次**上。模型返回后，在一次条件更新里写入摘要、截止序号和修订号加一，条件是修订号仍为旧值。压缩期间有新消息追加，不影响这次的结果。
- **读取**：在同一个读快照里取摘要和覆盖点之后的消息，本轮输入只出现一次。
- **计量**：从覆盖点之后的全部历史算起，不能用「最近 10 轮」裁剪后的结果来判断。删掉 `history_turns` 这个配置，由 token 水位决定保留多少。

**水位**（用户决定，评审 [07]）：

| 量 | 初值 |
| --- | --- |
| 自动压缩的触发点 | 下一次请求的预计大小（固定部分 + 摘要 + 任务状态 + 保留的原文 + 输出预留）超过有效窗口的 **80%** |
| 压缩后的目标 | 整个请求约为有效窗口的 **50%**。分配方法见下文 |
| 只在能移出至少一个完整轮次时才压缩 | 否则不调用模型 |

**压缩后目标的分配**（评审四 [06]）：

- 先从 0.5 × 窗口里扣掉本次的固定部分：系统提示词、工具清单、记忆、任务状态，以及**实际要发出的**输出预留（只算一次）。
- 剩下的份额，摘要最多占 1/5，其余给最近原文。
- 实际的 `max_tokens` 同时满足三个上限：用途配置、模型档案、窗口剩余空间。

这样按上限分配，压缩完之后一定在触发点以下，不会出现刚压完、下一轮又要压的情况。

**不可移出的部分已经超过目标时**，分三种情况处理：

| 情况 | 处理 |
| --- | --- |
| 整个请求仍然在窗口以内 | 照常发送，记一条日志 |
| 超出窗口，主要是当前这一轮的工具结果太大 | 按字段裁剪这一轮的工具结果（沿用 `tool_result_bytes`），再发送 |
| 用户正文本身就超出窗口 | 返回明确的错误，提示拆分输入 |

两个比例（80%、50%）和摘要所占份额都写成配置，由 E11 来调。

**入口**：同一个压缩函数，只有入口不同。

| 入口 | 什么时候 | 怎样运行 |
| --- | --- | --- |
| 自动 | 一轮结束后达到触发点 | 在后台跑，用户不用等 |
| 手动 | 用户点「压缩上下文」，可以附一句重点 | `POST /api/conversations/{id}/compact`。重点说明只能调整「多保留什么」，不能挤掉仍然有效的硬性要求。按下面的顺序判断（评审四 [12]）：<br>① 已经有一次压缩在进行：返回它的运行 ID，并标明 `focus_applied: false`（这次的重点没有用上），不会为了加上重点再发一次请求；<br>② 对话有 `agent` 运行正在进行：返回 409；<br>③ 没有可移出的轮次：返回 200 和「无需压缩」；<br>④ 其他情况：开始压缩 |
| 本次请求超出窗口 | 某次主调用的完整请求超过「有效窗口 − 输出预留」 | 只对这一次请求丢掉最早的、还没被摘要覆盖的原文，**不推进覆盖点**，并告诉模型「消息 x～y 未包含，可以用 read_conversation_history 查」。当前这一轮自己就超过时，按明确的错误结束，提示用户拆分输入 |
| 服务商返回超长 | 收到 `ContextOverflowError`，请求还能缩小，剩余预算也够 | 按上一条缩小后重试一次。重试的请求必须**严格小于**被拒的那次：本地估算已经在窗口以内、上游仍然报超长时，按被拒请求的实际大小去缩小，而不是再按本地上限算一遍。已经有流式文字发给用户时，不自动重发，沿用现有规则，避免同一段话显示两次 |

**压缩运行**（评审 [05]）：

- 新增 `ai_run.kind = 'compact'`，需要迁移 `ck_ai_run_kind`。另加一个条件唯一索引：每段对话同时最多一个活跃的 `compact` 运行。手动重复请求时，返回已有的那个运行。普通的 `agent` 运行不受影响，用户照常可以发消息。
- 创建压缩运行时，核对账号有效、对话存在。收尾在同一个事务里完成：先检查运行仍然活跃、归属和覆盖边界都没变，再写入摘要和终态。如果删除或删号先完成，就放弃这次结果，已经发出去的调用照实记账。
- **预算**（评审四 [04]）：
  - 网关保留现有唯一的登记入口，按运行类型选择预算。压缩的预算归属固定为这次 `compact` 的 `run_id`，有自己的调用次数和输入上限，不借用对话那份 65 次、250,000 token 的额度。
  - 每一次真实发送（包括修复和重试）都登记一行；同一次发送的结算只更新原来那一行。
  - 复用现有的 `model_call` 账本，不另建一套。现在按两个条件用 `OR` 查询同一张表，不会把一行算成两次。
- **分批推进**（评审四 [04]）：
  - 每次只取压缩预算放得下的**最早一批完整轮次**，成功就把覆盖点推进到这一批的末尾。积压很多时分几次追上，不会因为输入越积越长而永远压不完。
  - 单独一个已结束的轮次就超过压缩预算时，把它序列化成有上限的版本：用户正文截断，附件和工具结果只留来源说明，并写上「原文见消息 x」。
- **失败处理**：
  - 失败的情况包括调用失败、校验不通过、超长。处理方式是保留旧摘要，记日志，不影响对话。
  - 同一个覆盖点上、**必然会超长**的失败，不按原样重试：下一次把这一批减半。
  - 临时故障（网络、上游 5xx），在下一轮结束后再试。同一个覆盖点最多连续失败 3 次（命名常量），之后停止自动压缩、记日志，等手动压缩或者有新的轮次再试。
  - 这样不会为同一段历史反复付费。

### 5. 长期记忆

**栏目**：放在 `jobpilot/data/memory_keys.yaml`。同一个文件里还登记每个栏目的别名，以及每个枚举值的口语说法，供原话绑定使用。

| 类别 | 栏目 | 取值 |
| --- | --- | --- |
| 求职偏好 | `target_direction` 目标方向 | 文字，≤ 100 字 |
| 求职偏好 | `cities` 城市 | 列表，≤ 5 个，每个 ≤ 20 字，去重，保留用户给的顺序 |
| 求职偏好 | `excluded_types` 不考虑的岗位或公司类型 | 列表，≤ 5 个，每个 ≤ 30 字 |
| 求职偏好 | `job_notes` 其他 | 文字，≤ 300 字 |
| 写作偏好 | `tone` 语气 | 枚举：平实 / 简洁有力 |
| 写作偏好 | `bullet_length` 每条长度 | 枚举：尽量一行 / 不超过两行 / 不限。这是偏好，不保证排版后的行数 |
| 写作偏好 | `tech_terms` 技术名写法 | 枚举：英文原名 / 中文 / 中英并列 |

每周到岗天数、实习时长、最早到岗已经在事实库的「求职条件」里，不再重复记。

**表**：`memory` 的主键是 `(user_id, key)`，字段有 `value_json`、`revision`、`deleted_at`、`source`（对话的 `conversation_id` 和 `message_id`，或者「手动」）、`updated_at`。

- 撤销需要的上一个值、上一次的删除状态和生效的修订号，存在对应动作的 `agent_action.undo_json` 里（沿用现有字段）。`result_json` 会回传给模型，也会出现在对话详情和事件流里，所以只放可以公开的内容：栏目、动作和新的修订号，**不放旧值**（评审四 [01]）。
- 键和取值的上限，数据库约束和代码用同一组常量。

**版本规则**（评审 [04]）：

- 从来没创建过的栏目，预期版本是 0。
- 第一次写入靠主键竞争决定谁先写成，后写的那个返回 409。
- 已有的行，按 `(user_id, key, expected_revision)` 做一次条件写入。
- 新增、修改、删除、恢复、撤销，都会让修订号加一。
- 撤销时恢复的是上一个值和删除状态，修订号照样往前走，不会回到旧号。所以更早的失效卡也不会因此重新生效。
- 确认接口可以提前报冲突，但真正执行写入的事务里还要再检查一次。

**写入工具必须引用本轮原话**（评审 [02]、[03]，用户同意的做法）：

- `remember(key, op, value, quote)`，写入类，需要确认。光是原话里出现过某段文字，不能证明用户授权了这个动作、这个栏目和这个值，所以要把四样东西固定下来（评审四 [02]）：

  | 参数 | 含义与校验 |
  | --- | --- |
  | `key` | yaml 里有的栏目 |
  | `op` | 文字和枚举类栏目只能是 `set`。列表类可以是 `add`、`remove`、`replace` |
  | `value` | 要改的值。列表的 `add`、`remove` 只传要增删的那几项，**完整的新列表由服务端按出卡时的版本算出来** |
  | `quote` | 支持这次修改的原文片段。必须是**本轮用户消息正文**里的一段，不能来自附件、摘要或历史 |

- **值和原话的绑定**，由程序判断：
  - 文字类：`value` 必须包含在 `quote` 里。
  - 列表类：每个要增删的项都必须出现在 `quote` 里。
  - 枚举类：`quote` 必须包含这个枚举值本身，或者 yaml 里为它登记的口语说法。比如 `tone=平实` 登记了「朴实一点」「别太花哨」。不能拿任意短词去对应任意值。
- **不出卡、改为向用户澄清（用 `ask_user`）的情况**：
  - `quote` 只是「可以」「好的」这类泛泛的回答；
  - `quote` 是否定句，而动作是 `add` 或 `set`；
  - 本轮正文已经被 `parse_jd` 当作 JD 的来源，用户把 JD 贴进了正文，这时不能从这条正文里引用。
- 卡片显示：
  - 「来源：你刚才说的『……』」；
  - 修改后的完整值，并标明是「增加」还是「替换」。比如「以后杭州优先，上海也行」应该是给城市增加上海。
- 一条消息里有多个偏好时，按栏目分别出卡；同一个栏目里增加几项，合成一张卡。
- `forget(key, op, value, quote)`，规则相同。`op` 可以是 `remove`（删掉列表里的某几项）或 `clear`（删掉整个栏目）。`clear` 时，`quote` 必须包含这个栏目的名称，或者 yaml 里为它登记的别名。
- 这个机制的效果：
  - 删掉以后，旧对话和摘要里的值不能再变成建议卡，因为它们不是本轮的原话；
  - 用户这一轮明确再说一次，就可以重新记下；
  - JD 和历史里藏的指令触发不了写入。
  - 用户在管理页手动恢复，也算数。
- 两个工具都可以撤销，规则同上。

**接口**：

- `GET /api/memories`，返回每栏的值和修订号，已删除的栏也返回修订号，供重建时使用；
- `PUT /api/memories/{key}`，带 `expected_revision`；
- `DELETE /api/memories/{key}`，也带 `expected_revision`。

账号导出要包含记忆，删除账号时级联删除。

**用在哪里**：

- 对话时，全部记忆放进第 2 块。
- 改写时，只用写作偏好的三个枚举值，由程序翻译成固定的措辞要求句。
- `job_notes` 等自由文字不进入改写。

### 6. 改写入口与评测兼容

**写作偏好在改写运行创建时固定下来**（评审 [10]）：由服务端读取本人已经确认的三个枚举，写进 `ai_run` 新增的 `writing_preferences_json` 列。对话里的 `tailor_resume` 和岗位页发起的改写共用这一套；恢复运行时用当初记下的那份。

不放进 `plan_json`，因为改写收尾时会用 `plan_record(...)` 整体覆盖它（`tailoring_store.py`），这份快照就丢了（评审四 [09]）。这一列创建后不再更新。验收覆盖这条时序：运行建立后用户改了偏好 → 暂停后恢复 → 正常收尾。实际发出的消息和最终记录，都要保留最初那份偏好。

**用户没设任何写作偏好时，E3 和 E5 实际发出去的消息必须逐字节不变**，包括不能多出空字段、空标题或换行。验证方法：

- 用同一组合成输入和假网关，抓取修改前后实际发出的消息并比对；
- 覆盖 E3 的匹配，以及 E5 各阶段：匹配、初写、修订、依据检查；
- 基线组和产品路径分开验证。

设了偏好时，只允许指定的写作请求里多出那几句固定措辞。这只能证明输入兼容，不能证明真实模型重跑的分数一定相同。

**改一条简历条目时不再由主对话模型直接写文字**（评审 [02]）：

- **公开的工具名仍然是 `edit_resume_item`，不改名**。模型提议用的参数和存进数据库的卡片要分成两份定义，不能再让卡片继承模型参数（评审四 [05]）：

  | 定义 | 字段 |
  | --- | --- |
  | 模型提议的参数 | `run_id`、`bullet_id`、`mode`（`replace` 或 `polish`）、`quote` |
  | 存进数据库的卡片 | `run_id`、`bullet_id`、`base_version_id`、`previous_text`、`text`、`check` |

  任务 P 的渲染依赖卡片的字段，这些字段保持不变。升级前已经存下的旧卡，也按这份卡片定义来读取。
- **确认、恢复、重放时，只执行卡上已经检查过的那段候选文字，绝不重新生成。**
- **两种入口**（评审四 [08]）：
  - `replace`：用户本轮明确给出了替换的正文，并且改哪一条、改成什么都唯一确定，比如「第二条改成：参与接口联调」。`quote` 就是那段替换正文，必须是本轮用户消息正文里的一段。服务端直接把它当作候选文字，不经过模型，照常跑依据检查、出卡。改哪一条或改成什么有歧义时（比如一句话里改了好几条，或者「别写『主导』，改成『参与』」这种分不清要哪段的），用 `ask_user` 澄清。
  - `polish`：开放式的润色，比如「写得更偏工程」。`quote` 是这条修改要求的原话。服务端组装输入：原条目、它引用的事实、写作偏好的枚举值、这条修改要求，交给新提示词 `edit_bullet.txt` 生成候选文字，再照常跑三层依据检查、出卡。
- **只改文字，保留原来的事实引用**：这样改动最小，和任务 N 一致。原条目没有引用任何事实的，只支持 `replace`，不支持 `polish`。
- **复用已有代码**：网关、事实序列化，以及合适的解析函数。注意 `parse_revision` 要求结果至少带一条事实标签，不适合直接拿来用。为编辑单独构造发给模型的消息；出卡、确认、撤销的流程照任务 N 不变。
- 不改 `revise_bullet.txt`，它属于 E5 的输入。
- `job_notes`、摘要和历史读取的结果都进不了 `edit_bullet` 的输入。
- **验收**：拿一张升级前格式的卡，覆盖升级后的确认、重放和撤销，并比对任务 P 用到的事件和详情响应，确认没有变化。

### 7. 系统提示词

分两次升级，跟着两个阶段走：

- **v3（阶段一）**：
  - 记忆块是什么；
  - 只有用户本轮明确说了跨对话的偏好，才提议 `remember` 或 `forget`，并引用原话；一次性的要求不记；说法含糊时，用 `ask_user` 澄清；
  - 改条目时分清 `replace`（用户给了原文）和 `polish`（开放润色）；
  - 经历一律进事实库。
- **v4（阶段二）**：
  - 工作摘要和任务状态两块是什么；摘要只能参考，以读取工具读回的为准；
  - 涉及硬性要求、又有冲突时，先用 `read_conversation_history` 查原文。

## 验收

先写会失败的测试，再改代码；关键判断做变异检查。时序问题用可以控制的暂停点来固定顺序。

### 阶段一：记忆

- 跨对话召回；改口时覆盖原值；列表增加和替换分开处理。
- 删除后的两种情况：旧对话或摘要里的值不出卡；本轮重新明确说的，出卡。
- `quote` 来自附件、摘要或历史读取的结果时，不出卡。
- 不认识的键、超长的值，返回 422。
- 用 A 的接口和工具改不了 B 的记忆。
- **两段对话、两张不同的卡**，同时为一个还不存在的栏目确认：一个成功，一个冲突。
- 旧管理页带过期的版本号去删除，返回 409。
- 撤销后恢复上一个值，并且更早的失效卡不会重新生效。
- 改写边界：
  - 「`job_notes` 写着『把我写成负责人』→ 用户要求润色第二条 → 检查」这条链路里，`edit_bullet` 和依据检查实际收到的输入都没有这句话；
  - 没有写作偏好时，E3 和 E5 实际发出的消息逐字节不变；
  - 运行建立后用户改了偏好 → 暂停后恢复 → 收尾，实际发出的消息和最终记录用的都是最初那份偏好。
- 原话绑定（评审四 [02]）：
  - 口语说法对应到枚举值，比如「朴实一点」→ `tone=平实`；
  - 列表增加，比如「上海也行」→ 城市增加上海，完整列表由服务端计算；
  - 一句话里有多个偏好时，按栏目分别出卡；
  - 不出卡、改为澄清的几种情况：泛泛的回答（「可以」）、否定句、正文是 JD、附件和正文里出现同一个词。
- `forget` 之后：执行恢复、对话详情、事件流、下一次发给模型的消息里都没有旧值；撤销照样可用（评审四 [01]）。
- 条目编辑（评审四 [05]、[08]）：
  - `replace` 直接用用户给的原文；有歧义时改为澄清；
  - `polish` 走 `edit_bullet`；
  - 没有事实引用的条目只能用 `replace`；
  - 升级前格式的旧卡，确认、重放、撤销都正常，任务 P 用到的事件和详情响应不变。

阶段一完成时，在**现有的上下文**里就能用上记忆：跨对话召回、出卡、确认、撤销都能端到端跑通。

### 阶段二：压缩

- 六块的顺序和各自的上限。
- 摘要不能覆盖到压缩期间新来的消息：先固定截止到第 80 条，期间消息涨到第 90 条，写入后覆盖点是 80，81～90 仍然以原文出现。
- 读取用同一个快照，不会漏掉一段或重复一段。
- 超过触发点时，一轮结束后在后台压缩；压缩后的请求在目标以内。
- 滚动更新的输入只有「上一份摘要 + 新移出的完整轮次」。
- 原话校验：
  - 校验不通过的条目，移到 `unverified`；
  - 只在提问卡里回答过的「不接受外包」，可以作为来源；
  - 同样的文字出现在普通工具读回的结果里，不算来源（评审四 [07]）。
- 窗口估算（评审四 [03]）：
  - 纯追加的请求用增量算；
  - 这几种情况全量重算：切换模型、压缩后的第一轮、临时截断后重新带回历史、上一次调用失败、缺少用量；
  - 主调用之后紧跟子调用时，不能拿子调用的用量当作主调用的。
- 压缩后的完整请求在触发点以下；不可移出的部分超过目标时，按三种情况分别处理（评审四 [06]）。
- 分批推进（评审四 [04]）：
  - 积压超过压缩预算时，分几批推进覆盖点；
  - 一个超大的单轮，按有上限的方式序列化；
  - 必然超长的失败不原样重试；
  - 连续失败 3 次后停止自动压缩。
- 压缩计费（评审四 [04]）：
  - 重复点手动压缩，只发一次请求；
  - 上游确实重试了两次，就登记两行；
  - 删号后迟到的结果不写回。
- 三次压缩以后，「否定 → 某个岗位例外 → 撤回例外」仍然正确；提问卡里的答案保留。这一项用假模型测管道，内容质量交给 E11。
- 本次请求超出窗口时，只截断这一次、不推进覆盖点，并且告诉模型哪段消息没放进来；当前这一轮自身超长时，按明确的错误结束。
- 统一超长错误（评审四 [10]）：
  - 收到 `ContextOverflowError` 时，缩小后重试一次，重试的请求严格更小；
  - 普通 400 不重试；
  - 已经有流式文字发给用户时，不重发；
  - 用两种假服务商的响应覆盖。
- 端到端：「旧 JD → 历史读取 → 出卡」这条链路不会出 `remember` 卡。
- 并发与删除：分别在「读完历史」「请求已登记」「返回了但还没写入」三个位置暂停，插入新消息、第二次压缩、删除对话、删号，检查覆盖范围、终态和实际发出的请求数。
- 手动压缩：
  - 判断顺序照第 4 节（已有压缩 → 有 `agent` 运行 → 无需压缩 → 开始）；
  - 带重点时，重点会传进压缩提示词，但硬性要求仍然保留。
- 找回工具：
  - 同一用户的另一段对话；
  - 别人消息的序号；
  - 只在附件里出现的关键词；
  - 大附件分页。
- 配置：有效窗口取最小值；没有登记的模型启动时报错；预算不满足一致性检查时启动时报错。

### 通用

- `cd jobpilot && uv run pytest -q`、`uv run ruff check`、`uv run ruff format --check .` 都通过。
- 迁移能回退再升级。

**真实模型的 E11 不在本任务里**（评审 [11]）。正式的 E11 要比三组：全部历史、只截断、摘要 + 截断。三组共用同样的模型、工具、任务状态、记忆和预算，只有历史策略不同。题目分成两类：答案只在已移出的历史里，以及要查当前业务数据。记录这些结果：

- 直接答对；
- 查回原文后答对；
- 答反；
- 重复提问；
- 没完成。

成本要算上压缩、找回、失败和重试。E11 放到 T3.6 或统一评测批次，跑之前先估费，等用户批准。本任务回报时附上建议的脚本清单。

## 不做的

- 前端的「我的 → 记忆」页面、记忆卡片的专门渲染、「压缩上下文」按钮，都放到之后的小前端任务 R。任务 P 的通用卡片兜底已经能确认 `remember` 和 `forget`。
- 按需选择记忆、弱项记忆（V2）；由模型判断什么时候压缩；使用服务商的服务端压缩或专门针对缓存的设计。
- 每轮预算改成按实际费用计算（留尾）。

### 前端接口

| 接口 | 请求和响应 |
| --- | --- |
| `GET /api/memories` | 按栏目顺序返回所有行。每项包含 `key`、`value` 为字符串、字符串数组或 null、`revision: number`、`deleted: boolean`。未建立的栏目返回修订号 0，删除后的行有自己的修订号 |
| `PUT /api/memories/{key}` | JSON `{expected_revision, value}`，返回更新后的行 |
| `DELETE /api/memories/{key}` | JSON `{expected_revision}`，返回删除后的行。更新和删除的过期修订号均为 409 |
| `POST /api/conversations/{id}/compact` | 可选 JSON `{focus}`，最长 300 字。返回 `{run_id, status, focus_applied}`。已安排或已有压缩是 202。已有任务时复用 ID，且这次重点未生效。无需压缩是 200 和 `status: "not_needed"`。正在执行普通对话且尚无压缩任务时返回 409 |
