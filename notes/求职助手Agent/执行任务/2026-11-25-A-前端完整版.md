## 要做的

每一项做完都在浏览器里实测，再提交。

1. **工作台（首页）**：问候语；三张状态卡——经历事实库（已发布条数、版本、待确认条数）、不编造记录（改写条数、通过 / 回退 / 待处理条数）、记住的偏好（记忆还没做，显示「之后开放」）；岗位进度看板（未匹配 / 已匹配 / 已生成简历 / 已投递），卡片点进岗位详情。首页从 `/jobs` 改为 `/workspace`。
   - 后端新增 `GET /api/overview` 一次返回这些计数（新文件 `jobpilot/api/overview.py`），不要让前端为每个岗位各发几个请求。
2. **我的 · 简历**：每份定制简历一行（岗位、基于的事实库版本、状态、更新时间、当前版本号），「打开」进入对应岗位详情。
   - 后端新增 `GET /api/tailored-resumes`（02 第 6 节已列），按更新时间倒序。
3. **我的 · 经历补全**：手动补充事实（`POST /api/facts`：经历、类型、职责、文字），列表里标「你补充的」；已发布的事实可以修改、删除（`PUT`/`DELETE /api/facts/{lineage_id}` 会先复制进草稿），改完回到「待确认」等用户发布。
4. **岗位详情补全**：基本字段逐格点击修改、要求和关键词可增删改（`PUT /api/jobs/{job_id}`），每格标「AI 提取」或「你填写」（`JobOut.overridden`），没写的显示「未填写」；进度（stage）选择；JD 里有可疑指令时（`injection_flags`）显示提醒；匹配历史列表，可打开旧报告。
5. **定制简历面板补全**：
   - **依据追溯**：点一条改写，显示它引用的事实、原文片段和检查结论（`GET /api/tailor-runs/{run_id}/resume` 已返回 `facts`）；回退的条目说明「改写没通过检查，用了事实原文」，待处理的说明要用户处理。
   - **计划里的「建议补入」**：`GET /api/tailor-runs/{run_id}` 的 `blocks[].focus[].base_status`，在面板里列出「所选底稿没写到、建议补入」的要求。
   - **版本历史**：列出版本，可预览旧版本（`/preview?version=n` 只读）、从旧版本导出。
   - **运行历史**：同一岗位的其他改写运行（`GET /api/jobs/{job_id}/tailor-runs`），失败或额度用完的显示原因。
6. **07 第 7 节的细节逐页对照**：列表骨架屏、空状态给下一步、出错说人话并保留输入、删除二次确认、按钮动词开头。窄屏（< 992px）：侧栏变抽屉（已有）；岗位详情的简历面板改成全屏层，由顶部「查看结果」按钮打开。
7. **前端测试**：加 Vitest 和 Testing Library，`pnpm test` 能跑。至少覆盖：`api/http.ts` 的错误整理（401、404、409、422 列表、断网）；导入简历同一次重试复用幂等键、成功后换新键；事实库 409 时刷新并提示；简历面板轮询在运行结束后停止。关键判断做变异检查（故意改坏一处，确认有测试失败）。

后端新增的接口：写测试（含跨用户 404），在 `jobpilot/tests/test_isolation.py` 登记，`cd jobpilot && uv run pytest -q` 和 `uv run ruff check` 都通过。
