## 背景

用户马上要用自己的简历第一次真实投递。评审发现几处会直接影响**发出去的文件**或**用户保存的修改**的问题：导出的 HTML 里带着内部检查数据；编辑器的保存、导出、重置顺序会交付错误版本；条目换段后沿用旧的检查结论；底稿最后一行可能丢失。另有三处小的收尾（账号恢复、幂等键、日志）。

## 要做的

### 1. 投递用的 HTML 只带可见内容

现状：`api/tailored_resume.py` 的 `export_resume` 给导出 HTML 开了编辑器，`resume_export._editor_json` 把整份 `content.model_dump()` 嵌进 `<script type="application/json">`。正文虽然略过了待处理条目，HR 打开源码仍能看到那句模型原文、`fact_ids`、`check`（检查结论和问题说明）。`test_resume_export.py` 约 87 行的「导出没有标记」测试没传 `editor`，所以没发现。

- 给导出附件定义专用的数据结构：只放可见文字、版式（`style`）和离线编辑**实际用得到**的字段。先读 `resume_editor.js` 离线模式用了 `data.content` 的哪些部分，用不到的不嵌。
- 预览页（应用内在线编辑）保持现状，它需要完整内容做保存。
- 账号导出（`GET /api/account/export`）照旧保留完整依据，不改。
- 测试：在待处理条目的原文和检查问题里放**独特标记**（如 `ZZ_PENDING_MARK`），从**下载接口**拿 HTML，对**整份文件**（包括内嵌 JSON）断言没有标记、没有事实 ID、没有检查结论字段。先写这个测试，确认在现在的代码上失败。

### 2. 保存后回的是这次保存的版本

现状：`save_resume` 提交后调用 `load_resume()` 读「当前版本」。A 保存成 v2、回包前 B 又存成 v3，A 会收到 v3，下一次用 v3 当基准，可以覆盖 B 的修改。

- `save_version()` 已经返回这次建立的版本，用它组装回应（或在持锁期间组装，提交成功后返回）。
- 测试：用两个受控请求固定顺序，A 收到的一定是 v2；A 再以 v2 为基准保存，得到 409。

### 3. 检查结论绑定条目在服务端的位置

现状：`resume_versions.recheck` 按全局 `bullet_id` 找上一版条目，文字没变就沿用 `before.check`。把实习 A 的已通过条目移到项目 B，ID 和文字都不变，检查结论照搬，导出后 A 的成果就挂在 B 名下。重查时用的栏目类型 `section.kind` 也来自请求。

- 编辑器只支持原位改字，所以直接拒绝：条目换了所属经历、同一经历 ID 出现两次、经历换了栏目，都回 422（和现有「不认识的条目」一样处理）。
- 栏目类型和经历名一律取上一版（服务端），不信请求。
- 测试：三种情况各一条，先在现在的代码上失败。

### 4. 编辑器：保存串行、导出等保存、重置由服务端做

现状（`templates/resume_editor.js`）：「导出 HTML」直接跳转 `export_url`，不等一秒后的自动保存，把 30% 改成 20% 后立刻导出会下载到 30%。「重置」读出 v1 整份送回；如果当前版本删掉过条目，v1 里的条目 ID 对上一版来说「不认识」，服务端回 422。

- 同一页的保存串行：上一次没返回不发下一次，期间的修改合并到下一次。
- 导出：先清掉定时器立即保存，等保存成功后按**返回的版本号**导出（`?version=n`）；保存失败就不导出，提示原因。
- 重置：新增服务端动作（例如 `POST /api/tailor-runs/{run_id}/resume/reset`，带 `base_version_id`），在锁内核对基准后，把本简历 v1 的内容复制成新版本。编辑器改为调用它。接口登记进 `test_isolation.py`（跨用户 404、待删除账号被拒绝）。
- 测试：接口测试覆盖「删空条目并保存后重置」得到与 v1 相同内容的新版本；编辑器的「改字后立即导出」在浏览器里实测，记录结果。

### 5. 底稿最后一行不被当成栏目名拿走

现状：`resume_content._split_tail_title` 对每一段都把最后一行判断为「下一栏的标题」。最后一段的末行（例如单独一行「教育技术学」，短、含「教育」、没有标点）被拿走后没有下一段承接，专业名称从组装结果和所有导出格式里消失。

- 只有确实还有下一段时才拿尾端的栏目名；同时看 `is_section_title` 能不能收窄（例如要求整行就是栏目名词表里的词或「XX经历」形式），规则放数据还是代码按 `CLAUDE.md` 判断。
- 测试至少三种底稿：最后一段是教育且末行是专业名；整份没有分段；真的有下一栏标题。

### 6. 恢复账号绑定是哪一次删除申请

现状：`db/accounts.restore_account` 只按 `user_id` 和七天期限更新。同一次申请发出两次恢复，第一次完成后用户再次申请删除，第二个请求如果此时才执行，会清掉新的申请。

- 在账号行锁内重新核对 session，并把认证时看到的 `deletion_requested_at` 作为更新条件。同一次恢复重发仍然成功；旧请求不能改变新的申请。`api/account.py` 申请删除时已有锁内重新核对 session 的写法，照着来。
- 测试：用两个事务固定顺序复现，先失败再修。

### 7. 请求协程被取消时，幂等键不再一直「处理中」

现状：`api/idempotency.py` 约 99 行只 `except Exception`。请求协程在等模型时被取消（`CancelledError` 是 `BaseException`），收尾没执行，相同的键一直回 409 直到重启。`test_idempotency.py` 约 330 行目前断言的正是这个状态。

- 确知本次执行已经退出时，用独立的短事务把这次 `attempt_id` 和运行标为失败；`model_call` 保持 `unknown`（可能已计费，明确重试会再计费）。收尾完成后继续抛出 `CancelledError`。
- 其余行为不变：同键处理中 409、内容不同 422、已完成重放原回应。
- 改写那条已返回 202 的路径不受影响（后台任务另有终态处理）。
- 修改现有测试的断言，并说明原断言为什么不对。

### 8. 后台改写的错误日志不带简历正文

现状：`api/tailoring.py` 的 `_fail_execution` 用 `logger.exception`。数据库错误可能附带 SQL 绑定参数，校验错误可能附带输入值，正文会进日志。

- 这个边界只记运行 ID、异常类名和允许的错误码；`db/session.py` 创建引擎时关掉参数回显（`hide_parameters=True`）。
- 测试：用带独特标记的合成数据触发一次写入错误，抓取完整日志输出，断言没有标记。
