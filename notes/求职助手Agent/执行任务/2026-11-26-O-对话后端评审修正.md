### 1. 决定已保存后能恢复，详情给出权威状态（[01]、[11]）

问题：确认决定已经存下，但进程在恢复开始前退出。重启只回收 `running`，这轮运行一直停在 `waiting_confirmation`。详情的 `pending_action` 只返回还没决定的卡，所以是空的。前端既看不到卡，也发不了新消息。

另外，详情接口分两条查询读消息和运行，中间可能刚好提交了最终回复和终态。结果是详情返回「成功」，消息列表却是旧的，前端看到终态就停止轮询，最终回复被漏掉。

改法：

- **状态**：服务端能区分三种状态，并在详情里返回：
  - 等用户决定：最新的卡还是 `pending`；
  - 决定已保存、还没开始恢复：最新的卡是 `confirmed` 或 `rejected`，但还没执行完；
  - 正在恢复。

  后两种用现有字段推导，**不新增一个单独存的状态列**（能推导的不另存）。推导规则写成一个函数，详情接口和启动时的补做共用。
- **启动补做**：在 `fail_abandoned_runs` 旁边加一步：认领「决定已保存但没执行完」的运行，交给 `RunLauncher` 恢复。这相当于事务发件箱：决定和「还有事要做」一起写进同一条动作行。重复提交同一个决定只恢复已保存的那个，不会新增。
- **详情**：返回当前卡，以及最近一张已决定卡的状态和执行结果。消息、运行、卡在同一个读快照里取，用 `REPEATABLE READ` 的只读事务，或者合成一条查询。
- **验收**，用假模型：
  - 在「决定已提交、恢复未开始」处让进程退出。重启后，运行自动恢复完成，业务写入只有一份。
  - 详情查询和终态提交交错时，不会出现「终态 + 旧消息」。

### 2. 预算从已持久化的调用记录算（[02]）

问题：剩余额度存在图状态（`graph.py:71` 的 `_budget`）里。检查点没来得及保存时进程退出，恢复后会从旧余额重跑，已经花掉的调用就被重新发了一次额度。

改法：

- 每个节点进入时，用这次运行（包括改写子图派生的运行）在 `model_call` 里的记录算已用量。`unknown` 也算进去，因为请求已经发出、只是结果不知道。图状态里不再单独存余额。
- 子图用量归到父轮次。`model_call` 登记和预扣在同一个事务里，网关已经有 `_register_call`，复用它。
- 验收：在「上游已接收、`model_call` 已提交、检查点没保存」处中断。恢复后，总调用数不超过上限，已经发出的那一次算进用量。

### 3. 发消息去重，没接收的消息要明确告诉前端（[03]）

问题有两种：

- 两个标签页同时发不同的消息时，第二个会拿到第一个运行的事件流，返回 `200`，自己的正文和附件没有保存。
- 第一次请求其实已经执行完、只是客户端没收到响应，客户端重发同一条消息，会新开一轮、再计费一次。

改法：

- `MessageIn` 加必填的 `client_message_id`，一个 UUID。数据库按「对话 + 客户端消息 ID」建唯一约束。
- 同一个 ID 再次提交：返回原来那次运行，正在跑的就接上它的流，已经结束的就重放。
- 不同的 ID 遇到活跃运行：返回 `409`，响应体带当前运行 ID 和待确认卡，正文写明「这条消息没有保存」。
- 前端契约 `web/src/api/` 同步加字段。对话页还没接，只改类型定义。

### 4. 账号取消后，迟到的启动不能再调模型（[04]）

问题：发消息的事务已经提交，后台任务还没登记，这时删号事务把运行标为取消。启动器找不到任务可取消，后台任务随后照常启动，并且在调模型前没有再查一次运行状态。

改法，从根上修：在网关登记 `model_call` 时，带上条件「运行仍是活跃状态」，写法是 `INSERT … SELECT … WHERE` 运行状态属于活跃状态。条件不成立就抛一个「运行已取消」的错误。这样对话、改写和以后的所有运行，在每次调用前都会被拦住，不需要在各个入口分别加检查。

改写流程在 `35b16db` 里已经有入口检查，可以保留，但不再是唯一的防线。

验收：在「消息已提交、任务未登记」处暂停，先完成删号申请，再放行启动。预期假上游收到 0 次请求，运行最后的状态是 `cancelled`。

### 5. 流没收到完成标记时，不当成完整回复（[05]）

问题：流正常结束了，但没有收到 `finish_reason`。现在的校验（`graph.py:113`）只排除 `length`，会把半截正文当作最终回答存下，或者执行一个参数 JSON 恰好完整的工具调用。

改法：

- 在进入工具路由前检查：`finish_reason` 必须是 `stop` 或 `tool_calls`，并且和响应内容对得上：`tool_calls` 必须带工具调用，`stop` 必须有正文。
- 其他情况按传输没完成处理，`model_call` 保持 `unknown`。
- 完整的响应里如果工具参数是坏的 JSON，照旧只让那一个工具返回 422，并且把「模型响应成功」和「工具参数无效」分开记。

验收：用假的 SSE 上游分别构造这几种情况：正常 EOF 但没有 `finish_reason`、连接异常、坏的工具 JSON、同一轮多个工具、缺用量尾帧。

### 6. `parse_jd` 改为引用本轮输入，不再让模型抄全文（[06]）

问题：模型看到的输入遮蔽了联系方式，它回传的 `raw_text` 里是 `[EMAIL]`。服务端拿没遮蔽的原文做子串校验（`graph.py:214`），结果返回 422。模型换一段不带邮箱的子串，校验能通过，但岗位库只存下半份 JD。

改法：`ParseJobArgs` 把 `raw_text` 换成来源引用，取值是 `message` 或某个附件的序号。服务端核对这个来源属于本轮的用户输入，然后直接取原文去解析。模型只看到脱敏后的副本。删掉原来的子串校验，不保留旧参数的兼容分支。提示词 `agent.txt` 同步修改，并更新版本锁。

验收：给一份中间带招聘邮箱的 JD，存下的是完整原文，发给模型的内容里没有邮箱。

### 7. 生成类工具设上限，入口限制总长度（[12]）

问题：资料里藏的指令可能让模型反复调用 `match_job` 或 `tailor_resume`，这两个工具是自动执行的。正文加 5 个附件，每个 2 万字，合法的输入也可能在第一次请求前就把额度用光。当轮的工具结果全量追加，直到超出预算。

改法：

- **不按「意图」放行**：判断意图本身也要靠模型，同样会被注入，所以不做。改为程序能确定的约束：
  - 每轮每个生成类工具有调用次数上限：`tailor_resume` 1 次，`match_job` 2 次，`parse_jd` 按本轮附件数。上限放进 `AgentLimits`。
  - 同一轮里输入相同的重复调用直接复用上一次的结果，不再调用模型。
- **入口总长度**：正文加附件有一个总长度上限，用命名常量，从每轮的 token 预算推出来，给工具和回复留出余量。超出时返回 422，并说明上限是多少。
- **大的工具结果**：按字段裁剪，或者只返回摘要加 ID、需要时再读，保证返回的始终是完整的 JSON。下一次模型请求要有空间。

### 8. 岗位绑定加修订号，撤销按修订号判断（[13]）

问题：用确认卡把岗位从 A 切到 B，之后在面板上切到 C，再切回 B。这时撤销旧卡，只比较当前岗位是不是 B，于是把用户最后的选择覆盖成了 A。

改法：

- `conversation` 加一个岗位绑定的修订号。下面这些变化都要让它前进：确认卡、面板 `PUT`、删除岗位导致的解绑。
- 撤销时要求修订号仍等于这个动作生效时的值，做法和简历撤销核对版本 ID 一样。
- 这是表结构变化，迁移单独一个提交。

### 9. 提问卡的回答按结构校验（[14]）

问题：岗位选择卡收到 `answers: ["切换"]`、没有 `job_choice`，接口照样接受，动作被标为已执行，岗位却没有切换。合并提问时，答案数量和问题数量对不上也能提交，模型只收到一个没有标识的数组。

改法：

- 服务端分两种卡定义响应结构：普通问题、岗位选择。
- 岗位选择只接受 `job_choice`，取值必须是卡上给出的选项。
- 普通问题的每个问题有稳定的 ID，答案按 ID 一一对应，数量必须一致。回传给模型时保留对应关系。

### 10. 两处数据问题（[08]、[09]）

- **[08] 删除岗位后，重复导入的旧请求仍能取回**：先用键 A 创建岗位，再用键 B 导入同一份正文，B 存下了 `200` 响应快照，但没有绑定运行。删除岗位只清理绑定了运行的幂等键，所以重发 B 仍然返回完整的旧 JD 和已经不存在的岗位 ID。

  改法：删除事务里，按「用户 + 操作 + 结果 ID」清理对应的成功快照。正常查重和并发查重两条复用路径都要测。
- **[09] 清空已确认教育的就读状态后，整个发布返回 500**：修改接口接受了 `status: null`，草稿却仍是已确认状态。下次发布时转换报错，其他已确认的改动也被一起回滚。

  改法：修改的事务里要保证「已确认就一定能发布」，清空状态时把这一项降回待核对。发布接口遇到已经存在的异常草稿，返回能操作的 422，不再是 500。

### 11. 学历规则不把复合要求整句判成已覆盖（[07]，改变匹配行为）

问题：

- 「本科及以上且必须熟练使用 Python」：只要识别到本科，就接受整句。候选人只有学历证据时，程序会推翻模型给出的「缺口」结论，并清掉技术引用。
- 「本科及以上，计算机相关专业」：专业要求被 `filler_clauses` 当成填充词忽略了。

先问前提对不对：`filler_clauses` 把「相关专业」当填充词，这个前提就不对，因为专业是真实的限制条件。

改法：

- 程序只在把整句的限制条件都识别出来时，才用程序的结论。专业、届别、「提前到岗」、同一句里的技术要求，这些识别不了的剩余部分都标为待核对，保留模型的判断和引用。
- 把「专业」类词从 `filler_clauses` 里移出去，只保留「统招」「全日制」这种确实不影响判断的词。
- 缺口摘要按岗位要求 ID 对齐，不再按「学历」这样的关键词去删另一条要求的缺口。

验证：这一项改变匹配行为，按 06 T2.6 的规定在 E3 **开发集**上验证。

- 先用现有的程序层重算，这一步不花钱。
- 如果必须调模型，先报预计费用，等用户批准后再跑。

运行前把预测写进 `evals/README.md`，结果和取舍也记在那里。行为不变的整理和这次修复分开提交。
