# 任务 U：投递页

日期：2026-11-27。基准：`main` 最新提交（`683017b` 之后）。状态：待实施。

## 背景

任务 T 做完了投递追踪的后端和前端，但投递只能从岗位进去看：

- 想知道「现在有哪些投递在等结果」，要一个个点进岗位详情；
- 工作台看板的「已投递」一列把已投递、笔试、面试、Offer、未通过混在一起，一个岗位一张卡；
- 岗位库按进度筛选，还是一行一个岗位，同一岗位投两次只显示最近那次；
- 已删除岗位的投递藏在岗位库的一个抽屉里。

本任务新增一个**投递页**：一次投递一张卡，按投递阶段分列，在页面上直接改阶段。后端只补一个字段，其余接口沿用任务 T 的。

原型：[`prototype/applications/index.html`](../prototype/applications/index.html)，用浏览器直接打开，右下角「显示实现标注」。原型只定布局、文案和交互，数据是虚构的，实现时用 Ant Design 组件重写。

## 成熟方案对照（2026-11-27 调研）

| | 视图 | 改阶段 | 一张卡是什么 | 没下文怎么办 |
| --- | --- | --- | --- | --- |
| Huntr | 看板，列可增删改名 | 拖动卡片，自动记一条活动 | 一个岗位 | 无专门处理 |
| Teal | 表格，字段点开就改 | 点开状态字段 | 一个岗位，另有「跟进日期」「兴趣程度」 | 用户自己填跟进日期，一般一周后 |
| Simplify | 看板和列表可切换 | 看板拖动；列表下拉；详情里改 | 一个岗位 | 无专门处理 |
| 第三方模板（Obsidian 插件等） | 看板 | 拖动 | 一个岗位 | 加一列「Ghosted（没下文）」 |

本项目的取法：

- **看板和列表两种视图**，同 Simplify。看板看全局，列表方便按日期排序、扫一遍。
- **一张卡是一次投递，不是一个岗位**。这是和上面几个产品不同的地方，原因是任务 T 已经把阶段记在投递上，同一岗位投两次各有阶段。同一岗位有多条时，卡上标「第 N 次投递」。
- **改阶段用菜单加日期，不做拖拽**：
  - 改阶段要带发生日期（任务 T 的阶段记录可补填过去的日期），拖拽没地方填；
  - 拖拽要新增依赖（如 `@dnd-kit`），还要单独处理键盘操作；
  - Simplify 也在列表里提供下拉。
  以后要加拖拽，可以拖完再弹出同一个日期弹层。
- **「没下文」是提示，不是阶段**。阶段表示公司给了什么结果；没下文只是用户这边等了多久，由阶段停留天数推出来，不存。不另加「跟进日期」字段，提醒属于 V2（任务 T「不做的」）。
- **未通过默认收起**。投出去的大多数最后是未通过，一直摆在看板上会盖住还在进行的投递。

来源：[Huntr 看板](https://help.huntr.co/en/articles/10042685-the-job-board)、[Huntr 活动](https://intercom.help/huntr-1d0e8ee7323d/en/articles/10042702-activities)、[Teal 追踪投递](https://help.tealhq.com/en/articles/14435727-how-to-track-your-job-applications)、[Teal 看板字段](https://tealhq.helpscoutdocs.com/article/27-exploring-the-dashboard)、[Simplify 追踪器](https://help.simplify.jobs/en/articles/2140179-using-the-job-tracker)、[Careerflow「Ghosted」需求](https://careerflow.canny.io/feature-suggestions/p/new-board-ghosted)。

## 设计

### 1. 后端：投递列表带上「进入当前阶段的日期」

`GET /api/applications` 的每一条增加 `stage_changed_at: date`，等于这条投递**最后一条阶段记录**的 `occurred_at`。「最后一条」的顺序和 `list_events` 一致（`created_at`、`event_id`），这样它和 `stage` 列始终对应同一条记录。

- 在 `list_applications` 的同一次查询里算出来（`DISTINCT ON (application_id)` 子查询再连接，或者用窗口函数），不对每条投递单独查，也**不加列**（CLAUDE.md：能推导的状态不单独存）。
- 用一个新的输出模型 `ApplicationListItem(ApplicationOut)` 只加这一个字段。创建、更新接口仍返回 `ApplicationOut`，前端写入后会重新读取列表，不需要它们也带这个字段。
- 带 `job_id` 和不带 `job_id` 都返回这个字段，前端类型统一。

### 2. 路由与导航

- 新路由 `/applications`。侧栏在「岗位库」和「我的」之间加「投递」，图标用 `@ant-design/icons` 里现成的（如 `SendOutlined`）。
- `/applications?id=<application_id>` 直接打开这条投递的详情抽屉，给其他页面链接用。id 不存在或不属于当前用户时，提示「这条投递不存在或已删除」，并去掉参数。

### 3. 页面结构

从上到下：

1. **标题**（宋体，方向 D）、一句说明，以及唯一的主按钮「记录投递」。
2. **汇总条**：共几次投递、几条在等结果（阶段为已投递、笔试、面试）、其中几条超过 14 天没有进展、几个 Offer。数字用等宽数字。不放转化率，统计属于 V2。
3. **工具条**：
   - 「看板 / 列表」切换（`Segmented`）；
   - 按岗位名或公司搜索；
   - 「显示未通过」开关；
   - 右侧一行灰字说明「超过 14 天没有新进展的会标出来」。
   视图和开关的选择记在 URL 参数里（`?view=list&rejected=1`），刷新后保留，不用 `localStorage`。
4. **看板**：已投递、笔试、面试、Offer 四列，打开「显示未通过」后多一列。列内按 `stage_changed_at` 倒序。未通过收起时，看板下方写「另有 N 条未通过，显示」。
5. **列表**：列为岗位（岗位名和公司）、阶段（下拉）、投递日期、渠道、简历版本、最近变动、标记。可按投递日期或最近变动排序，默认按最近变动。窄屏时表格横向滚动。

空状态：

- 一条投递都没有：「还没有投递记录。在岗位详情点『记录投递』，或在对话里说『我投了』。」
- 搜索没有结果：「没有匹配的投递。」
- 看板空列：「已投递」列写进入方法，其余列写「暂时没有」。

### 4. 卡片

一张卡对应一次投递：

- **岗位名和公司**取 `job_snapshot_json`，也就是投递时的信息。岗位之后改名不影响已经投出去的那份。
- **小块元信息**（`MetaList`）：投递日期、渠道、第 N 版简历。
- **标记**，可以同时出现几个：
  - 「N 天没有进展」，琥珀色。条件是阶段为已投递、笔试或面试，且今天距 `stage_changed_at` **超过** 14 天；
  - 「岗位已删除」：`user_job_id` 为空；
  - 「第 N 次投递」：同一 `user_job_id` 有多条时，按 `applied_at`、`created_at` 正序编号；
  - 「迁移前记录」：`backfilled`。
- 没有任何标记时，显示「本阶段 N 天」。
- 右下角「改阶段 ▾」，见第 5 节。
- 点卡片或在卡片上按 Enter 打开详情抽屉，卡片可以用 Tab 聚焦。

14 天写成一个有名字的常量（如 `STALE_AFTER_DAYS`），放在 `labels.ts` 或新的 `applicationStatus.ts`，判断写成纯函数，单测覆盖。

天数计算：`applied_at`、`stage_changed_at` 是日期字符串，和「今天的本地日期」都按日期比较，不要用 `new Date('2026-11-20')`，它按 UTC 解析，在东八区早上会差一天。项目没有直接依赖 `dayjs`，不要为这个引入，写一个小的日期差函数并单测。

### 5. 改阶段

- **卡片上**：点「改阶段」弹出 `Popover`，里面是目标阶段（排除当前阶段）、发生日期（默认今天，不能晚于今天），以及「改阶段」按钮。
- **列表里**：阶段下拉选了新值后，弹出同一个弹层，只填日期；取消就恢复原值。
- **抽屉里**：沿用现成的「编辑投递」弹窗。
- 三处都调用 `PUT /api/applications/{id}`，带 `expected_revision`。成功后刷新投递、岗位和工作台的查询（复用 `useRefreshApplications`）。409 时提示「投递记录刚被别处改过，已重新读取」，并重新读取，和现有写法一致。
- 改阶段的弹层抽成一个组件，三处共用，不写三遍。

### 6. 详情抽屉

右侧 `Drawer`：

- 标题是岗位名，副标题是公司和地点；岗位还在时加「打开岗位详情」链接。
- 内容直接复用岗位详情里的投递行：阶段记录、查看当时的简历、和现在对比、编辑投递、删除投递。
- 已删除岗位和补录记录的说明文字沿用任务 T。

投递行现在只有 `user_job_id` 为空时才显示岗位名。抽屉标题已经有岗位名，所以给它加一个属性控制是否显示岗位信息，不要复制一份改。

### 7. 记录投递

主按钮「记录投递」打开一个两步弹窗：

1. 先选岗位。只列有定制简历的岗位，按最近更新排序，可以搜索；
2. 选好后进入现成的 `NewApplicationModal`。

没有任何定制简历时，按钮仍可点，弹窗里说明「先在对话里为一个岗位生成定制简历，才能记录投递」，并给出「去岗位库」的链接。

### 8. 和其他页面串起来

- **工作台**：看板「已投递」列标题旁加「查看全部投递」，链接到 `/applications`。看板本身仍按岗位，不改。
- **岗位库**：删掉「已删除岗位的投递」按钮和 `DetachedApplicationsDrawer`。投递页已经包含这些投递（带「岗位已删除」标记），留着就是两处入口。如果之后真需要筛选，可以在投递页工具条里加「只看已删除岗位」。
- **岗位详情**：「投递记录」卡片标题旁加「在投递页查看」，链接到 `/applications`。
- **对话**：`record_application` 的结果行在「查看岗位」后面加「在投递页查看」，链接到 `/applications?id=<id>`。如果结果里拿不到投递 ID，就只链接 `/applications`，不为这个改后端。

### 9. 窄屏（< 992px）

- 看板改成按阶段从上到下排列的分组，每组就是原来的一列；
- 列表可横向滚动，抽屉占满宽度；
- 1440×900 和 375×844 都不能出现整页横向滚动。

## 验收

改规则或判断前，先写一个会失败的测试，再写实现；关键判断要做变异检查。

1. **后端**：
   - `stage_changed_at` 等于最后一条阶段记录的 `occurred_at`。补填一个更早的发生日期后，取的仍是最后追加的那条，不是日期最大的那条；
   - 带不带 `job_id` 都有这个字段；
   - 列表查询的条数不随投递数增长：用 SQL 计数，或断言只执行一次查询；
   - 隔离测试不变，并通过；全量 `uv run pytest -q`、`ruff check`、`ruff format --check .` 通过。
2. **前端单测**：
   - 「没进展」判断：恰好 14 天不标，15 天标；未通过和 Offer 不标；
   - 日期差函数：跨月和跨年都对，不受时区影响；
   - 「第 N 次投递」的编号；
   - 看板分列、列内排序、未通过收起后的计数和「显示」；
   - 列表排序切换；
   - 改阶段：卡片弹层、列表下拉取消后恢复原值、409 后重新读取；
   - `?id=` 打开抽屉，id 不存在时提示；
   - 记录投递两步弹窗，以及没有定制简历时的说明；
   - 岗位库不再有「已删除岗位的投递」。
3. **变异检查**，至少三项要被测试抓到：
   - 「超过」改成「不少于」；
   - 列内排序改成按 `applied_at`；
   - 「第 N 次投递」改成倒序编号。
4. **浏览器实测**（合成账号、独立测试库、假上游，不花模型费用）：
   1. 准备 6 条以上的投递，包括同一岗位两次、已删除岗位、补录、一条 20 天前的已投递；
   2. 在看板改阶段，补填日期，确认阶段记录；
   3. 切到列表，用下拉改阶段，再取消一次；
   4. 打开抽屉，查看当时的简历和对比；
   5. 从工作台、岗位详情和对话结果行跳进来。
   1440×900 和 375×844 各截一组图，检查没有横向溢出。
5. `pnpm --dir web format:check`、`lint`、`test`、`build` 通过。

## 不做的

- 拖拽改阶段（理由见「成熟方案对照」）；
- 跟进日期、提醒、兴趣程度、投递统计和转化率（V2）；
- 自定义看板列，把「没下文」做成阶段；
- 在对话里改阶段的工具（任务 T 已定 V1 不做）；
- 批量操作（批量改阶段、批量删除）；
- 工作台看板改成按投递显示（工作台看的是岗位从未匹配到已投递的整条流程，和投递页分工不同）。
