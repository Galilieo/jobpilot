# 任务 P：对话页前端（T4.1 对话部分）

日期：2026-11-26。基准：`main` 最新提交。

## 背景

对话 Agent 的后端已经由任务 N 完成，第二轮评审的修正也由任务 O 完成：
- 对话、消息、确认卡、撤销都有了；

- 消息按 `client_message_id` 去重；

本任务**只改 `web/`**。和它并行的任务 Q（长期记忆与上下文，后端）只改 `jobpilot/`，两边互不碰对方的文件。

## 要做的

### 1. 侧栏与对话列表

- 「最近对话」接 `GET /api/conversations`。有当前岗位的对话和普通对话用不同的图标，用 Ant Design X 的 `Conversations` 组件。
- 「＋ 新对话」打开欢迎页。用户发出第一条消息时，先 `POST /api/conversations` 建对话，再发消息，然后跳到 `/conversations/:id`。不在点按钮时就建空对话。
- 支持重命名和删除。删除时，运行中的对话后端会返回 409，要显示原因。

### 2. 消息与流式输出

- 消息列表用 `Bubble.List`，渲染详情里 `messages` 的内容。工具步骤（`steps_json`）用 `ThoughtChain` 做成一行可折叠的进度，例如「✓ 已完成 4 步」，展开后显示每一步的工具名和简短结果。
- 发消息用 `fetch` 加 `ReadableStream` 读 SSE。浏览器自带的 `EventSource` 只支持 GET，这里用不了。不另外加状态库。
- 需要处理的事件：`text`、`tool_start`、`tool_end`、`confirm`、`done`、`error`。
  - 事件名和数据形状以后端代码为准，在 `web/src/api/` 写一个小的解析函数，并给它写单元测试。
  - 一个数据块可能被拆成几段，也可能一次到好几个事件，都要处理。
- **去重和冲突**：
  - 每次发送生成一个 `client_message_id`（`crypto.randomUUID()`）。网络错误时，用同一个 ID 重试。
  - 收到 409 时，把「这条消息没有保存」告诉用户，并把输入框里的文字还给用户。然后显示返回的当前运行和待确认卡。
- **断线和刷新**：
  - 流断了，或者页面刷新了，就重新读一次详情接口。
  - `run.status` 还是活跃状态，或者 `confirmation_status` 是 `decision_saved` / `recovering` 时，每隔 2 秒左右轮询一次详情，直到运行结束。
  - 轮询的间隔和上限写成命名常量。
- **不做「停止生成」**：后端没有取消接口。客户端断开时，后端的运行照常完成。界面上不显示停止按钮，在回报里记下这个缺口。

### 3. 确认卡与提问卡

- **写入确认卡**（`kind: 'confirmation'`）：
  - 按 `tool` 分别渲染。`set_current_job` 显示「把当前岗位设为 X」；`edit_resume_item` 显示改前、改后两段文字，以及依据检查的结论。
  - 认不出的工具，用一个通用的兜底渲染：显示工具名，参数按键值对列出。以后加的工具（比如记忆）就算没有专门的渲染，也能确认。
  - 「确认」「拒绝」两个按钮调用 `POST /api/conversations/{id}/actions/{action_id}`。请求体只有决定本身，不带参数。按钮点下后立即禁用，防止重复点击。
  - 返回的仍是 SSE，处理方式和发消息一样。
- **提问卡**（`kind: 'question'`）：
  - `questions` 类型：每个问题一个输入框，再加一个「先跳过」。按 `question_id` 交答案，答案数量要和问题数量一致。
  - `job_choice` 类型：显示三个按钮，「新开对话」「切换到新岗位」「保持不变」，提交时只带 `job_choice`。
- **决定之后**：卡片变成一行结果文字。已执行的写入在结果旁边显示「撤销」，调用 `POST /api/actions/{action_id}/undo`。撤销返回 409 时，显示原因，比如「之后又改过，不能撤销」。
- **以详情为准**：卡片状态以详情接口里的 `pending_action`、`latest_decided_action`、`confirmation_status` 为准，不靠前端自己猜。

### 4. 当前岗位

- 标题旁边放一个岗位标签，点开是下拉菜单：查看当前岗位、换成岗位库里的别的岗位、解除关联。用的是 `PUT /api/conversations/{id}` 的 `current_job_id`。
- 关联、切换、解除时，在对话里显示一行居中的灰色提示（07 第 5.1 节）。

### 5. 输入框与附件

- 用 `Sender`。Enter 发送，Shift + Enter 换行。
- 附件复用 `TextSourceInput` 和 `POST /api/extract-text`（任务 G 已经做好），先提取出文字，再作为 `attachments` 的文字发出去。最多 5 个附件，超过总长度上限时，把后端 422 的提示显示出来。
- 欢迎页按 07 放四个入口建议，点击后把对应的文字填进输入框。

### 6. 右侧产物面板

- 按 07 第 5.2 节的规则决定显示哪些标签，没有内容时不显示面板。
- **简历**：用 `iframe` 嵌入 `/api/tailor-runs/{run_id}/preview`，沿用现有的编辑器和保存逻辑。`run_id` 按当前岗位取最新的定制简历，接口是 `GET /api/tailored-resumes`。
- **匹配报告、岗位**：复用岗位详情页已有的组件。确实需要抽成公共组件的，先单独做一个「行为不变的整理」提交，再接到面板上。
- 「事实库变化」标签不做，记为留尾。
- 窄屏（小于 992px）按 07 第 6 节处理：侧栏变成抽屉，面板通过「查看结果」按钮打开。

## 验收

- **单元测试**（Vitest），覆盖这些情况：
  - SSE 解析：数据块被拆开、一次多个事件、未知事件；
  - 409 时把文字还给用户；
  - 网络重试用同一个 `client_message_id`；
  - 确认按钮点一次就禁用；
  - 提问卡的答案和问题一一对应；
  - 不认识的工具用兜底渲染；
  - 轮询在终态时停止。

  每一项先写会失败的测试，再做变异检查。
- **浏览器实测**：用本地开发服务器加合成资料（`evals/datasets/` 下的合成简历和 JD），不用真实简历。走完这几步，每一步截图：
  - 发 JD → 岗位被设为当前岗位并显示提示；
  - 匹配；
  - 生成定制简历，面板显示出简历；
  - 改一条简历条目 → 出确认卡 → 确认 → 撤销；
  - 刷新页面，状态能恢复；
  - 窄屏布局。

  实测会调用真实模型，先报预计费用（参考任务 N：一次完整流程约 3 万 token），等用户批准后再跑。
- `pnpm --dir web format:check`、`lint`、`test`、`build` 都要通过。
