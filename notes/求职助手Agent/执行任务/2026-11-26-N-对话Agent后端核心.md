# 任务 N：对话 Agent 后端核心（T3.1～T3.3）

日期：2026-11-26。基准：`main` 最新提交。前置：任务 L、M 已完成；统一评测批次延后（`06` T2.6 2026-11-26 再调整），本任务**不改**匹配、改写、依据检查的行为。

## 背景

V1 的入口是对话（00 第 1.4、1.5 节，02 第 2.2 节，决定 22）：每条用户消息触发一次 Agent 运行，读取和生成类工具自动执行，写入类工具先出确认卡、用户确认后才执行，执行后可以撤销。第 1～2 周把能力做成了服务（解析、匹配、改写、组装导出），这一步把它们接成对话。

本任务只做后端：表、Agent 图、第一批工具、确认与撤销、SSE。长期记忆、投递记录和前端对话页放在后面的任务（O）。

## 成熟方案对照（2026-11-26 调研，设计已据此定下）

| 问题 | 参考 | 本项目的做法 |
| --- | --- | --- |
| 暂停等确认后恢复，节点会不会重跑 | [LangGraph interrupts 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)：`Command(resume=...)` 恢复时**被中断的节点从头重跑**，`interrupt()` 之前的副作用必须幂等；社区建议把确认放在单独节点 | 确认拆成三个节点：`propose_action` 写待确认的 `agent_action`（按 `(run_id, tool_call_id)` 唯一，重跑不会多写一行）→ `await_confirmation` 只调 `interrupt()`，没有别的副作用 → `apply_action` 执行 |
| 审批粒度和恢复方式 | [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/human_in_the_loop)：工具声明 `needs_approval`，待批的调用作为 interruption 返回，批完把同一份 RunState 交回继续 | 工具在注册表里声明类别（读取 / 生成 / 写入 / 提问），由类别决定要不要确认，模型改不了；恢复用同一个 `thread_id` |
| 客户端伪造审批 | [Vercel AI SDK tool approvals](https://ai-sdk.dev/docs/agents/tool-approvals) 提醒：不做服务端校验，客户端可以伪造一份「已批准」绕过人工 | 决定接口只收 `action_id` 和「确认 / 拒绝」，执行用的参数从数据库里的 `agent_action.args_json` 取，不接受客户端传参；校验动作属于本人、本对话、状态仍为 pending |
| 断线后怎么接上 | Vercel / TanStack / Ably 的 resumable streams：事件带序号持久化，重连从断点重放 | V1 不做逐字重放：运行由后端进程执行（决定 4），断线不取消；每个工具步骤和最终回复写进 `message`，重开对话读消息和运行状态，运行中就轮询（和现有改写运行一样）。逐字续传记为 P1 |
| 模型调用封装 | 各框架自带模型封装 | 决定 9 不变：不用 LangChain 模型封装，LangGraph 只负责图、检查点和 `interrupt()`；工具调用和流式输出加进自己的网关 |

## 设计（已定）

### 表与接口（T3.1）

- 迁移：`conversation`、`message`、`agent_action`，`ai_run.conversation_id` 关联列和外键（组合外键保证同一用户，决定 29）。`memory`、`application` 不在本任务。
- `agent_action.status` 只允许 02 列出的六个值；`(run_id, tool_call_id)` 唯一。同一对话同时只能有一个 running 或 waiting_confirmation 的 agent 运行（条件唯一索引，06 T3.1 的 2026-11-24 决定）。
- 接口按 02 第 6 节：对话列表、新建、获取（含消息）、改标题和当前岗位、删除；`POST /api/conversations/{id}/messages`；`POST /api/conversations/{id}/actions/{action_id}`；`POST /api/actions/{action_id}/undo`。全部登记进隔离测试；新表进账号导出清单。

### 网关扩展

- `request_completion` 支持 `tools` 和流式输出（或新增一个同级函数，共用发送、遮蔽、额度扣减、`model_call` 记录，不复制）。
- 工具结果回到模型时按不可信数据包装（里面有简历和 JD 原文），发送前同样遮蔽联系方式。
- 用途 `ModelPurpose.AGENT`，提示词 `prompts/agent.txt`，版本规则照旧。

### Agent 图（T3.2）

```text
build_context → call_model ──没有工具调用──▶ finish
                    │
                    ├─ 读取 / 生成 ──▶ execute_tools ──▶ call_model
                    ├─ 写入 ──▶ propose_action ──▶ await_confirmation ──▶ apply_action ──▶ call_model
                    └─ 提问 ──▶ ask_user（interrupt，回答作为工具结果）──▶ call_model
```

- `build_context`：本任务只放最近 N 轮（配置项，初值 10 轮、8,000 token，决定 30）和当前岗位摘要；记忆在任务 O。
- 一次模型回复里有多个写入调用时，一次只出一张卡，处理完一个再出下一个；同一轮的提问合并成一张卡（决定 26）。
- 每次运行的预算：工具调用次数、token、时长上限（配置项）。用完就停，并告诉用户做到了哪一步。等待确认期间重启，不重置本轮剩下的预算（合并条件）。
- 检查点：`AsyncPostgresSaver`，`thread_id = {user_id}:{conversation_id}`，恢复前校验运行和对话归属。删号彻底删除前按 `thread_id` 清掉检查点（合并条件，`services/accounts.py` 那条注释）。

### 第一批工具

| 类别 | 工具 | 说明 |
| --- | --- | --- |
| 读取 | `list_jobs`、`read_job`、`read_facts`、`read_match_report`、`read_resume` | 调用现有查询，只能读本人的 |
| 生成 | `parse_jd`、`match_job`、`tailor_resume` | 调用现有服务，产生新结果，不覆盖旧的；依据检查在服务里强制执行 |
| 写入 | `set_current_job`、`edit_resume_item` | 必须确认。`edit_resume_item` 绑定出卡时的 `base_version_id`，确认时版本已变就 409；检查结果只提示、不阻止确认（02 第 2.2 节）；撤销 = 恢复到修改前的版本（新建一个版本，不删历史） |
| 提问 | `ask_user` | 一轮最多一张卡 |

`propose_fact`、`remember`、`record_application` 和删除类工具放到任务 O。

### SSE（T3.3）

`POST .../messages` 和 `POST .../actions/{action_id}` 返回 SSE：`text`、`tool_start`、`tool_end`、`confirm`、`done`、`error`。运行交给 `Launcher`，SSE 只是旁听，客户端断开不影响运行。

## 验收（照 06 T3.2、T3.3，假模型为主）

- 写入类工具没确认之前，任何数据都没变；拒绝后不执行；撤销后回到原状态；双击确认只执行一次；业务已提交、检查点还没前进时重启，再确认也只执行一次。
- 用 A 的工具读写 B 的岗位、事实、运行和简历版本，包括在参数里嵌套 B 的 ID，B 的数据都不变。
- 真实 Postgres 检查点：暂停后新建一个图实例，覆盖拒绝、确认、双击确认；停在确认卡时重启，原卡仍在等待，确认后继续。
- 收到第一个工具事件后断开客户端，后端照常完成；重开对话能看到结果，业务写入只有一次。
- 预算：对话只剩一次模型调用时启动改写，改写子图再想调用会被停下，本轮只扣一次。
- 待删除账号调新接口返回 403；新表出现在账号导出里。
