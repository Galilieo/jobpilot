# 任务 Z：跨对话搜索（V1 的 RAG）

日期：2026-11-28。基准：[任务 Y](./2026-11-28-Y-长期记忆重设计.md) 完成后的 `main`。状态：程序验收与 E13 检索对照完成。

## 背景

- V1 目前没有用到 RAG。pgvector 扩展已启用、Python 依赖也装了，但没有任何表有向量列，也没有代码调用 Embedding。
- `read_conversation_history` 只能查**当前对话**（按序号范围，或者对关键词做不区分大小写的子串匹配）。用户问「上次聊字节那个岗位时我说了什么」，Agent 查不到。
- 全部对话都在 `message` 表里（用户消息、附件、工具步骤、Agent 回复），所以不需要新的数据来源，缺的是让它们能被搜到。
- 这正好是任务 Y 三层记忆里「按需提取」那一层：常驻记忆只放短的偏好，其他对话里说过的细节要用时再找。

为什么 RAG 放在这里而不是别处（2026-11-28 讨论）：

| 位置 | 是否需要检索 | 结论 |
| --- | --- | --- |
| 跨对话搜索 | 需要：对话会越来越多，放不进上下文；数据现成；可以标注评测 | **V1 做** |
| 长期记忆 | 不需要：约 1,500 字符，全部注入更可靠，检索会漏 | 不做（任务 Y） |
| 改写时检索事实 | 不需要：一份简历几十条事实，全部给模型 | 不做 |
| 岗位推荐、面经知识库 | 需要，但岗位量和面经资料要到 V2 才有 | V2 |

## 设计

### 1. 索引什么

| 内容 | 是否索引 | 理由 |
| --- | --- | --- |
| 用户消息正文 | 是 | 主要的查找对象 |
| Agent 最终回复 | 是 | 「你上次建议我……」 |
| 工具步骤、工具结果 | 否 | 程序输出，权威数据另有读取工具 |
| 附件（简历、JD 文本） | 否 | 已在事实库、岗位库；JD 是不可信内容，会让结果被 JD 原文占满 |
| 少于 4 个字符的消息（「好的」「可以」） | 否 | 没有检索价值 |

### 2. 切块与存储

- 一条消息一块；超过 `CHUNK_MAX_CHARS = 500` 字的按段落切，段落仍过长再按句切，块之间不重叠。
- 新表 `message_chunk`：`chunk_id`、`message_id`、`conversation_id`、`user_id`、`chunk_no`、`span_start`、`span_end`、`content`、`embedding vector(1024)`（可空，空表示待计算）、`embedding_model`、`created_at`。
  - 组合外键指向同一用户的 `message`，`ON DELETE CASCADE`：删对话、删账号时一起删。
  - 存 `content` 副本，供关键词检索和返回片段；`span` 用于定位回原文。
- 向量是派生数据，**不进账号导出**。
- 先不建 HNSW 索引：每个用户的数据量小，按 `user_id` 过滤后精确计算余弦距离（02 第 10 节的说明）。E13 里记录耗时，消息量上来再加索引。

### 3. Embedding

- 沿用决定 18：本机 Ollama `bge-m3`（1024 维），用 `httpx` 调 `POST /api/embed`。配置 `OLLAMA_BASE_URL`、`EMBEDDING_MODEL`，写进 `.env.example`。
- 文本不出本机，不经过模型网关的脱敏与计费；调用耗时写结构化日志。
- 每块记录 `embedding_model`（R4），换模型时按它重算。

### 4. 什么时候算

- 运行结束、消息落库后，起一个后台任务给新消息切块并计算向量；失败只记日志，`embedding` 留空。
- `uv run python -m jobpilot.scripts.embed_messages` 补算全部待计算的块（首次上线用来处理已有的 91 条消息，以后 Ollama 停掉过也用它补）。
- 搜索从不等待计算：没有向量的块只参与关键词检索。

### 5. 搜索工具 `search_conversations`

- 类别：读取，自动执行。
- 参数：`query`（1～120 字）、`limit`（1～8，默认 5）。
- 范围：本人的**其他**对话（当前对话用 `read_conversation_history`），用户 ID 来自登录态。
- 返回：每条结果包含对话标题、`conversation_id`、消息序号、角色、日期、片段（块内容，过长截到 300 字）、来源方式（向量 / 关键词 / 两者）。整体按不可信数据包装，因为 Agent 的旧回复里可能引用过 JD 原文。
- Ollama 不可用时退回关键词检索，结果带 `degraded: true`，Agent 应告诉用户结果可能不全。
- `read_conversation_history` 增加可选的 `conversation_id`（只能是本人的对话），Agent 找到片段后可以读前后文。
- 什么时候用（写进工具说明）：用户提到以前的对话（「上次」「之前说过」），或者需要的信息不在记忆、事实库、岗位库里。引用时注明出处「（来自《对话标题》）」。

### 6. 检索方式与对照实验

| 方案 | 做法 |
| --- | --- |
| A 向量（基线） | 查询向量与块向量的余弦距离，取前 k |
| B 关键词 | jieba 分词后存 `tsvector`（`simple` 配置），`websearch_to_tsquery` 检索，按 `ts_rank` 排序 |
| C 融合 | A、B 各取前 20，RRF（k=60）合并 |

- 先实现 A；B 引入新依赖 `jieba`，单独提交。
- 用 E13 开发集比较三种，**明显更好才保留更复杂的方案**（R2 的原则）。「明显」的标准在运行前写进预期。
- 不做重排序、查询改写、结果摘要（02 第 9.3 节）。

### 7. 界面

工具步骤展开后显示查询词和命中列表，每条可以跳转到对应对话的那条消息。不另做搜索页。

## 验收

### 程序测试

- 索引范围：工具消息、附件、短消息不切块；长消息切块的 `span` 能还原原文。
- 隔离：用户 A 搜不到用户 B 的内容；`read_conversation_history` 传别人的 `conversation_id` 返回 404；加入 `test_isolation.py` 遍历清单。
- 删除：删对话、删账号后块一起消失。
- 降级：Embedding 服务不可用时消息照常落库，搜索返回关键词结果并标 `degraded`。
- 补算脚本幂等：重复运行不重复切块、不重复计算。
- 单元测试用假的 Embedding（固定向量），不依赖 Ollama。
- 变异检查：至少改坏「用户过滤」「排除当前对话」「不索引附件」三处。

### E13 跨对话检索（新增评测）

- **数据**：合成 30 段求职对话（每段 6～20 轮，涉及不同公司、岗位、偏好、简历修改），由执行会话构造，用户抽查 10 段。
  - 2026-11-28 补充（第一版被退回：600 条消息只有 123 种不同文字，8 句话在 30 段里一字不差地重复，Agent 的回复和上一句对不上）：
    - **逐段单独写，不用模板拼接。** 校验脚本加一条：任何一条消息的文字（去掉空白后）出现在两段以上对话里就报错。
    - **像真实的 JobPilot 对话**：贴 JD 片段、问匹配、讨论匹配报告、改简历条目、说偏好、准备面试；Agent 的回复要接着上一句说，长短不一，可以提到工具结果（「我看了匹配报告……」）。轮数在 6～20 之间变化，不要每段一样长。
    - **干扰项要有意设计**：安排几组主题相近的对话（例如两个 Agent 岗位、两个实时数仓岗位），让「换说法」的查询必须分辨是哪一段，而不是靠模板句意外重复制造干扰。
    - 查询也要覆盖 Agent 的回复（「你上次建议我怎么写那段压测？」），允许一条查询有多条相关消息。
  - 2026-11-28 第二版的对话和标注已获抽查确认。首次运行前改用 `e13-v3`，补足真实长度的 Agent 回复、30 则多段长回复和 10 则贴入正文的 JD，并校验换说法查询与原消息、实际分块的字符二元组排名。每个切分的无答案查询各含 3 条未提及数字和 3 条未聊过话题。
- **查询**：60 条，开发、测试各 30，每条标注应找到的消息。类型：
  - 原词（公司名、技术名）；
  - 换说法（「那家做大模型的公司」）；
  - 只记得大意（「我们讨论过要不要写实习时长」）；
  - 无答案（库里没有）。
- **指标**：Recall@5、MRR；无答案查询的最高分分布（用来决定要不要设阈值）；每次搜索耗时。
- **对照**：A、B、C 三种。
- **端到端**（2026-11-28 移到[任务 AB](./2026-11-28-AB-Agent行为评测批次.md)）：Agent 该搜时是否调用、不该搜时是否不调用、引用是否带出处。本任务的合成对话要能被 AB 复用为起始状态。
- 预期在首次运行前写进 `evals/README.md`；只在开发集上调；测试集只跑一次。
