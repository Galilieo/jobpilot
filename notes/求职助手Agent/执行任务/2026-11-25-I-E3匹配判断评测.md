## 背景

T2.6 还差 E3 和 E5，第 2 周的完成标准要求「E5 五个版本都有结果」。E3 量的是匹配判断准不准：每条岗位要求，系统判「已覆盖 / 部分覆盖 / 未覆盖」和人工标注一致的比例，以及「已覆盖」时引用的依据对不对。定义见 [04 E3](../04-评测方案.md#e3-匹配判断v1)。

E5 是对外公开的编造率基准，只能用合成数据；E3 和 E5 用同一批 50 组，所以 E3 也全部用合成数据。

## 设计（已定）

- **只测匹配这一步。** 事实、求职条件、教育直接取 E1 标注（标准答案），不跑抽取；岗位要求直接取 JD 标注，不跑 JD 解析。这样 E3 的分数不混入 E1、E2 的误差，样本 ID 也是固定的（评审要求「先冻结事实、条件与 JD 要求的样本 ID」）。
- **10 份简历 × 5 份 JD = 50 组，按简历分开发集和测试集。** 简历沿用 E1 的分组：从 E1 开发集挑 5 份组成 E3 开发集（25 组），从 E1 测试集挑 5 份组成 E3 测试集（25 组）。挑的时候让方向（AI 应用、后端、算法、前端）、短样本和完整简历、单段和多段教育都有。分组写进 `evals/datasets/e3-split.json`，在跑模型之前提交。
- **5 份合成 JD**，放 `evals/datasets/jds/jd-syn-01.txt`～`jd-syn-05.txt`，公司名虚构。参照 `evals/README.md`「真实 JD 样本」的分布写，但不抄任何真实 JD 的句子。五份分别偏：AI 应用 / Agent 实习、后端实习、算法实习、前端实习、校招 AI 应用。合起来要覆盖：每周到岗天数、实习时长（含范围）、学历硬性加优先（「本科及以上，硕士优先」）、「硕士在读」类就读状态、复合句、只写在加分项里的技术。每份 6～12 条要求，硬性和加分都有。
- **JD 标注**按 E2 的格式（`evals/README.md`「E2 JD 标注」），放 `evals/datasets/annotations/jd-syn-0N.json`，每条要求加固定的 `requirement_id`（如 `jd-syn-01-r03`）。

## 要做的

### 1. 数据集（一个提交）

- 5 份合成 JD 原文和标注；`e3-split.json`。
- 标注自检测试（加进 `jobpilot/tests/test_eval_annotations.py` 或同级新文件）：每份 JD 标注的要求 ID 唯一、`source_quote` 在原文里能找到；分组里的简历都有 E1 标注；开发集和测试集不重叠。

### 2. 标注规则和开发集标注（一个提交）

- 在 `evals/README.md` 新增「E3 匹配判断」一节，写清规则，至少回答：
  - 「部分覆盖」和「已覆盖」的界线（例如要求「熟悉 TypeScript」、事实只写了「用 Vue 3 开发」，算什么）；
  - 复合要求（「具备 JavaScript、HTML、CSS 基础，有 Vue 3 或 React 项目经验」）按整句判，还是要求里每一项都满足才算覆盖；
  - 依据怎么写：事实用 E1 标注里的下标，求职条件和教育用 `criteria.onsite_days_per_week`、`education.<下标>`；「已覆盖」「部分覆盖」至少一条依据，「未覆盖」不写依据；
  - 「表达缺口」不标注（E1 的事实都来自简历，由程序派生，单元测试保证）。
- 格式：`evals/datasets/e3/labels-dev.jsonl`，每行一条：`{"pair_id", "resume_id", "jd_id", "requirement_id", "verdict", "evidence": [...], "note"}`。
- **在对这些组合跑任何模型之前**标完开发集 25 组并提交。
- 标完请用户抽查 3 组（像 E1 那样），口径确认后再标测试集。抽查材料做成一页：每组列要求原文、你的判断和依据原文，把拿不准的条目标出来放前面，用户只需要回答「同意 / 不同意，应该是……」。等用户回复期间先做第 4、5 项里不调模型的部分（材料、脚本、预测）。

### 3. 测试集标注封存（单独一个提交）

- 按同样的规则标完测试集 25 组，**在跑任何模型之前**单独提交；提交号写进 `evals/README.md`，之后不再修改。

### 4. 第二人标注材料

04 要求抽 50 条请第二个人标注，算两人一致率；人和人都不一致，说明标注标准要改。这一步要用户找人，执行者做不了，只准备材料：

- 从开发集和测试集分层抽 50 条（三种判断、硬性和加分、程序判定和模型判定都有），生成一份给人看的表：要求原文、这份简历的事实和求职条件、空的判断栏；**不放第一份标注，也不放模型输出**。放 `evals/datasets/e3/second-annotator-sheet.csv`（全是合成数据，可以提交）和对应的 `second-annotator-key.jsonl`（50 条的 ID 列表）。
- 写好计算脚本：用户把填好的表放回 `evals/private/e3-second-annotator.csv` 后，一条命令算出一致率和 Cohen's kappa（扣除随机碰巧一致之后的一致程度），列出不一致的条目。
- 第二人标注没回来之前，E3 的结果照常报告，注明「标注一致性待测」。第二人标注不阻塞本任务，也不阻塞任务 J。

### 5. 运行脚本和预测（一个提交）

- `evals/runners/e3_match.py`：对每组用 E1 标注造出事实库、用 JD 标注造出岗位快照，调用现有的 `match_job`（不要另写匹配逻辑）；`--split dev|test`、`--runs N`；每次运行记录评测集版本、代码提交号、模型名、提示词版本、参数（和 E1、E4 一样）。
- `evals/runners/e3_score.py`：指标——
  - 三分类一致率，混淆矩阵；按硬性 / 加分、按程序判定 / 模型判定分别统计；
  - 「已覆盖」的依据：命中率（引用的依据里至少一条在标注依据中）和多引率（引用了标注依据以外的事实）；
  - 每次运行之间结论不一致的条目数（稳定性）。
- **运行前**在 `evals/README.md` 写预测（04 第 1.2 节：E3 的预期在首次运行前补写）。参考：程序判定的求职条件和教育应接近 100%；模型判定部分三分类一致率的预期、依据命中率的预期，写下数字和理由。

### 6. 开发集运行、调整、测试集运行（一个提交记录结果）

- 开发集每组跑 3 次，按指标看错在哪类。要改匹配提示词（`match_job.txt`）或规则，就在开发集上改、版本号加 1、重跑开发集，每轮结果和改动写进 `evals/README.md`。
- 满意后测试集每组跑 3 次，只跑这一轮，结果如实记录，不在测试集上调。
- 报告放 `evals/reports/e3-*.md`：总表、混淆矩阵、失败案例（每类挑 2～3 个，写明原因：标注口径、模型判断、程序规则）、和预测的对照。
- `06` T2.6 的 E3 一行记完成情况；`04` E3 一节补上实际规模和指标定义的调整（如果有）。
