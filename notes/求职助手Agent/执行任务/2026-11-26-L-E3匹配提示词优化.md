# 任务 L：匹配提示词 v3——收紧「部分覆盖」和依据引用

日期：2026-11-26。基准：`main` 最新提交（任务 I 已完成，`c2ffc2d`）。

## 背景

E3 第一轮（`match_job@2`）总一致率开发集 92.2%、测试集 87.8%，看着不低，但大头是容易判的「未覆盖」。按开发集的混淆矩阵看模型判定部分：

- 模型判「部分覆盖」59 次，只有 20 次标注也是部分覆盖，**33 次标注是未覆盖**——相关但不对口的经历被算成了部分证据（离线检索评测 → 接口自动化测试，FastAPI → Spring Boot 或 Go，技能栏列名 + 测试环境跑过场景 → 写过接口自动化）。
- 「已覆盖」引用依据时 36% 多引了标注以外的事实。

这不只是评测分数：改写计划（`services/tailoring_plan.py` 第 216 行附近）会突出引用了事实的要求，部分覆盖也算。误判的部分覆盖会让改写把不对口的经历往这条要求上靠，正是编造最容易发生的地方，E5 会直接受影响。所以在跑 E5 全量之前先改这一版。

## 要做的

### 1. 先分清错在哪（不提交也可以，结论写进 README）

把开发集上 47 条三分类不一致逐条归类：模型判断错、标注口径错、规则没写清。标注确实不符合已确认规则的，改开发集标注并写明原因（开发集可以改，测试集标注封存不动）。归类结果写进 `evals/README.md`。

### 2. 提示词 v3（一个提交）

- 改的是原则，不是照着某几条案例补特例。方向：
  - 「部分覆盖」要求事实里有这条要求**本身**的一部分（复合要求中的某一项、同一技术的较浅程度），而不是同领域、相近技术或可迁移能力；相近经历判未覆盖，可以写进建议。
  - 技能栏只列名、没有使用场景的，按标注规则处理（看 README 已确认口径），不和别的事实拼起来升级。
  - 依据只引用直接支撑这条要求的事实，宁少勿多。
- `match_job.txt` 版本号改 3，更新 `versions.lock.json`；单元测试（假模型）里涉及提示词版本的地方同步。

### 3. 开发集重跑

- 开发集每组 3 次，和 v2 用同一个模型和参数。写下运行前预测（部分覆盖精确率、模型一致率、多引率），再跑。
- 合格线：模型判定一致率不低于 v2（90.2%），部分覆盖的精确率明显提高（v2 约 34%），已覆盖依据命中率不低于 95%，未覆盖 → 已覆盖不增加（这个方向最危险）。不合格就再改一轮，最多三轮，每轮写进 README。
- 结果报告 `evals/reports/e3-dev-v3-*.md`，和 v2 对照。

### 4. 不跑测试集

测试集用 v3 再跑一次，放到全部优化做完后的统一评测批次里（见 `06` T2.6「评测冻结」2026-11-26 调整），本任务不跑。README 写明「v3 开发集定稿」的提交号。
