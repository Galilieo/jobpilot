## 必须改

### [01] 任意一个旧字体版本都能让整个账号导出返回 500

**位置** `jobpilot/services/account_export.py:26`、`jobpilot/services/resume_content.py:103`

**场景** 用户在字体改用固定代码之前保存过一版简历，库里仍有 `font: ""` 或旧 CSS 字体串。普通预览和投递快照能读取这版，账号导出却用请求校验器解析每个历史版本。只要有一个旧值，整个归档就失败，待删除期间也下载不了。

**建议改法** 导出渲染复用 `ResumeContent.from_stored()`，归档中的原始 `content_json` 照常保留。用一份同时包含旧字体和新字体版本的账号验证整包可下载。

**是否已记过** 否。任务 E 已写明旧字体兼容要求，导出是本轮全局核查发现的遗漏。

### [02] 摘要可以把用户的否定写成已核实的肯定

**位置** `jobpilot/services/agent/work_summary.py:83`、`jobpilot/services/agent/work_summary.py:101`、`jobpilot/services/agent/compaction.py:432`

**场景** 原文是「我不接受外包」。压缩模型返回引文「接受外包」、结论「用户接受外包」，子串校验通过，后续对话在「要求」栏读到相反结论。`goal`、`done_and_decided` 也可由模型直接填写，程序没有检查是否存在对应的用户回答或已执行动作。压缩推进后，原文需要主动找回才会重新进入上下文。

**成熟做法** 将可追溯的用户原话、系统确认的业务状态和模型推断分开存放。引用存在只能证明这些字符出现过。

**建议改法** 要求和例外以保留否定、条件的完整原句或提问卡答案为准。业务完成状态尽量从数据库的动作结果生成。模型生成的转述和适用岗位无法核实时放入待核实区。

**是否已记过** 否。任务 Q §3 已要求保留否定和核验来源，未记录子串校验会放过相反结论。

### [03] 删除投递后，延迟重试可以重新创建这条投递

**位置** `jobpilot/services/applications.py:305`、`jobpilot/db/idempotency.py:114`、`jobpilot/db/idempotency.py:162`

**场景** 创建投递已提交，客户端因响应丢失准备重试。用户在另一标签页看见并删除该投递，删除也移除了幂等键。延迟的 POST 携原键到达，服务端创建新投递和初始阶段事件，岗位阶段也可能随之改变。幂等键的用途是让同一个操作重送时只生效一次。

**建议改法** 删除投递时清空成功响应内容，保留最小的已退役键和请求指纹。旧键返回明确的已删除状态，新键可以重新记录。岗位删除也复核同一种重放时序。

**是否已记过** 否。任务 O §10 记录的是删除岗位后仍能取回旧响应，本场景会重新写入数据。

### [04] 压缩和找回原文会先截断联系方式，再做脱敏

**位置** `jobpilot/services/agent/compact_input.py:42`、`jobpilot/services/agent/history.py:108`、`jobpilot/services/llm_gateway.py:337`

**场景** 把合成邮箱放在附件第 500 字边界，自动压缩只留下邮箱的一截。历史找回按字节分页时也有同类问题。网关看到的是片段，匹配完整邮箱的规则不会遮蔽其中仍能识别个人的账号名或域名片段。

**建议改法** 先对完整来源定位敏感片段，再构造外发预览和分页结果。保留原文与原游标，让本地读取和归档仍能拿到完整资料。

**是否已记过** 否。《03 可信安全与隐私》§3.2 已要求所有外发用途脱敏。

## 应该改

### [05] 有可用的较小请求时，超长重试仍可能直接结束本轮

**位置** `jobpilot/services/agent/graph.py:207`、`jobpilot/services/agent/window_messages.py:84`

**场景** 上游拒绝估算约 20K 的输入，去掉旧轮能缩至约 19K。代码要求至少缩 20%，所以会直接提示拆分当前消息，连 19K 的候选请求也不发送。换用默认配置时，HTTP 入口按字符放行，主调用按 UTF-8 字节预估，也可能在接收较长的中文 JD 后立刻拒绝运行。

**建议改法** 优先尝试缩减 20%，失败后尝试任一严格更小、满足窗口和剩余额度的请求。仍只发送一次重试。入口与窗口错误给出同一口径的可操作提示。

**是否已记过** 否。任务 Q §4 已允许当前轮本身太长时拒绝，另要求能缩小时重试一次。

### [06] 岗位删除与简历卡确认或撤销可能相互等待

**位置** `jobpilot/services/agent/graph.py:546`、`jobpilot/services/resume_versions.py:451`、`jobpilot/db/jobs.py:63`

**场景** 确认或撤销简历编辑先锁对话，再锁定制简历。另一标签页删除当前岗位时，先级联删除这份简历，再试图解除同一对话的岗位绑定。两边都等对方释放行锁。数据库会中止其中一笔事务，用户可能收到删除 500，或看到决定已保存、编辑却失败。

**建议改法** 统一涉及岗位、对话和简历的加锁顺序，或在跨资源编辑边界沿用投递创建的做法，遇到锁竞争即返回可重试的 409。

**是否已记过** 否。任务 T 已处理投递确认的一处类似锁顺序问题。

### [07] 领取幂等键与删除旧快照交错时可以返回 500

**位置** `jobpilot/db/idempotency.py:118`、`jobpilot/db/jobs.py:70`

**场景** 重试请求尝试插入，发现键已存在。下一条查询之前，删除岗位的事务移除了该键。查询用 `.one()` 读取已经不存在的行，抛异常并返回 500。投递删除共享这条路径。

**建议改法** 配合 [03] 保留退役状态。在领取键时显式处理行消失，让请求得到稳定的冲突或已删除响应。

**是否已记过** 否。任务 O §10 已修普通时序下重放出旧岗位内容的问题。

### [08] 恢复能守住单轮额度，仍可能重复发送同一逻辑调用

**位置** `jobpilot/services/agent/runtime.py:326`、`jobpilot/services/agent/graph.py:473`、`jobpilot/services/llm_gateway.py:558`

**场景** 已保存决定的一轮正在恢复，随后准备简历编辑卡。润色和依据检查已经付费，甚至卡片已入库，但进程在保存图的检查点前退出。重启时该节点可以重做，先调用模型，再按工具键去重卡片。旧调用仍占额度，第二次也会登记并可能计费。已正常结算的请求也一直按预扣量占本轮额度，长中文上下文可能在实际用量较低时提前耗尽额度。

**成熟做法** 检查点是供流程恢复的持久状态。外部调用要复用结果，还需要单独持久化可重放的业务结果，或使用提供方支持的请求幂等。

**建议改法** 出卡节点先用稳定工具键查已保存的候选，命中就直接复用。对已经发送但结果未知的调用继续保守计入。预扣和实际用量的差额是否释放，可和费用策略一起定。

**是否已记过** 部分。任务 O §2 已记持久化预算及未知用量，任务 Q §1 已记按字节预扣偏保守。出卡节点先付费再去重的顺序未记。

### [09] 旧提问卡答案在原文工具里读不回来

**位置** `jobpilot/services/agent/history.py:65`、`jobpilot/services/agent/questions.py:77`、`jobpilot/db/history.py:28`

**场景** `7af7af7` 把已回答的问题存成数组。新工具只从字典提取答案，再统一从步骤摘要移除 `answers`，所以按序号或关键词都拿不回旧答案。另一个缺口是附件关键词先匹配 JSON 的序列化文字，含真实换行或反斜杠的查询可能在这一层漏掉原文。

**建议改法** 复用现有的旧答案转换函数，用归属一致的确认卡恢复问题和答案。关键词筛选基于 JSON 中实际的文本值，并和分页层使用一致的匹配规则。

**是否已记过** 否。任务 Q §3 已把提问卡答案列为可找回来源。

### [10] 「我不想清空城市」仍可通过删除记忆的出卡校验

**位置** `jobpilot/services/memory_words.py:118`、`jobpilot/data/memory_keys.yaml:43`

**场景** 账号已有城市偏好。模型从「我不想清空城市」提议 `forget`。清空分支认出「清空」和「城市」，但保护词表没有覆盖「不想清空」，因此可以出删除卡。用户仍须确认。

**建议改法** 根据删除动词所在的短句判断否定作用在什么动作上。只有明确同意删除才出卡，语义含糊时澄清。

**是否已记过** 否。任务 Q §5 已要求把原话与操作绑定。

### [11] 复合学历修正仍会把「全日制」当作无关文字

**位置** `jobpilot/data/criteria_rules.yaml:58`、`jobpilot/services/criteria_match.py:319`、`jobpilot/services/criteria_match.py:591`

**场景** JD 写「全日制本科及以上」，用户只有非全日制本科。词表忽略「全日制」，教育档案也没有该维度。程序仍可用本科学位把整条硬性要求判为已覆盖，覆盖模型的待核对结论。

**建议改法** 把全日制、统招这类有实际限制但本地缺少数据的条件交给待核对。补上只满足学历等级的反例。

**是否已记过** 否。任务 O §11 已处理专业及技术要求的类似错误。

### [12] 投递对比会提示从未发出的文字，也会漏掉正文没变的依据变化

**位置** `jobpilot/services/application_diff.py:46`、`jobpilot/services/application_diff.py:151`、`jobpilot/services/resume_export.py:165`

**场景** 快照 JSON 中的待处理条目没有进入实际投递 HTML。它引用的事实后来变动，对比仍会提示用户准备这条。反过来，事实正文没改，仅把职责从「负责」改为「参与」，当前按文本比较的逻辑不会报变化。事实拆分、合并或删除后新建时，`lineage_id` 会把变更呈现为原事实删除及新事实新增。这个结果可用于追溯，无法表达它们之间的继承关系。

**建议改法** 简历条目对比复用导出可见性规则，风险比较包含能改变依据强度的结构化字段。拆分、合并继续按新增和删除报告，避免猜测配对。

**是否已记过** 否。任务 T §6 已定义对比和提醒的目标。

### [13] 降级删除投递表后，确认卡还指向消失的投递

**建议改法** 降级时显式失效本版专属的确认卡及等待这些卡的运行，记录受影响范围。记忆迁移也应说明删除档案和写作快照后，旧卡和历史消息如何处理。

**是否已记过** 部分。数据库设计 §2.20 已说明多次投递、快照和阶段历史会丢失，未说明确认卡和独立填写的日期、渠道。

### [14] 同一个岗位的「最新简历」有两种排序

## 清单一 · 隔离

## 清单三 · 费用

以下是仓库默认配置。**代码里未找到按账号、按天或按金额的总上限。** 因此单轮有界，反复开新轮、使用新请求键或手动压缩仍可累积费用。若要自用期间有硬上限，应在发送登记处共用一个日额度。上游账户自身的限额未核验。

| 路径 | 何时会调用、额度在哪里 |
|---|---|
| 对话主模型，含确认后继续 | 用户发消息或作决定后，后续多次发送不再逐次确认。默认每轮共享 **65 次、250,000 预扣 token、12 个工具步骤、180 秒运行时长预算**。同一消息 ID 重连会接入原运行或重放已保存内容，不单独开新轮 |
| 对话自动解析、匹配、改写 | `parse_jd` 默认按附件数、至少 1 次，`match_job` 2 次，`tailor_resume` 1 次。程序按参数复用同轮结果。改写内部若没有相同事实版本和岗位快照的报告，会自动匹配。子调用全部占父轮额度 |
| 简历编辑出卡前 | `polish` 先付费用模型润色，再跑第三层依据检查。`replace` 用用户给的文字，仍跑第三层。用户拒绝卡也已发生这些费用。记忆和投递的确认写入本身不调模型，恢复对话后主模型可继续 |
| 自动或手动压缩 | 一轮成功走到收尾后，超过有效窗口 80% 且可移出完整轮次时，后台自动启动。每段对话最多一个活跃压缩。预算独立，默认 **3 次**、配置输入上限 **24,000**、输出配置 **4,096**，账本总预扣上限 **84,288**，实际单次输出还受摘要空间限制。连续失败的自动暂停以同一摘要修订号及候选边界判断，有新完成轮次后仍可再试 |
| HTTP 直达业务接口 | 简历拆分 **3 次 / 60,000**，JD 解析 **3 次 / 40,000**，匹配 **3 次 / 40,000**，独立改写 **60 次 / 200,000**。独立改写内自动匹配共用该次改写预算。`/ocr` 和 `/extract-text` 走本地处理 |
| 网关重试、超长和重启 | 超时、连接错误和 5xx 默认共 2 次网络尝试。结构校验失败可另做 1 次 JSON 修复。主对话上游超长可尝试一次更小请求，已输出流式文字时停止自动重发。每次真实发送前登记，结算更新原行。崩溃后未知用量继续占原轮额度。普通运行重启标失败，已保存决定的对话会自动补做，仍有 [08] 的重复发送窗口 |

（默认配置：`jobpilot/config.py:67`；发送和重试：`jobpilot/services/llm_gateway.py:159`；持久化预算：`jobpilot/services/llm_gateway.py:533`；压缩安排：`jobpilot/services/agent/compaction.py:298`）

## 设计得好的地方

1. **已保存决定和执行结果可恢复。** 启动会补做已决定的等待运行，对话详情用同一份数据库快照读取消息、运行和卡片。对话的普通断线重连不用再发一轮。
2. **长期记忆的事实边界明确。** 同一栏目用修订号做乐观锁，也就是仅在保存时发现版本仍相同才写入。普通改写在建运行时固定三项写作枚举，新一轮生成才取新偏好。条目润色出卡时取当前写作枚举，确认和撤销复用已检查的候选。岗位匹配走已发布事实、求职条件和教育，改写和依据检查没有直接读取 `job_notes`，投递对比也不重新调用模型。主 Agent 能读到自由文字偏好，回答时仍需遵守事实来源边界。
3. **投递的版本、阶段和预览处理一致。** 创建和改阶段在同一事务追加事件，修改或撤销核对修订号。列表按最后追加的事件取得 `stage_changed_at`，补填较早日期不会取错事件。PostgreSQL 18 的列清单只将 `user_job_id` 或 `resume_version_id` 置空，`user_id` 保留。预览复用内容安全策略，模板转义用户文字，快照没有编辑器脚本。

（确认恢复：`jobpilot/services/agent/runtime.py:198`；记忆条件写入：`jobpilot/db/memories.py:29`；投递预览：`jobpilot/api/applications.py:84`）
