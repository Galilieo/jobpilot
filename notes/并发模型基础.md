# 并发模型基础：事件循环、线程池与多进程

**相关知识：async / await、协作式与抢占式调度、线程池、GIL、多进程、无状态服务**

**适用版本：Python 3.12、FastAPI 0.163（Starlette 1.10、anyio 4.16）、uvicorn**

2026-11-22 整理自 T1.4 第 ③ 步（本机 OCR）的讨论。代码示例来自 JobPilot 当前源码；「我的理解」保留我的原话并注明校准。

## 一、项目用途

只写 `async def` 和 `await`，并不会让程序自动并发。JobPilot 里有两处慢的计算，暴露了这个问题：

| 计算 | 耗时 | 位置 |
|---|---|---|
| OCR 识别一张截图 | 约 1 秒，长截图约 4 秒，期间占满全部 CPU 核心 | `jobpilot/services/parsing.py` 的 `ocr_pages` |
| argon2 校验或生成密码哈希 | 约 20 毫秒（故意设计得慢，防暴力破解） | `jobpilot/services/auth.py` |

如果直接在 `async def` 接口里调用它们，计算期间服务器不处理任何其他请求，连只需 1 毫秒的 `GET /api/me` 也要等。

## 二、三层调度

| 层次 | 谁来调度 | 方式 | 要注意什么 |
|---|---|---|---|
| 协程（事件循环内） | 代码自己 | 协作式：遇到 `await` 才让出 | 不能长时间不 `await`：CPU 计算和同步阻塞 IO 要移出去 |
| 线程（线程池） | 操作系统 | 抢占式：按时间片轮流 | 线程数量有限，等待时不应占着线程；Python 有 GIL，见第五节 |
| 进程（多 worker） | 操作系统 | 各自独立，内存不共享 | 状态放数据库或 Redis，不放 Python 变量 |

## 三、事件循环：一个线程，协作式

所有 `async def` 接口共用**一个事件循环线程**。它大致是这样一个循环：

```
while True:
    看看有哪些请求到了、哪些 await 的结果回来了
    挑一个可以继续执行的协程，运行它
    一直运行到它遇到 await，才交回控制权
```

新请求到了不会丢，会先排着；但只有当前协程交回控制权（遇到 `await`），事件循环才会去处理它。交回的时机完全由代码决定，操作系统管不到协程这一层。

| 代码在做什么 | 有没有 `await` 让出 | 要不要移出事件循环 |
|---|---|---|
| 查数据库、调用模型 API（`await session.execute(...)`） | 有，等结果时让出 | 不用，这正是 async 擅长的 |
| OCR、argon2 这类 CPU 计算 | 没有，一直在算 | 要，放到线程池 |
| 同步库的 IO，例如 `requests.get()`、`time.sleep()` | 没有，阻塞着等 | 要，或者换成异步库 |

**async 只对「等待」有效，对「计算」无效。** CPU 计算没有空闲的时间可以让出，写成 `async def` 也照样卡住事件循环。计算型任务只能交给别人执行：线程池、进程池，或者独立的任务队列服务。

单线程的事件循环也有好处：

| 好处 | 例子 |
|---|---|
| 不用加锁 | `OcrQueue` 的计数器直接 `+= 1`。检查和加一之间没有 `await`，不会切到别的请求 |
| 切换成本极低 | 协程切换只是保存几个变量；线程切换要进入操作系统内核 |
| 内存占用小 | 一个协程几 KB；一个系统线程默认要 MB 级的栈 |

## 四、线程池：把计算交给能被抢占的线程

### 4.1 基本用法

```python
# jobpilot/api/auth.py
password_ok = await run_in_threadpool(verify_password, body.password, hashed)
```

事件循环把 `verify_password` 交给线程池里的另一个线程执行，自己在 `await` 处让出，去处理别的请求；算完再回到这一行继续。函数本身仍然是同步的，变的是由谁来等。

Java 类比：`CompletableFuture.supplyAsync(() -> verify(...), executor)`；WebFlux 里把阻塞调用放到 `Schedulers.boundedElastic()` 上执行。

计算移走了，CPU 照样要花，为什么其他请求不受影响？因为线程由操作系统**抢占式**调度：时间片一到就强制切换，OCR 线程无法独占 CPU，事件循环线程总能分到时间。`/me` 只需约 1 毫秒的 CPU，最多从 1 毫秒变慢到几毫秒，不会等上 4 秒。

### 4.2 线程池是共用的，等待不能占着线程

FastAPI 的 `run_in_threadpool` 用的是 anyio 默认的线程池，上限 **40 个线程**，所有人共用：同步的 `def` 接口、同步依赖、读取落盘的上传文件（`UploadFile.read()` 内部就是 `run_in_threadpool`）都靠它。

T1.4 ③ 第一版的写法是：每个 OCR 请求先从共用线程池拿一个线程，再在线程里用 `threading.Lock` 排队。结果是排队的请求**各占着一个线程什么都不做**，40 个人排队就把线程池占满。

改进后（`jobpilot/api/ocr.py` 的 `OcrQueue`）：

```python
self.limiter = anyio.CapacityLimiter(1)   # OCR 专用，只有 1 个名额

async def run(self, filename: str, data: bytes) -> list[str]:
    return await anyio.to_thread.run_sync(
        ocr_pages, filename, data, limiter=self.limiter
    )
```

- 没轮到的请求在**事件循环里**等，只是一个暂停的协程，不占线程。
- OCR 用自己的名额，不再用共用线程池。
- 正在识别加排队超过 4 个，直接返回 503 并带 `Retry-After`，不让请求无限等。

Java 类比：第一版相当于每个请求都 `executor.submit()`，再在任务里 `lock.lock()`，线程全堵在锁上；改进后相当于在提交任务**之前**先用 `Semaphore` 控制，没轮到的请求根本不进线程池。

为什么 OCR 同时只跑一个？onnxruntime 一次推理就占满全部核心（配置 `intra_op_num_threads: -1`），两个同时跑只会互相抢核心、多占一份内存；而且 pdfium 不是线程安全的。`parsing.py` 里的 `_OCR_LOCK` 保留作兜底，防止别处直接调用 `ocr_pages` 时并发进入 pdfium。

## 五、GIL：为什么 Python 用多进程而不是多线程

### 5.1 GIL 是什么

CPython（官方的 Python 解释器）有一把**全局解释器锁（GIL）**：同一个进程里，同一时刻只有一个线程能执行 Python 字节码。开再多线程，纯 Python 的计算也只能轮流在一个核心上跑。

例外是 C 扩展：它在做不需要接触 Python 对象的计算时，可以主动**释放 GIL**，这段时间别的线程就能同时运行。hashlib、onnxruntime、argon2（通过 cffi 调用 C 库）都会这么做。所以第四节把 OCR 和 argon2 放进线程，确实能让事件循环同时干活。

多进程没有这个限制：每个进程有自己的解释器和自己的 GIL，操作系统可以把它们放到不同的核心上真正并行。

Java 没有 GIL，所以 Java 用多线程就能用满多核；Netty 按 CPU 核数开 N 个线程，每个线程跑一个事件循环。

> Python 3.13 起提供可选的无 GIL 构建（PEP 703），但默认安装仍带 GIL，不少 C 扩展也还在适配。JobPilot 用的 3.12 带 GIL。

### 5.2 实测

同样 4 份计算，分别串行、用 4 个线程、用 4 个进程执行（M 系列 Mac，10 核，Python 3.12.14）：

| 计算类型 | 串行 | 4 线程 | 4 进程 |
|---|---|---|---|
| 纯 Python 循环（全程持有 GIL） | 0.83 秒 | 0.81 秒 | 0.25 秒 |
| hashlib 计算 SHA-256（C 代码，计算时释放 GIL） | 0.31 秒 | 0.15 秒 | 0.07 秒 |

- 纯 Python：多线程**完全没有变快**，多进程快了约 3 倍。
- C 扩展：多线程也能变快，因为哈希计算期间释放了 GIL。它没快到 4 倍，是因为准备 200 MB 数据的那一步仍然持有 GIL，只能串行。

演示脚本：

```python
import hashlib
import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor

N = 4


def pure_python(_: int) -> int:
    total = 0
    for i in range(15_000_000):
        total += i
    return total


def c_extension(_: int) -> str:
    return hashlib.sha256(b"x" * 200_000_000).hexdigest()


def timed(label, run) -> None:
    start = time.perf_counter()
    run()
    print(f"  {label:<6} {time.perf_counter() - start:5.2f} 秒")


def main() -> None:
    for work in (pure_python, c_extension):
        print(f"{work.__name__}：")
        timed("串行", lambda: [work(i) for i in range(N)])
        with ThreadPoolExecutor(N) as pool:
            timed("4 线程", lambda: list(pool.map(work, range(N))))
        with ProcessPoolExecutor(N) as pool:
            list(pool.map(work, range(N)))  # 先把进程启动好，不计入耗时
            timed("4 进程", lambda: list(pool.map(work, range(N))))


if __name__ == "__main__":  # 必须有，见 5.3
    main()
```

### 5.3 坑：`if __name__ == "__main__":`

第一次运行这个脚本时漏了最后两行，报错 `An attempt has been made to start a new process before the current process has finished its bootstrapping phase`。

原因：macOS 和 Windows 创建子进程的默认方式是 **spawn**，即启动一个全新的解释器，再**重新导入主模块**，从中找到要执行的函数。没有这个保护的话，子进程一导入主模块，就又执行到创建进程池的代码，形成递归。加上保护后，子进程导入时 `__name__` 不是 `"__main__"`，不会再执行 `main()`。

### 5.4 多进程的代价

| 代价 | 说明 |
|---|---|
| 内存翻倍 | 每个进程各自加载一份代码和数据，例如 OCR 模型 |
| 启动慢 | 要启动新的解释器（所以演示里先预热进程池） |
| 通信要序列化 | 进程之间传参数和结果都要 pickle，传大对象开销明显 |
| 状态不共享 | 一个进程里的变量，别的进程看不到 |

所以 Python Web 服务的常见组合是：**每个进程内用事件循环处理大量等待型请求，再开多个进程用满多核。**

## 六、多 worker 部署

```bash
uvicorn jobpilot.main:app --workers 4
```

uvicorn 先由主进程打开监听端口，再启动 4 个子进程，共用同一个监听 socket。新连接由**操作系统内核**交给正在空闲等待的 worker，这部分不用写代码。多台服务器时，在前面放 Nginx 或云负载均衡，这也是配置。

真正要注意的是**存在进程内存里的状态**：

| 状态 | 存在哪 | 多 worker 时 |
|---|---|---|
| 登录 session、事实库、运行记录、LangGraph 检查点 | 数据库 | 不受影响 |
| `OcrQueue` 的计数和名额 | 进程内存 | 每个进程各算各的；只要 worker 数不超过核数，可以接受 |
| `_engine` 加载的 OCR 模型 | 进程内存 | 每个进程各加载一份，内存乘以 worker 数 |

原则：**让进程本身不保存状态，状态都放进数据库或 Redis**，扩容就只是改启动参数。

以后会遇到的地方：第 3 周 Agent 对话的「停止生成」。停止请求可能落到 worker 2，而正在生成的任务在 worker 1。停止信号如果只是 worker 2 内存里的一个变量，worker 1 收不到，要经过数据库传递，例如在 `ai_run` 写一个「已请求取消」标记，由运行中的任务定期检查。

## 七、我的理解

- 「事件循环本身有点算单线程，如果有事件来了不分出去会一直等。」
  - 校准：它就是单线程。新请求会先排队，等当前协程遇到 `await` 交回控制权才会被处理。要「分出去」的是长时间不 `await` 的代码，不是新来的请求。
- 「操作系统的底层设计让每个时间片的事件不能占太久。」
  - 校准：准确地说是抢占式调度，时间片用完由操作系统强制切换线程；协程那一层没有这种强制。
- 「之前学习写的时候基本没意识到这个底层问题，多 worker 只知道要 async 异步处理。」

## 八、误区与验证

| 误区 | 实际 | 证据 |
|---|---|---|
| 写成 `async def` 就不会阻塞 | 没有 `await` 的计算照样卡住事件循环 | 第三节；argon2 改为 `run_in_threadpool`（提交 `beb50c0`） |
| 放进线程池就万事大吉 | 线程池共用且有限，排队的请求不能占着线程 | `tests/test_ocr.py::test_waiting_requests_hold_no_thread`：断言共用线程池借出 0 个；改回旧写法后同时运行数变成 3，测试失败 |
| 多线程能让 Python 计算变快 | 纯 Python 计算受 GIL 限制，多线程无效 | 第五节实测：0.83 秒对 0.81 秒 |
| 多 worker 只要接口是 async 就行 | 进程内存不共享，状态要放数据库 | 第六节；session 存数据库，所以登录不受 worker 数影响 |

## 九、自检问题

写接口时问自己：

1. 这段代码会不会长时间不 `await`？会的话交给线程池。
2. 排队等待时，是不是占着某种有限的资源（线程、数据库连接）？
3. 这个状态存在内存里，换一个进程还看得到吗？看不到就放进数据库。

面试常见问法：「FastAPI 里 `async def` 和 `def` 有什么区别」「为什么 Python 用多进程而不是多线程」「服务开多个实例时要注意什么」。
